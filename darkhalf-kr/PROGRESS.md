새 세션에서 이 파일부터 읽으면 이어서 작업할 수 있습니다.

- **대상**: `Dark Half (Japan).sfc` — SNES HiROM, 3MB, MD5 `55108013f875db3b39da04b8f58489ab`
- **작업 폴더**: `darkhalf-kr/`
- **목표**: 전체 한글화. 메뉴 UI + 마법/아이템 설명문 완료, 한자 553자 식별 완료(대사 판독률 98.7%)
- **버전**: 현재 **`v0.9.0`** (완성 = `v1.0.0`). 남은 것은 §4.38.7 아래와
  README 의 「버전」 표에 있다 — 몬스터 이름표, 컷신 「復活節第１日」, 실기 통과 플레이

## 1. 확정된 기술 사실

### 1.1 인코딩 (relative search + 폰트 렌더로 검증)

1바이트 코드. 가나가 반각 가타카나 Shift-JIS 코드와 같은 자리에 배치돼 있고, 글리프만 히라가나로 렌더됩니다.

| 코드 | 내용 |
|---|---|
| `0x20` | 공백 |
| `0x21` `0x3F` | `！` `？` |
| `0x30-0x39` | `０`~`９` |
| `0x41-0x5A` | `Ａ`~`Ｚ` |
| `0xA1-0xA6` | `。` `「` `」` `、` `‥` `を` |
| `0xA7-0xAF` | 작은 가나 `ぁぃぅぇぉゃゅょっ` |
| `0xB0` | 장음 `ー` |
| `0xB1-0xDD` | `あ` ~ `ん` (45자 연속) |
| 그 외 `0x22-0xA0` 산재 | 단일바이트 한자·가타카나 |

전체 테이블은 `darkhalf.tbl`, 폰트 시트는 `font_single.png`.

### 1.2 제어 코드

| 코드 | 의미 | 근거 |
|---|---|---|
| `0xFF` | **메시지 종료** | 포인터 테이블 목적지 직전이 58/58 일치 |
| `0x01` | **탁점** (앞 글자에 결합) | `ト`+01=`ド`, `ホ`+01=`ボ` → "オレはドロボー" 복원 |
| `0xE3` | 개행 | |
| `0xF5 xx` `0xF6 xx` `0xF7 xx` | 한자 뱅크 0/1/2 | `F505`=人 `F512`=王 `F50E`=下 |
| `0xF7 xx` | 한자 뱅크 2 | 원문 대사에서 171회 사용 확인 |
| `0xEB xx` `0xE7` `0x06` `0x1C` 등 | 미해독 | 고정쌍 관측: `F0 C4`(92%) `F2 01`(91%) `1C 06`(81%) `FB EB`(67%) |

**`0x00`~`0x05`는 제어 코드가 아니라 실제 글리프입니다.** `00=魔` `01=士` `02=見` `03=ヴ`
`04=◀` `05=▶`. 「聖騎士」가 `F50A F50B 01`, 「発見」이 `F531 02` 로 쓰입니다.
`0x01`만 예외로, 앞 글자가 탁음 가능한 가나면 탁점으로 결합하고 아니면 `士` 글리프가 됩니다.
이걸 제어 코드로 버리면 문맥이 잘려 보입니다 (`kanjictx.py` 의 렌더러가 이 규칙을 구현).

**중요**: 탁음을 항상 `기본+0x01`로 쓰므로 완성형 탁음 슬롯(`0x02-0x1F`, `0xE6-0xFF`)의 **코드값이 통째로 비어 제어 코드로 재활용**되고 있습니다. 본문에 `ざ`(0xEB)가 1426회 나오는 식의 이상한 통계는 전부 이것 때문입니다.

### 1.2.1 글리프 주소 지정 = 10비트 평면 인덱스 (코드 확정)

`0x005c96` 글리프 페치 루프:

```
a5 00              LDA $00          ; 글리프 인덱스
0a 0a 0a 0a 0a 0a  ASL x6           ; x64
aa                 TAX
bf 00 00 ef        LDA $EF0000,X    ; 폰트 데이터
```

`0x009544` DMA 큐 설정도 동일하게 소스 뱅크 `$EF` 고정, 오프셋 `인덱스*64`,
전송 크기 `#$0040`. 단일바이트 인덱스 계산은 `0x009530` (SBC/CMP 로 범위 보정).

**이스케이프 판별 루틴 `$5CFA` (텍스트 바이트 -> 글리프 인덱스)**

```
005cfa  c9 f8 / b0 0e     CMP #$F8, BCS -> 제어 코드 경로
005cfe  c9 f4 / 90 0a     CMP #$F4, BCC -> 단일바이트 경로
                          ; 즉 $F4 <= A <= $F7 이 이스케이프
005d02  29 03             AND #$03      ; 하위 2비트만 인덱스 상위 바이트로
005d04  85 01
005d06  20 f1 5c          JSR $5CF1     ; 다음 바이트 읽기
005d09  85 00             STA $00
```

`$5CF1` 은 `LDA [$28]` + 포인터 증가 = '다음 텍스트 바이트 읽기'.

**이스케이프는 `$F4`~`$F7` 네 개이고, F5/F6/F7 은 별개 뱅크가 아니라
10비트 글리프 인덱스의 상위 비트다.**

**`$F4` 는 이미 동작하는 프리픽스다.** `F4 xx` = 인덱스 `0*256+xx` = 0~255 로,
맨바이트로는 쓸 수 없는 제어 범위 인덱스에 닿는 경로다. 원문이 실제로 그렇게
쓴다 (본문 153회): `F4 00`=魔 `F4 01`=士 `F4 02`=見 `F4 FF`=★.
맨바이트면 0x00~0x02 는 결합 부호로, 0xFF 는 메시지 종료자로 먹히기 때문이다.

**결합 부호는 세 개다** (`$5D0C` 이후). 현재 바이트가 글리프일 때 '다음'
바이트가 0x00/0x01/0x02 면 앞 글자의 인덱스를 보정한다.
본문 분포로 확인: `0x01` 3,705회(앞 글자 か/た/て/と = 탁점),
`0x02` 144회(앞 글자 は행 = 반탁점). `0x00` 의 682회는 대부분 제어 파라미터다.

주의: 한자 뒤에 맨 `0x01` 을 두면 **앞 한자의 인덱스가 보정되어 엉뚱한 글리프**가
나온다. 士를 쓰려면 반드시 `F4 01` 로 써야 한다.

| 표기 | 글리프 인덱스 | ROM 주소 |
|---|---|---|
| 단일바이트 `c` | c | `0x2F0000 + c*64` |
| `F5 xx` | 256 + xx | `0x2F4000 + xx*64` |
| `F6 xx` | 512 + xx | `0x2F8000 + xx*64` |
| `F7 xx` | 768 + xx | `0x2FC000 + xx*64` |

X 가 16비트이므로 **주소 지정이 1,024 글리프에서 끊긴다**
(`0x2F0000`~`0x300000` = 정확히 64KB = 1024 x 64바이트).
뱅크를 더 추가하려면 인덱스를 11비트로 넓히고 페치 루틴, DMA 설정,
텍스트 파서의 이스케이프 인식을 함께 패치해야 한다. 파서 쪽은 미특정.

### 1.2.2 엔진 패치 — 글리프 인덱스 10비트 -> 11비트 (실기 검증 완료)

수용량 상한을 없애기 위해 렌더러를 패치했다. **실기에서 작동 확인** (image/002.png:
힐 설명문에 「한글성공 확장！」 이 정상 렌더).

**패치 원리**

인덱스 1024 를 `ASL x6`(x64) 하면 `0x10000` 이라 16비트에서 하위 `0x0000` 으로
감긴다. 즉 하위 16비트는 이미 '다음 뱅크 내 오프셋'으로 정확하고, 바꿀 것은
**뱅크 바이트 하나**뿐이다.

    뱅크 = $EF + ($6A >> 2)

`$6A` 가 0~3 이면 `$EF`, 4~7 이면 `$F0`. HiROM 에서 뱅크 `$F0` = ROM `0x300000`
이므로 롬을 4MB 로 확장해 그 자리를 새 폰트 영역으로 쓴다 (헤더 롬 크기 바이트는
원래부터 `0x0C` = 4MB).

`$6A` 는 `0x9552` 의 `STA $69`(16비트) 에서 덮이므로 뱅크 계산을 인덱스 시프트보다
**먼저** 해야 한다. 그래서 `0x9548` 이후 꼬리를 빈 공간으로 옮겨 재구성했다.

**패치 지점** (`patch_engine.py`)

| 주소 | 변경 | 크기 |
|---|---|---|
| `0x00950F` | `JMP $F200` — 이스케이프 판별 확장 (메인 대사 렌더러) | 39바이트 |
| `0x005CFA` | `JMP $F260` — 이스케이프 판별 확장 (옵션·엔딩 렌더러) | 37바이트 |
| `0x009548` | `JMP $F300` — DMA 꼬리 재구성, 뱅크 계산 | 63바이트 |
| 롬 크기 | 3MB -> 4MB | |

`$5CFA` 는 바이트를 `A` 로 받아 상위를 `$01` 에 직접 저장하는 구조라 `$950F` 쪽과
코드가 다르다. 새 코드는 빈 공간 `0x00F200`/`0x00F260`/`0x00F300` (뱅크 `$C0`).

**프리픽스로 쓴 바이트**

`$5D`(備) 와 `$D5`(ゆ). 이 두 바이트는 우리가 번역하지 않는 구간(설명문 A/B,
옵션·엔딩 텍스트)에서 한 번도 쓰이지 않는다. 마법·아이템 이름 테이블은
`0x4f3d3` 부근으로 뱅크 0x04 안이라 우리 통제 하에 있다 (`ヒール` 를 인코딩해
검색으로 확정).

    $5D xx -> 인덱스 1024+xx -> ROM 0x300000 + xx*64
    $D5 xx -> 인덱스 1280+xx -> ROM 0x304000 + xx*64

**부작용**: 이 두 바이트가 이제 프리픽스이므로 단일바이트 글리프로 배정하면
안 된다 (`krcodec.PREFIX_BYTES`). 그래서 단일바이트 슬롯이 145 -> 143 으로 줄고,
그 영향으로 기존 설명문 2개가 1바이트씩 넘쳐 문구를 줄였다.
또 **아직 번역하지 않은 일본어 세그먼트 중 備/ゆ 가 들어간 것은 깨져 보인다.**
전량 번역이 끝나면 해소된다.

**확장 여지**: 뱅크 계산이 `$6A >> 2` 이므로 `$6A` = 6, 7 (인덱스 1536~2047,
ROM `0x308000`~`0x30FFFF`) 도 **코드 변경 없이** 쓸 수 있다. 프리픽스로 쓸 여분
바이트만 더 확보하면 된다.

## 2. 결정적 제약

### 2.1 텍스트 영역이 100% 꽉 참

뱅크 0x04 텍스트 영역 62,464바이트 = 런 본문 61,058 + 종료자 1,406. **여유 0바이트.**

### 2.2 리포인팅 금지 → 제자리 삽입만

번역문 길이를 바꿔 재배치했더니 **게임이 메뉴에서 멈췄습니다.** 원인은 주소 이동으로 미갱신 참조가 깨진 것입니다. 뱅크 0x04 밖에도 이 텍스트를 가리키는 테이블이 있고(`0x052128`, `0x054c41`, `0x0a045f` 등), 포인터가 하나도 없는 고아 런이 254개(5,025바이트) 있습니다.

전수 조사도 시도했으나 실패했습니다 — 런 시작 후보가 1,088개라 임의의 u16이 우연히 맞을 확률이 1.7%, 300만 위치면 기대 오탐이 5만 개입니다. 정적 스캔으로는 진짜 포인터를 가려낼 수 없습니다.

**따라서 현재 방식: 원본과 동일한 바이트 길이로 제자리 삽입, 남는 자리는 공백(`0x20`) 패딩.** 주소가 안 바뀌므로 포인터를 건드릴 필요가 없고 이 문제가 구조적으로 발생하지 않습니다.

### 2.3 바이트 예산

일본어 평균 **1.59 바이트/자**. 한글은 음절당 2바이트(뱅크) 또는 1바이트(단일바이트 슬롯).

현재는 미번역 일본어를 읽을 수 있게 **가나 글리프를 보존**하고 있어 단일바이트 슬롯이 34개뿐 → 평균 1.34~1.59 바이트/음절. 번역문이 원문보다 짧아야 합니다.

전면 번역 시엔 가나 145칸을 전부 회수할 수 있어 평균 1.0 근처로 떨어집니다.

### 2.4 고유 음절 상한 — 전면 번역의 실질 제약

수용량은 **1,321자**다. 엔진 패치(1.2.2)로 프리픽스 두 개를 추가해 확보했다.
(913 -> 753 -> 811 -> 1,321. 913 은 잘못된 가정, 753 은 실측, 811 은 `$F4`
프리픽스 발견, 1,321 은 엔진 패치.)

| 구분 | 슬롯 | 근거 |
|---|---|---|
| 단일바이트 | 145 | `0x20-0xDF` 중 보존 47개 제외 |
| F5 뱅크 | 256 | 전 구간 실제 글리프 |
| F6 뱅크 | 256 | 전 구간 실제 글리프 |
| F7 `0x00-0x3D` | 62 | 실제 글리프 (橋速遅左右輝識謁書修木節第臨土景 등) |
| F7 `0xDE-0xFF` | 34 | `0xFF` 채움 = 미사용 |
| **확정 안전 합계** | **753** | |
| F7 `0x3E-0xDD` | 160 | **엔딩 텍스트다** (2026-09-08 확정). `0x2FCFC0~0x2FF780`, 10,176바이트. 절대 덮으면 안 된다 |
| 주소 지정 이론 상한 | 1,024 | 10비트 인덱스 |

**필요량 추정**: 번역 91개(1,026음절) 시점의 Heaps 피팅 `V = 3.12 * N^0.647`,
전체 예상 19,500음절 -> 고유 **1,600~1,900자**. 보수적으로 봐도 1,600자.

**해결됨.** 엔진 패치(1.2.2)로 수용량이 1,321자가 되어 필요량 약 1,200자를
넘겼다. 어휘를 극단적으로 줄일 필요가 없어졌다. 아래는 패치 전 분석 기록이다.

패치 전 상황: 주소 지정 상한(1,024)을 전부 써도 필요량의 60% 였다.

다만 811자는 753자보다 실질적으로 다르다. 어휘를 의식적으로 통제한 번역이라면
(어미 고정, 한 개념 한 단어, 희소 음절 회피, 고유명사 12개 정도) 700~820자에
들어갈 수 있다. **빡빡하지만 가능한 범위**다. 대신 진행 중에 곡선을 감시해야
후반에 벽을 만나지 않는다 — `trcheck` 가 구간별 가드레일로 경고한다.

대응 방침 (사용자 확정): 어휘를 753자 인벤토리에 맞춘다. 문체의 다양성을

## 4. 미해결 문제

### 4.1 메뉴 폰트가 한글로 안 나옴 ← 미해결, 여러 차례 실패

**증상**: 메뉴 폰트를 쓰는 창만 한글화가 안 먹음. 대화창·설명문은 정상.

**2026-09-04 갱신 — 영향 범위가 라벨 13개가 아니었다. 우선순위 낮음 -> 높음.**

같은 문자열이 창마다 다르게 나오는 것을 프로브로 확정했다
(`make_probe_list.py`, 소생 탐침 화면 2장).
마법 [06] 이름을 단일바이트 코드만으로 「소생」(`b1 d4`) 으로 바꿨더니

| 창 | 출력 | 쓰는 폰트 |
|---|---|---|
| 마법 설명문 | 「소생」 | 메인 폰트 (0x2F0000) — 패치됨 |
| 마법 목록 | 「あや」 | 메뉴 폰트 — 미패치 |

`B1=あ`, `D4=や` 다. 즉 목록 창은 **패치한 글리프를 안 보고 원본 가나를
본다.** 이 관측 자체는 아래 '확정된 관측' 에 이미 있던 것과 같다
(0xB1 을 덮었는데 あ 가 나옴). 이번에 새로 확정된 것은 **범위**다.

  - 마법 이름 목록, 포메이션 창, 장비 창이 모두 메뉴 폰트를 쓴다
  - 즉 4.1 을 풀지 않으면 마법·아이템·장비 이름은 화면에서 영원히 일본어다
  - 라벨 13개 문제가 아니라 이름표 전체의 전제 조건이다

**VRAM 덤프로 배제한 것** (2026-09-04, 목록 창 열린 상태, 마제스티 수동 export)

덤프는 확보했다. 기존 문서가 선행 조건으로 지목한 바로 그 자료다.
그런데 이것만으로는 폰트 위치가 안 나왔다. 배제한 것을 남긴다.

| 시도 | 결과 |
|---|---|
| VRAM 비어있지않은 타일 3,038개를 롬에서 그대로 검색 | 237개 발견. 전부 배경·스프라이트 (0x26b000 0x26d000 0x1f1000 0x271200) |
| 메인 폰트 あ 비트맵을 VRAM 에서 검색 (2bpp OR / plane0만 / plane1만 / 1bpp) | 전부 0곳 |
| plane0==plane1 서명으로 글리프형 타일 추출 | 89개. 전부 창 격자무늬·세로줄 (VRAM 0x1400~0x1800) |
| 대역별 잉크량 필터로 글자 형태 육안 탐색 | 전부 디더링된 배경 그래픽 |

핵심 소득이 하나 있다. **메뉴 폰트의 あ 는 메인 폰트의 あ 와 비트맵이 다르다.**
같은 서체를 재인코딩한 것이 아니라 별개 서체다. 그래서 메인 폰트 비트맵으로
VRAM 이나 롬을 검색하는 접근은 원리적으로 실패한다. 이 계열은 더 시도하지 말 것.

또 하나. 내가 만든 「소」「생」 글리프와 ♥(0xa0) 이 이 덤프에 없다.
목록 화면은 그것들을 그리지 않으므로 당연하고, 동시에 **목록 창이 메인 폰트
글리프를 단 하나도 쓰지 않는다**는 독립 확증이다.

**DMA 로그로 확정한 것** (2026-09-07, `dma_log3.txt` 953줄, 마제스티 제공)

| 경로 | 관측 | 뜻 |
|---|---|---|
| 메인 폰트 | `src=$EF:xxxx size=64` **172건 전부 64바이트** | ROM 0x2F0000 에서 글리프 단위 직접 DMA. 기존 결론과 일치 |
| 메뉴 텍스트 | `src=$7E:81xx~85xx` -> `VRAM $F1xx~$F5xx` (델타 일정 0x7016) | **WRAM 에서 조립한 뒤 DMA** |

전체 소스 뱅크 분포: `$7E` 543건, `$EF` 172건, `$C6` 90건, `$C0` 33건,
`$CF`/`$E6` 32건, `$E7` 24건, `$7F` 15건, `$DF` 12건.

**이것이 롬 바이트 검색이 전부 실패한 이유다.** 메뉴 글리프는 롬에서 VRAM 으로
바로 가지 않는다. CPU 가 WRAM 버퍼에 조립하고 그 버퍼를 DMA 한다. 그래서
VRAM 타일과 롬 바이트가 일치하지 않는다 (압축이 아니라 조립이었을 수 있다).

VRAM 덤프와 이 로그를 직접 대응시키지는 않았다. 두 자료가 서로 다른 세션이라
같은 화면 상태가 아니다. 그 대응은 추정이므로 세우지 않는다.

**WRAM 추적 1차 결과 — 대상이 틀렸다** (`wram_write2.txt`)

`$7E:8100~8600` 에 쓰이는 값이 `00 01 02 03` / `20` / `23` / `32` 였다.
글리프 비트맵이 아니라 **타일 인덱스**다. 즉 그 버퍼는 타일맵이고, 그것이
VRAM `$F100~$F600` 으로 간다. 폰트 CHR 은 다른 경로다.

건진 것이 있다. `PC=$C0:9593/9597/959B/959F` 가 `00 01 02 03` 을
`$7E852C/852E/856C/856E` 에 쓴다. 0x40 간격 2x2 배치이므로 **16x16 글자
하나를 타일 4개로 놓는 루틴**이다. 즉 목록 창의 글자도 16x16 이다.

**CHR 조립 버퍼를 로그로 특정했다** (`dma_log3.txt` 재분석)

WRAM -> VRAM `$0000~$1FFF` 전송이 434건이고 그 소스가 몰려 있다.

| 소스 | 건수 |
|---|---|
| `$7E:2C00xx` | 246 |
| `$7E:2B00xx` | 178 |
| `$7E:27xx` | 8 |

전송 크기가 8~60바이트로 잘게 쪼개져 있다. 글리프를 조립해 부분 전송하는
방식이다. `$7E:273B`(v1 이 본 주소)도 이 목록에 있지만 8건뿐이고 본체는
`$2B00~$2CFF` 다. v1 이 실패한 이유가 이것일 수 있다.

**WRAM 2차 추적도 대상이 틀렸다** (`wram_write3.txt`)

`$7E:2B00~2CFF` 에 쓰이는 값이 `0x78 0x80 0x88 0x90 0xB0 0x28` 같은 좌표성
변수였다. 글리프 비트맵이 아니다. 그 구역은 스크롤·위치 변수로도 쓰인다.

DMA 로그에서 이 구역을 소스로 본 것은 내가 `r[1] & 0xFF00` 으로 버킷팅해
`$2B00xx` 로 뭉갠 결과였다. 실제 소스 오프셋은 `$273B~$F0A9` 로 넓게
퍼져 있어 특정 버퍼로 좁혀지지 않는다. **버킷팅이 만든 착시였다.**

**64바이트 전송 전수 조사 — 메뉴 폰트 전송이 이 로그에 없다**

64바이트는 16x16 글리프 1개 크기다. 전체 215건의 소스를 갈랐다.

| 소스 | 건수 | 오프셋 종수 | 판정 |
|---|---|---|---|
| `$EF` | 172 | 다수 | 메인 폰트. 글자마다 오프셋이 다르다 |
| `$C6` | 36 | **2종** (`0x951`, `0x991`) | 폰트 아님. 같은 것을 반복 전송하는 그래픽 |
| `$7E` | 7 | 5종 | WRAM 조립분 |

`$C6` 는 오프셋이 두 개뿐이므로 폰트일 수 없다. 폰트라면 글자마다 달라야 한다.
그리고 폰트 CHR 을 통째로 올리는 큰 전송(0x800 이상)이 로그에 아예 없다.

즉 **세 번의 로그로도 메뉴 폰트의 롬 출처를 특정하지 못했다.** 배제만 늘었다.

**그래도 확정된 진입점이 하나 있다 — 여기서 코드 읽기로 전환한다**

`PC=$C0:9593` 이 16x16 글자를 타일 4개로 배치하는 루틴이다 (`00 01 02 03` 을
`0x40` 간격 2x2 로 쓴다). 그리고 이 주소는 **내가 이미 패치한 메인 렌더러와
같은 구역**이다.

  `0x00950F`  이스케이프 판별 (내가 패치)
  `0x009548`  DMA 꼬리, 뱅크 = `$EF + ($6A>>2)` (내가 패치)
  `0x009593`  16x16 글자를 타일 2x2 로 배치  <- 목록 창 경로로 확인됨

목록 창 텍스트가 메인 렌더러 구역을 타는데도 원본 가나가 나온다. 그러므로
같은 폰트를 쓰면서 **인덱스나 뱅크 계산이 다른 갈래**가 있을 가능성이 높다.
이것은 로그가 아니라 디스어셈블로 확인할 일이다.

**코드 읽기로 확정한 것** (2026-09-08, 롬만으로)

`0x9593` 주변을 디스어셈블해 대사·설명문 렌더러의 전모를 읽었다.

```
0x009548  REP #$20 / LDA $69 / ASL x6        인덱스 x64
0x00955c  ADC #$1800                          VRAM 목적지 워드주소 = 0x1800 + Y*8
0x009576  LDA #$80EF / STA $0700,X            소스 뱅크 $EF 를 상수로 지정
0x009590~ STA $7FEA,X / $7FEC,X / $802A,X / $802C,X   타일맵 2x2 배치
```

즉 이 경로는 **뱅크 $EF(ROM 0x2F0000)를 코드에 박아** 쓰고, 글리프를 VRAM
바이트 0x3000 부근에 올린다. 내가 패치한 그 경로다.

DMA 뱅크를 쓰는 지점을 전수 조사했다 (`STA $0700,X` = `9d 00 07`, 12곳).
상수로 지정하는 곳은 넷뿐이다.

| 주소 | 뱅크 | 정체 |
|---|---|---|
| `0x009579` | `$EF` | 메인 폰트. 대사·설명문 |
| `0x003e5c` `0x003f46` `0x007b9f` | `$7E` | WRAM 조립분 |
| `0x025f94` `0x025fe2` | `$7F` | WRAM 상위 |

나머지는 `LDA $06FE,X` 로 읽는데, X 가 슬롯당 2씩 늘므로 `$06FE,X` 는
**직전 큐 슬롯**이다. 즉 앞 전송의 뱅크를 물려받는 것이고, 새 폰트 주소를
지정하는 코드가 아니다.

**따라서 롬에서 VRAM 으로 폰트를 올리는 경로는 $EF 하나뿐이다.**

그런데 프로브에서 목록 창은 원본 가나를 보였다. 롬에 あ 비트맵은
0x2F2C40 한 곳뿐이고 프로브 롬에는 그 자리에 한글이 들어 있다. 그러므로
목록 창은 **롬에서 직접 읽지 않는다.** 남는 설명은 하나다 —
롬(압축 또는 별도 포맷) -> WRAM -> VRAM 소구간 전송.

이것은 DMA 로그의 관측과 일치한다 ($7E 소스 543건, 큰 롬 전송 없음).

**다음에 할 것**: WRAM 폰트 적재 구간을 특정해야 한다. 다만 그 구간을
두 번 잘못 짚었으므로(4.1 기록 참조) 추측으로 대상을 정하지 않는다.
부팅·장면 전환 시 WRAM 에 쓰는 큰 루프를 찾는 것이 정공법이다.

**우선순위 재조정**: 4.1 을 풀지 않아도 이름표는 확인 창·대사 삽입·설명문
에서는 정상 표시된다 (실기에서 확인됨). 그래서 아이템
이름표 조립기를 먼저 만드는 편이 눈에 보이는 진전이 크다.

**로그 요청은 중단한다.** 세 번 받아 배제 목록만 늘렸다. 다음은 `0x9593`
주변을 읽어 어느 DMA 설정을 쓰는지 확인하는 것이고, 그것은 롬만 있으면 된다.

버퍼를 채우는 것은 CPU 쓰기이므로 DMA 로그로는 안 보인다. 그 버퍼에 쓰는
명령의 PC 를 모으면 루틴을 특정할 수 있고, 루틴을 읽으면 원본 폰트의 롬
주소가 나온다. 대상 주소는 추측이 아니라 위 로그로 확정한 `$7E:8100~8600` 이다.

(기존 `tracewram.lua` 는 `$7E:273B` 를 봤는데 그것은 실패한 추적에서 나온
추정 주소였다. 그 계열을 반복하지 말 것.)

**참고 — 예전 DMA 로그** (이 방법으로 메인 폰트 경로를 이미 확정한 전례가 있다)

기존 문서에 「DMA 로그에서 `src=$EF:xxxx size=64` 가 45건」 으로 설명문 경로를
확정한 기록이 있다. 같은 방법을 목록 창에 적용하면 소스 주소가 직접 나온다.
글리프 비트맵을 추측할 필요가 없어진다.

  Mesen `Debug -> Event Viewer` 를 열고 마법 목록 창을 여는 순간을 기록.
  또는 `Debug -> Trace Logger` 로 DMA 레지스터($4300-$437F) 기록.
  필요한 것은 그 창을 열 때 발생하는 DMA 의 **소스 주소와 크기**다.

**이번에 추가로 배제한 것** (역검색 계열은 문서가 금지한 길이었다. 반복하지 말 것)
| 시도 | 결과 |
|---|---|
| あ 글리프 64바이트 롬 전체 검색 | 원위치 1곳뿐. 생(raw) 복사본 없음 |
| 행단위 1bpp 32바이트로 재포장해 검색 | 0곳 |
| 타일순서 1bpp 32바이트로 재포장해 검색 | 0곳 |
| 상단 8행 16바이트만 검색 | 0곳 |

메뉴 폰트는 메인 폰트의 단순 재인코딩이 아니다. 압축이거나 별개 서체다.
(문서의 기존 경고대로 '압축 확정' 으로 단정하지 않는다. 배제된 것은
'단순 재인코딩' 가설뿐이다.)

**확정된 관측** (진단 ROM `make_probe.py` 로 재현 가능)
- 메뉴 라벨 바이트를 바꾸면 표시가 바뀜 → 게임이 패치한 바이트를 읽는 것은 맞음
- 코드 `0xB1`(히라가나 범위)을 한글로 덮었는데 화면엔 `あ`가 나옴
- 코드 `0x71`(가타카나 범위)도 마찬가지로 `ア`가 나옴
- 코드 `0x22`(한자 범위)는 깨져서 나옴

**확정된 반대 사실**: 마법 이름·설명문은 메인 폰트를 씀. DMA 로그에서
`src=$EF:xxxx size=64` 가 45건 잡혔고, `$EF`=ROM `0x2F0000` 이며 64바이트는
글리프 1개. 코드로 환산하니 `ヒール` + `ＨＰを回復する呪文` 이 정확히 복원됨
(뱅크 F5/F6 한자까지 일치). **즉 설명문 경로는 메인 폰트 글리프 단위 DMA.**

**실패한 추적들** (같은 길 반복 금지)
| 시도 | 결과 |
|---|---|
| VRAM 타일을 ROM 에서 역검색 | 일부 구간만 맞음. "압축 확정"은 **오판**이었음 |
| `$E7:1200`(=ROM `0x271200`) 추적 | VRAM 과 128/128 일치하지만 **스프라이트 그래픽**이었음 |
| `$7E:273B` → VRAM `$5C00` 추적 | 값이 `1F 07 03 / E0 F0 F8 FC FF` → **창 테두리** 생성 버퍼 |
| VRAM 에 직접 쓰기 콜백 | Mesen 이 VRAM memType 콜백 미지원. 로그 빈 파일 |
| `emu.isKeyPressed("D")` | 무반응 (키 이름/포커스 문제) |
| 진단 ROM VRAM 덤프 | 메뉴가 열린 화면이 안 잡힘. 한글도 원본 가나도 VRAM 에 없음 |

**Mesen2 Lua 주의점**
- `emu.getState()` 는 **점 포함 평면 키**를 씀: `st["cpu.pc"]`, `st["cpu.k"]`.
  `st.cpu.pc` 는 nil → PC 가 `$00:0000` 으로 찍힘
- VRAM 은 `addMemoryCallback` 대상이 안 됨. PPU 레지스터
  (`$2115` VMAIN / `$2116-7` VMADD / `$2118-9` VMDATA)를 감시해 주소를 직접 추적해야 함

**다음에 시도할 것**
1. **메뉴가 확실히 열린 상태의 VRAM** 확보가 선행 조건. 자동 덤프는 타이밍을 놓침
   → Mesen `Debug → Memory Tools → Video RAM → File → Export` 로 수동 저장이 확실
2. 그 VRAM 에서 라벨 글리프 위치를 **확정한 뒤** 감시 대상을 정할 것.
   지금까지 실패는 전부 위치를 추정으로 정한 데서 비롯됨
3. 메뉴 화면 스크린샷도 단서가 됨 (무엇이 어떤 크기로 깨지는지)

**우선순위**: **높음** (2026-09-04 상향). 라벨 13개 문제가 아니라 마법·아이템·
장비 이름 전체가 걸려 있다. 이름표를 번역해도 목록 창에서는 보이지 않는다.

**선행 조건은 사람이 해야 한다**: 메뉴가 열린 상태의 VRAM 덤프.
Mesen `Debug -> Memory Tools -> Video RAM -> File -> Export`.
자동 덤프는 타이밍을 놓친다 (기존 실패 기록). 그 덤프에서 라벨 글리프
위치를 확정한 뒤에야 감시 대상을 정할 수 있다.

### 4.2 오프닝 컷신 텍스트를 못 찾음

동생(ホセ)이 형에게 말하는 오프닝 장면. `あにき`는 뱅크 0x04에 14곳뿐이고 그건 후반 재회 장면입니다(근처에 "호세의 시신" 표현). 확정된 텍스트 구간 4곳 어디에도 오프닝이 없습니다. **압축됐거나 별도 시스템**으로 추정 — 4.1과 같은 방법으로 접근하면 같이 풀릴 가능성이 높습니다.

### 4.3 몬스터 이름 구간은 다른 인코딩을 씀 ← 신규

미식별로 남긴 F7 뱅크 상위 약 55개 코드는 대사가 아니라 **가타카나 몬스터 이름** 안에
나타납니다: `グレーターオ<C4C>オ<C9A>ッサーオ` `ヘル<C79>ルベロス` `ドラゴＲ<C44>ナイト`
`Ｈ<C8E>ブ<C47>スラッグ`. 즉 이 구간은 `0xF7`을 뱅크 이스케이프로 쓰지 않습니다.
한자 매처가 실패한 것(IoU 0.39~0.6)도 글리프가 한자가 아니기 때문입니다.

몬스터 이름도 번역 대상이므로 나중에 별도로 풀어야 합니다. 다만 **전면 번역 시 이 슬롯은
어차피 회수 대상**이라 식별 자체는 불필요합니다. 필요한 것은 인코딩 구조입니다.

### 4.5 추출기의 0xFF 스캔이 이스케이프를 모른다 ← 신규 (2026-09-07)

**증상**: 세그먼트 17개가 프리픽스 바이트(`F4`~`F7`)로 끝난다.

**원인**: 원문에 「`Fx FF`」 형태의 글리프 참조가 있다. 예를 들어 `#802` 는
`... f5e7 f6 ff a6 ...` 인데 `f6 ff` 가 글리프 인덱스 767 을 가리키는 정상
참조다. 그런데 추출기의 메시지 경계 판정은 0xFF 를 무조건 종료자로 보므로
그 `ff` 에서 메시지를 쪼갠다. 그래서 앞 조각은 프리픽스로 끝나고, 뒤 조각이
별도 세그먼트가 된다.

게임은 그렇게 읽지 않는다. 렌더러는 `f6` 을 프리픽스로 보고 다음 바이트를
인덱스로 먹으므로 `ff` 를 종료자로 해석하지 않고 뒤 조각까지 이어 읽는다.

**해당 세그먼트 17개**
```
#364 #802 #917 #954 #1198~#1210
```
`#1198~#1210` 은 4바이트짜리 13개가 연속인데, 이 구간은 이름·아이템 관련
데이터일 가능성이 있다 (아직 확인 안 함).

**내가 이것 때문에 만든 회귀**: 「고아 프리픽스 정리」 때 `#364` 말미의
`<F5>` 를 지웠다. 그러자 뒤 `ff` 가 진짜 종료자가 되어 이어지는 `#365`
("예정대로입니다")가 화면에서 사라졌다. 원문 구조를 오류로 보고 지운 것이다.
`<F5>` 를 복구했다.

**대응**: `trcheck` 의 고아 프리픽스 검사에 예외를 넣었다. **원문이 같은
프리픽스로 끝나는 세그먼트에서는 번역문 말미의 프리픽스를 허용한다.**
그러면 정상 구조를 보존하면서도 진짜 고아는 계속 잡는다.

**남은 판단**: 이 17개를 번역하려면 말미 프리픽스를 유지해야 하는데, 그러면
`Fx FF` 글리프(원문 일본어 글자)가 한국어 문장 중간에 하나 남는다. `FF` 는
세그먼트 밖이라 우리가 못 바꾼다. 선택지는 셋이다.
1. 그대로 두기 — 글자 하나가 일본어로 남는다
2. 추출기를 이스케이프 인식으로 고쳐 두 조각을 한 세그먼트로 합치기
   (파이프라인 전체에 영향. 세그먼트 수와 주소가 바뀐다)
3. 프리픽스를 `F4` 로 바꾸고 인덱스 `0xFF`(폰트 255번)에 한글을 배정하기
   — 단어표·이름표는 `0xFF` 를 종료자로 쓰므로 그쪽과 충돌하지 않게
   대사 전용으로만 허용해야 한다

지금은 1번 상태로 두고 해당 세그먼트를 미번역으로 남겼다. `#364` 만 이미
번역돼 있어 원문 구조를 복구해 뒀다.

### 4.6 접미사 공유 이름표는 조립기가 필요하다 ← 신규 (2026-09-08)

몬스터·아이템 이름 엔트리 안에 절대 포인터가 박혀 있다.

  `EE <ptr16>`      ptr 의 0xFF 종료 문자열을 이어 붙인다
  `F0 C4 <ptr16>`   ptr 의 문자열을 넣는다

그리고 접미사를 공유한다. `#1325` 는 `0xf68c` 를 다섯 번 참조하는데 그
접미사는 앞쪽 다른 세그먼트에 있다. 제자리로 번역하면 참조 대상이 그대로
일본어로 남아 섞여 나오고, 거꾸로 참조되는 쪽을 덮으면 그것을 쓰는 다른
이름들이 함께 바뀐다.

**조립기 없이는 손댈 수 없다.** 재배치하면서 (1) 포인터 표, (2) 엔트리 안에
박힌 참조, (3) 공유 접미사의 위치를 함께 다시 계산해야 한다.

`trbatch.todo()` 가 이 세그먼트들을 작업 목록에서 뺀다. 표가 소유한 구간
(마법 이름 18개)도 함께 뺀다 — 그쪽은 `nametbl` 이 정본이다.

**같은 자리를 두 경로가 다투는 문제가 세 번 있었다**
  배치 42  patch_all.MENU 13개가 대사 세그먼트를 잘라 먹었다
  배치 65  이름표를 대사보다 먼저 써서 대사 되쓰기에 덮였다
  배치 79  마법 이름 7개를 대사로도 번역해 종료자가 어긋났다
`trcheck` 의 표 침범 검사와 `trbatch` 의 목록 제외로 두 층에서 막았다.

**보류 목록** (조립기 또는 별도 판단 필요)
| 세그먼트 | 성질 |
|---|---|
| `#1325` `#1326` `#1336` | 접미사 공유. 내부 참조 있음 |
| `#1316` `#1317` | 제어 비율 58~62%. 텍스트가 아니라 데이터로 보인다 |
| `#1198`~`#1210` | 4바이트 13개 연속. `Fx FF` 오분할 계열 (4.5) |

### 4.7 아이템 이름표는 손대지 않는다 ← 판단 (2026-09-08)

구조를 전수 측정한 결과 **문자열이 서로 겹친다.** 접미사 공유가 아니라
문자열 자체가 겹쳐 쌓여 있다.

| 측정 | 값 |
|---|---|
| 포인터 표 `0x040260` | 130엔트리 |
| 고유 문자열 | 95개 |
| **다음 엔트리를 침범하는 문자열** | **11개** |
| 내부 참조 대상 | 17곳 (각 3~7회 참조) |
| 주소 범위 | `0xf1c0 ~ 0xf46f` |

예를 들어 `0xf1de` 의 문자열은 13바이트인데 다음 엔트리(`0xf1e5`)까지
6바이트뿐이다. 즉 `0xf1de` 의 문자열 뒷부분이 곧 `0xf1e5` 엔트리이고,
그 자리를 두 엔트리가 함께 쓴다.

**두 방법 모두 막힌다**
- 제자리 번역: 한 바이트 위치가 여러 엔트리를 동시에 섬기므로 불가능
- 재배치 + 포인터 갱신: 표 130개는 고칠 수 있으나 이 주소 범위를 가리키는
  다른 참조를 전부 찾아야 한다. 범위를 값으로 갖는 16비트 위치가
  **25,246곳**이고 대부분 오탐이다. 원칙 1 의 리포인팅 실패, 그리고 이름표
  재배치로 메뉴가 멈춘 사고(4.5 앞부분)와 같은 상황이다

**성과도 반쯤 막혀 있다**: 4.1 이 미해결이라 아이템 이름은 목록 창에서
보이지 않는다. 확인 창과 대사 삽입에서만 보인다. 이 프로젝트에서 가장
위험한 작업인데 보상이 절반이다.

**결론**: 4.1 을 먼저 풀고, WRAM 폰트 경로를 알게 된 뒤에 다시 판단한다.
그때는 목록 창까지 보이므로 위험을 감수할 이유가 생긴다.

### 4.8 F7 `0x3E-0xDD` 의 정체 = 엔딩 텍스트 ← 해결 (2026-09-08)

오래 「정체 불명 데이터」 로 남아 있던 160슬롯이 무엇인지 확정했다.

**어떻게 찾았나.** 세 번째 렌더러(`0x005650~`)를 디스어셈블하다가
`0x005666` 의 `LDA $EFCFC0,X` 를 읽었다. `$EF:CFC0` = ROM `0x2FCFC0` 이고,
그 주소를 직접 판독하니 일본어 문장이 나왔다 (`0xF1` 줄 구분, `0xFD` 표식).

**확정된 구간**

| | |
|---|---|
| 엔딩 텍스트 | `0x2FCFC0 ~ 0x2FF780` (10,176바이트) |
| 읽는 코드 | `0x005666` `LDA $EFCFC0,X`, `0xFF`/`0xFE`/`0xFD` 판별 |
| 폰트 인덱스 환산 | 831 ~ 989 |

**F7 슬롯 배정이 안전함을 실측했다**

  F7 하위 `0x00-0x3D` -> 인덱스 768~829  = ROM `0x2FC000~0x2FCF80`
  엔딩 텍스트          -> 인덱스 831~989  = ROM `0x2FCFC0~0x2FF780`
  F7 상위 `0xDE-0xFF` -> 인덱스 990~1023 = ROM `0x2FF780~0x300000`

상위 슬롯 구간(2,176바이트)은 **100% `0xFF` 채움**이다. 엔딩 텍스트가
끝나는 바로 그 지점에서 시작한다. 경계가 정확히 맞아 겹침이 없다.

즉 「F7 0x3E-0xDD 는 쓰지 않는다」 는 기존 보수적 판단이 옳았고, 이제
그 이유를 안다. 그리고 상위 34슬롯은 안전이 증명됐다.

**엔딩 텍스트는 남은 번역 대상이다.** 10KB 이고, 스트림을 순차로 읽는
구조여서 제자리 번역이 가능해 보인다. 다만 진입점이 인덱스로 잡히는지
확인해야 길이를 바꿀 수 있는지 판단할 수 있다.

### 4.9 엔딩 본문은 866바이트다 (4.8 정정, 2026-09-08)

4.8 에서 본문을 `BODY`~`0x2FF780` (10,168바이트) 로 적었습니다. 틀렸습니다.
포인터 표는 4개고 각 블록은 첫 `0xFF` 에서 끝납니다.

| 블록 | 오프셋 | 크기 | 내용 |
|---|---|---|---|
| 1 | `0x000`~`0x0b0` | 176B | 팔코에게 남기는 부탁 |
| 2 | `0x0b1`~`0x139` | 136B | 팔코가 팔찌와 세계를 맡는다 |
| 3 | `0x13a`~`0x251` | 279B | 루큐가 세계를 물에 가라앉힌다 |
| 4 | `0x252`~`0x365` | 275B | 루큐가 모든 생명을 없애고 허공에 잠긴다 |

합 866바이트, 가나 포함 52조각. **엔딩은 4종입니다.**

`0x366` 이후 6.6KB 는 엔딩이 아닙니다. 포인터가 4개뿐이라 렌더러가 닿지
않습니다. `ending.TEXT_END = 0x366` 을 두고 `patch_ending.load()` 가 이 밖을
걸러냅니다. 상수는 `ending.text_end(rom)` 이 다시 계산해 검증합니다.

**F7 상위 슬롯은 폰트가 아닙니다.** 4.8 은 F7 `0x3E`~`0xDD` 를 "엔딩 텍스트"로
적었지만, 실제 엔딩은 F7 `0x3F`~`0x4C` (14슬롯) 만 씁니다. 그 뒤 `0x4D`~`0xDD` 는
위의 미식별 데이터가 깔려 있습니다. 글리프로 렌더해 보면(`0x4B` `0x77` `0x85`
`0x8F` 확인) 전부 노이즈입니다. **폰트 여유 슬롯으로 쓸 수 없습니다.**

### 4.10 몬스터 이름표 — 절반만 가능하다 (2026-09-08)

`0x04f672`~`0x04f801`. 아이템표(4.7)와 달리 **문자열이 겹치지 않습니다.**
각 엔트리가 `0xFF` 로 끝나고 다음 엔트리가 바로 이어집니다. 제자리 삽입 가능.

| 분류 | 개수 | 처리 |
|---|---|---|
| 깨끗한 이름 | 19개 | **번역 완료** |
| 접미사 공유 `<EE>` | 10개 | 불가 (4.6 — 어셈블러 필요) |
| `F7` 비글리프 참조 | 5개 | 손대지 않음 (아래) |

접미사 공유 10개 안에 이름이 여럿 들어 있습니다 (`#1354` 하나에 6개). 그래서
번역한 19개는 전체의 대략 절반이고, **몬스터 목록은 한국어와 일본어가 섞인
상태입니다.** 나머지는 4.6 이 풀려야 합니다.

**`F7` 비글리프 참조 5개** (`#1333` `#1334` `#1341` `#1344` `#1350`): `f7 4b`
처럼 F7 상위 슬롯을 가리키는데, 4.9 에서 확인한 대로 그 슬롯은 글리프가
아닙니다. 접미사 공유가 `<EE>` 만 쓰는 게 아니라는 뜻이거나 애초에 이름이
아니라는 뜻입니다. 어느 쪽이든 손대면 안 됩니다.
`trbatch.has_nonglyph_f7()` 이 걸러냅니다.

**아이템표 구간이 필터에 빠져 있었습니다.** 4.7 에서 손대지 않기로 판단한
`0xf1c0`~`0xf46f` 가 `table_owned()` 에 없어서 작업 목록에 장비 이름이 그대로
떴습니다 (`#1223` `#1261` `#1269` `#1315`). 배치 79 와 같은 표침범을 네 번째로
되풀이할 자리였습니다. 구간을 추가했습니다.

부수 효과: `#1222` 「フォーメーション」(`0x04f1b7`, 표 바깥) 은 「진형」으로
번역했지만 같은 낱말인 `#1315` (`0x04f466`, 표 안) 은 일본어로 남습니다.
4.7 이 풀릴 때까지 이 불일치는 남습니다.

**증상**: 메뉴를 열면 게임이 멈춤. §4.5 와 같은 증상이지만 원인은 다르다.

**원인**: `#1095` 「`<EB><15>の頂<EE>に←`」 (이동 목록, `0x04e214`). 예산 4바이트에
맞추려 「`<EB><15>의 정상←`」 으로 줄이면서 **`<EE>` 를 지웠다.**

```
원  fa 01 20 20 20 20 20 eb 15 c9 f5 6c ee c6 e0
패  fa 01 20 20 20 20 20 eb 15 2b 20 bd c6 e0 20   ← ee 없음
```

같은 이동 목록의 다른 네 항목(`#1078` `#1085` `#1087` `#1093`)에는 `<EE>` 를
남겼는데 이것만 빠졌다. 이동 목록은 메뉴 화면이다.

**기존 검사가 못 잡은 이유**

| 검사 | 왜 못 잡는가 |
|---|---|
| `[1]` 바이트 역검증 | 길이만 맞으면 통과한다. 15바이트 그대로였다 |
| 고아 프리픽스 | `F4`~`F7`·`5D`·`D5` 만 본다. `EE` 는 대상이 아니다 |
| 예산 초과 | 오히려 지워서 예산에 들어갔다 |

**고친 것**: 「` 정상`」 + `<EE>` + 「`에`」 = 4바이트. 공백1 + 정1 + 상1 + 에1.
「마왕 정상에←」 로 렌더된다. `의` 를 버렸지만 `#1078` 「자가트 마을에←」 와
같은 방식이다.

**검사 9 를 추가했다** — 제어 코드 개수 보존. `E5`~`FE` 중 `F4`~`F7`(글리프
프리픽스, 한자를 한국어로 바꾸면 같이 사라지는 게 맞다)과 `EB`(단어표 참조,
넣고 빼는 게 번역 선택)를 제외한 전부.

이 검사로 이전 세션의 결함 둘도 찾았다.

- `#57` SAVE 창에 `<E9><15>タ` 가 잘못 끼어 있었다 (원문에 없는 제어 시퀀스)
- `#954` 페이지 넘김 `<E7>` 이 빠져 있었다

**폐기한 가설**: 「`#1222` 「진형」이 메뉴 명령 라벨이고 `f4` 이스케이프를 쓰므로,
이스케이프를 모르는 단순 라벨 루틴이 멈춘다.」 → 같은 라벨 표의 `#1220`
「コンディション」→「컨디션」이 이전 세션에 번역됐고 「컨」은 `F6` 이스케이프인데
메뉴가 동작했다. 라벨 표의 이스케이프는 무해하다.

### 4.12 메뉴 정지 — F4 이스케이프 (2026-09-08)

**이분 탐색으로 좁혔다.** 추측만으로는 두 번 틀렸다.

| 롬 | 담긴 것 | 결과 |
|---|---|---|
| A | 이번 세션 전 상태 | 열림 |
| B | 현재 − 엔딩 쓰기 | 멈춤 |
| C | 현재 − 표·메뉴 구역 32개 | 열림 |
| D | 현재 − 이동목록 7개 | 멈춤 |
| E | 현재 − 이름표 25개 | **열림** |

→ 원인은 `0x04f000` 이상 표 영역 25개 안에 있다.

**원인: `F4` 이스케이프.** `F4` 는 다른 뱅크와 성질이 다르다.

`F4 xx` 는 글리프 `xx` 를 가리킨다. 단일바이트로 쓸 수 있는 글리프는 단일바이트로
쓰므로, `F4` 에는 **바이트 값이 제어 코드와 겹쳐 단일바이트로 못 쓰는 글리프만**
남는다 (`F4_SLOTS = 0x00~0x1F, 0xE6~0xFF`). 즉 **`F4` 의 두 번째 바이트는 항상
제어 코드 값이다.**

`#1222` 「진형」은 `f4 1f f4 ef` 로 들어갔다. 라벨 렌더러가 `F4` 를 모르면 `0x1F` 를
제어 코드로 읽는다.

**원본 표를 전수 확인한 결과가 이를 뒷받침한다.**

| 구역 | 원본에 `F4` | 원본에 `F5`~`F7` |
|---|---|---|
| 라벨 표 | 0개 | 0개 |
| 몬스터 이름 | 0개 | **14개** |
| 화자 이름표 | 0개 | 0개 |
| 아이템표 | 1개 | 1개 |

`F5`~`F7` 은 쓰는데 `F4` 는 안 쓴다. 대사 렌더러는 `F4` 를 처리한다 (원문도
`<F4><魔>` 로 魔 를 쓴다). 메뉴·표 렌더러는 처리하지 않는다.

**고친 방법**: `krcodec.allocate(no_f4=...)`. 메뉴·표 영역(`0x04e000` 이상)과
단어표·이름표에 실리는 음절은 `F4` 를 받지 않는다. 뱅크 이스케이프는 어느
뱅크든 2바이트라 재배치 비용이 0이고, 표 음절이 건너뛴 `F4` 슬롯은 뒤의 대사
전용 음절이 받으므로 총 슬롯 소비도 같다 (`5D`/`D5` 로 넘치지 않는다).

결과: `#1222` = `f5 1d f5 26`. 표·메뉴 세그먼트 173개 중 `F4` 사용 0개.

**틀린 가설 둘을 기록한다**

1. 「`#1095` 에서 `<EE>` 를 지운 것이 원인」 — `<EE>` 제거는 실제 결함이었고
   고친 게 맞지만 정지의 원인은 아니었다. 새 빌드로도 멈췄다.
2. 「라벨 표의 이스케이프가 문제」를 `#1220` 「컨디션」으로 폐기했던 것 —
   폐기가 틀렸다. `#1220` 은 `f6cf c9 f6f1` 로 **F6** 만 쓴다. F4 와 F6 를 같은
   부류로 묶은 것이 오판이었다. 대조군을 볼 때 코드까지 봐야 했다.

### 4.13 F4 슬롯이 원본 글리프를 덮고 있다 ← 미해결

`F4` 슬롯 57개가 **원본 글리프를 전부 덮어쓴다.** 덮이는 글리프에 이런 것들이
있다.

| 글리프 | 내용 | 쓰이는 곳 |
|---|---|---|
| `0x00` | 魔 | 원문 `<F4><魔>` (미번역 세그먼트에 남아 있다) |
| `0x01` | 士 | 같음 |
| `0x02` | 見 | 같음 + 「アルヒ<見>ーヌ」 |
| `0x04` `0x05` | ◀ ▶ | **메뉴 화살표** |
| `0x06`~`0x1F` | ガギグゲゴ… | 미번역 이름의 탁음 가나 |

4.12 의 `no_f4` 는 표 영역만 막았고, `F4` 자체는 대사 전용 음절 57자가 계속 쓴다.
그래서 이 글리프들은 여전히 덮인다. 표시가 틀리는 문제이고 멈추지는 않는다.

**고치려면 `F4` 를 아예 안 써야 하고, 그러면 57칸이 부족하다.**

  단일 142 + F5 255 + F6 255 + F7 95 = 747 < 804

두 길뿐이다.

- `--engine` 을 켜서 `5D`/`D5` 를 쓴다. 다만 `5D`/`D5` 도 메뉴 렌더러가 모르므로
  표 영역에는 `no_5d` 제약이 같이 필요하다
- 고유 음절을 747 이하로 줄인다. 출현 1~2회 음절이 272자라 여지는 있다

**F7 이 95/95 로 꽉 찼다**는 점도 같이 걸린다. 다음에 새 음절이 하나라도 늘면
`5D`/`D5` 가 필요해지고 `--engine` 이 필수가 된다.

### 4.14 F4 를 비웠다 — 엔진 패치 기본 적용 (2026-09-08, 4.13 해결)

`--engine` 을 기본으로 켜고 **F4 를 배정 풀에서 뺐다.**

```
수용량  1314 -> 1257   (F4 57칸 제외)
필요량  약 836자        (여유 421자)
뱅크    단일 142 / F5 255 / F6 255 / F7 95 / 5D 255 / D5 255
롬      3MB -> 4MB
```

**되찾은 글리프 57개** — 전부 원본 유지로 확인했다.

| 글리프 | 내용 |
|---|---|
| `0x00` `0x01` `0x02` `0x1F` | 魔 士 見 入 (원문 `<F4><魔>` 등) |
| `0x04` `0x05` | ◀ ▶ 메뉴 화살표 |
| `0x06`~`0x1F` | ガギグゲゴ… 탁음 가나 |

그 57자는 새 폰트 영역 `0x300000`(뱅크 `$F0`)으로 옮겼다.

**`5D`/`D5` 도 위험 프리픽스다.** 엔진 패치는 이스케이프 판별 두 곳(`$950F`
대사, `$5CFA` 옵션·엔딩)만 고친다. 메뉴·표 렌더러는 모른다. 그래서
`krcodec.RISKY_PREFIX = {0xF4, 0x5D, 0xD5}` 를 두고, 메뉴·표 영역
(`0x04e000` 이상)과 단어표·이름표 음절은 이 프리픽스를 받지 않는다.

**배정 알고리즘을 바꿨다.** 처음엔 위험 슬롯을 만나면 건너뛰고 보류했다가
뒤의 대사 음절에게 주는 방식이었는데, 안전 슬롯이 먼저 소진되면 뒤에 오는
희귀한 표 음절이 빈손이 된다 — 단어표 `[07]` 「에놋」 의 「놋」 이 걸렸다.
지금은 **뒤에 남은 표 음절 수를 미리 세어 안전 슬롯을 그만큼 남겨 둔다.**

**`備`/`ゆ` 노출을 재봤다.** 이 두 바이트가 프리픽스가 되므로 미번역 일본어에
있으면 깨진다 (1.2.2 의 경고). 미번역 603개 중 5개뿐이고 전부 제어 코드 위주의
데이터다 (`#668` `#1316` `#1317` `#1434` `#1502`). 라벨·몬스터·화자 이름표에는
하나도 없다.

**삽입 검사를 손봤다**

- `[3]` 새 폰트 영역 `0x300000`~ 까지 훑는다 (안 하면 804 중 747만 보인다)
- `[5]` 엔진 패치가 고치는 자리를 허용 목록에 넣었다 (`$950F` `$5CFA` `$9548`
  + 새 코드 `$F200` `$F260` `$F300`)
- `[9]` 절대 개수 대신 **원본과의 차이**를 본다. 제어 코드마다 파라미터 길이가
  달라 이스케이프와 구분할 수 없다 — `#1187` 「`<FD>ゆ<F0>`」 의 `ゆ`(0xD5)는
  `FD` 의 파라미터인데 프리픽스로 오인됐다. 원본에 있던 것은 게임이 그대로 돌던
  것이므로 새로 넣은 것만 잡는다

### 4.15 이스케이프 둘째 바이트가 0x20 미만이면 안 된다 (2026-09-08)

4.12 에서 「F4 프리픽스가 문제」로 결론했는데 **절반만 맞았다.** F4 를 빼고
빌드한 롬(4.14)에서 실기 확인하니 메뉴는 열리지만 글자가 여전히 깨졌다
(실기 확인).

**대조군이 원인을 정확히 가리켰다.** 같은 창(아이템 버리기 확인)에서:

| 음절 | 코드 | 둘째 바이트 | 화면 |
|---|---|---|---|
| 괜 | `f5 64` | `0x64` | 정상 |
| 찮 | `f5 58` | `0x58` | 정상 |
| 예 | `f5 1e` | **`0x1E`** | 깨짐 |
| 힐 | `f7 13` | **`0x13`** | 깨짐 |
| 진 | `f4 1f` | **`0x1F`** | 정지 (4.12) |

「아니오」(`71 25 2c`)는 전부 단일바이트라 정상이었다.

**프리픽스가 아니라 둘째 바이트 값이 문제다.** 원본 표도 `F5`~`F7` 을 쓴다
(몬스터 이름 14곳). 메뉴·표 렌더러는 이스케이프를 처리하지만, 둘째 바이트가
`0x20` 미만이면 그것을 제어 코드로 읽는다. `F4` 프리픽스까지 겹치면 멈추고,
`F5`~`F7` 이면 깨져 보인다.

`F4` 가 유독 위험했던 이유가 이제 설명된다. `F4_SLOTS` 는 `0x00~0x1F` +
`0xE6~0xFF` 라 **절반이 저값**이다. 다른 뱅크는 저값이 일부일 뿐이다.

**고친 방법**: `krcodec.menu_safe(slot)`.

```
단일바이트                       안전
F5/F6/F7 + 둘째 바이트 >= 0x20   안전
F4 / 5D / D5                     위험 (프리픽스를 모르는 렌더러가 있다)
둘째 바이트 < 0x20               위험
```

안전 슬롯 651칸 (단일 142 + F5 223 + F6 223 + F7 63), 메뉴·표 고유 음절 359자.
평균 바이트는 그대로다 (1.21).

결과: 힐 `f713` -> `f7e3`, 예 `f51e` -> `f53e`, 진 `f51f` -> `f53f`,
컨 `f709` -> `f7e0`.

**남은 것**: `problem_013`(아이템 목록 창이 빈 채로 뜸)과 `problem_014`(우측
패널 깨짐)는 이 수정과 별개일 수 있다. 4.1(메뉴 폰트가 ROM->WRAM->VRAM 으로
따로 올라간다)이 미해결이라, 그 경로로 그려지는 창은 이 수정으로 낫지 않는다.

### 4.15.1 제약의 범위가 틀렸다 — 설명문을 빼먹었다

4.15 의 규칙(`menu_safe`)은 맞았지만 **어디에 적용할지를 틀렸다.** 메뉴는
열리는데 힐을 **선택하는 순간** 멈췄다.

선택하면 설명문이 뜬다. 그런데 제약 대상에 설명문이 없었다.

```
힐 설명문 0x05b5d8 「ＨＰ를 회복\n언데드를 소멸시킨다」
  f6 03   f5 1c   f6 09     <- 둘째 바이트가 전부 0x20 미만
```

설명문 20개 중 11개가 위험했다. `5D` 프리픽스를 쓰는 것도 8개 있었다.

**주소로 가른 것이 근본 실수였다.** `0x04e000` 이상을 메뉴로 봤는데, 시스템
메시지는 대사 뱅크 **앞쪽**에 몰려 있다.

| 세그먼트 | 주소 | 내용 |
|---|---|---|
| `#1` | `0x040c01` | 「괜찮습니까？」 |
| `#4` | `0x040c5b` | 「장비 못 합니다！」 |
| `#8` | `0x040c98` | 「못 버린다！！」 |
| `#145` | `0x04193a` | 「〜을 버려도 괜찮습니까？」 |

**기준을 뒤집었다. 이야기 대사가 아니면 메뉴로 본다.**

이야기 대사는 이름표(`<FB>`)·초상화(`<F2>`)를 달거나 `「` 로 시작하고, 패치된
대사 렌더러(`$950F`)가 그린다. 그 밖은 전부 시스템·UI·표다.

```
이야기 대사 780개 / 그 밖 286개
합집합 고유 음절 494자 / 메뉴 안전 슬롯 651칸 (여유 157칸)
```

삽입 검사 `[9]` 도 같은 기준으로 넓혔다 — 설명문과 단어표를 대상에 넣었다.
검사가 대사 세그먼트만 보고 있었던 것이 이번 정지를 놓친 직접 원인이다.

**세 번 고친 셈이다.** 규칙은 4.12(프리픽스) → 4.15(둘째 바이트)로 두 번
정확해졌고, 범위는 4.15.1 에서 한 번 넓어졌다. 반복된 실패는 규칙이 아니라
**범위**였다. 배정 제약과 검사 대상이 같은 기준을 쓰지 않으면 또 새는 곳이 생긴다.

### 4.15.2 선택 항목은 단일바이트만 — 창이 아니라 필드가 다르다

설명문과 「HP 최대」는 정상이 됐는데 확인 창의 「예」가 여전히 깨졌다
(`image/problem_015.png`).

**같은 세그먼트 안에서 갈렸다.** `#1` (`0x040c01`):

```
원  fa02 d6dbbcb2c301bdb63f  f1f1 fe1c f906 ed24 cab2 20 ed20 ...
패  fa02 f584f5782d25933f     f1f1 fe1c f906 ed24 f53e 20 ed20 ...
         ^^^^^^^^ 괜찮습니까 = 이스케이프 → 정상          ^^^^ 예 = 이스케이프 → 깨짐
```

「괜찮습니까？」 는 `f5 84` `f5 78` 을 쓰는데 정상이고, 「예」 는 `f5 3e` 인데
깨진다. **창이 아니라 필드가 다르다.**

`<ED>出` … `<ED> ` 로 감싼 **선택 항목 필드는 바이트 하나를 타일 하나로 그린다.**
이스케이프를 넣으면 두 글리프로 갈라진다.

**고친 것** — 전수로 세 곳뿐이었다.

| 세그먼트 | 전 | 후 |
|---|---|---|
| `#1` `#1052` | 「예」 `f5 3e` | 「**네**」 `0x9a` |
| `#139` | 「되돌림」 (림 = `f5 c9`) | 「**되돌리기**」 (전부 단일바이트) |

`검사 10` 을 추가했다 — 선택 항목에 이스케이프가 있으면 잡는다.

**앞머리 글리프 두 개는 우리 것이 아니다.** `#145` 첫 8바이트
(`fa 01 ed 3c fe 26 ed 20` = `<FA><士><ED>者<FE>手<ED>공백`)는 원본과 **완전히
동일하다.** 이미지에서 그 글리프들의 색이 본문과 다른 것도 아이템 아이콘일
가능성을 뒷받침한다. 원본 롬과 비교해 확인이 필요하다.

### 4.15.3 선택 필드는 칸 수가 고정이다 — ASCII 탐침이 확정했다

「예」를 「네」로 바꿔도 그대로였다. 짐작을 멈추고 **ASCII 탐침 롬**을 만들었다.
선택 항목을 `ＹＥＳ`/`ＮＯ`, 마법 이름을 `ＨＬ` 로 넣었다. ASCII(`0x41`~`0x5A`)는
`KEEP` 이라 원본 글리프를 그대로 쓰므로 반드시 올바르게 그려진다.

**두 화면이 답을 줬다** (탐침 화면과 원본 화면).

| 화면 | 선택 줄 |
|---|---|
| 원본 | `はい  ◀ ▶  いいえ` |
| 탐침 | `ES ◀ ▶ [깨짐][깨짐]NO` |

`ＹＥＳ`(3칸)의 `Ｙ` 가 왼쪽으로 잘려 나갔고, `ＮＯ`(2칸) 앞에 이전 타일이
남았다. **필드는 칸 수가 고정이다.** 원문보다 많으면 밀려 잘리고, 적으면 남은
칸에 이전 타일이 남는다.

| 원문 | 칸 | 우리(전) | 칸 | 우리(후) | 칸 |
|---|---|---|---|---|---|
| `はい ` | 3 | 「네 」 | 1 | 「네  」 | 3 |
| `いいえ` | 3 | 「아니오」 | 3 | 그대로 | 3 |
| `もどす` | 3 | 「되돌리기」 | 4 | 「돌리기」 | 3 |
| `やめる` | 3 | 「그만」 | 2 | 「그만 」 | 3 |

**칸은 바이트가 아니다.** 원문 `もどす` = `d3 c401 bd` 로 **4바이트 3칸**이다.
`c4 01` 은 탁점 결합 부호라 2바이트 1칸이다. 반면 우리 이스케이프(`f5 xx`)는
1칸으로 묶이지 않고 **2칸으로 갈라진다.** 그래서 선택 필드는 단일바이트만 쓰고
칸 수를 원문과 맞춘다.

**앞머리 글리프 두 개는 아이템 아이콘이다.** 원본 화면에도 있다. 확정.

`검사 10` 을 칸 수 비교로 확장했다. 되돌려 넣어 시험하니 「`#1`: 칸 3 -> 2」 로
정확히 잡는다.

### 4.15.4 선택 항목은 「ＯＫ / 아니오」 로 확정

원본과 **바이트 모양이 같아야** 한다.

| | 원본 | 우리 |
|---|---|---|
| 항목1 | `ca b2 20` = 글리프2 + 공백1 | `4f 4b 20` = 「ＯＫ 」 |
| 항목2 | `b2 b2 b4` = 글리프3 | `71 25 2c` = 「아니오」 |

**「예」·「네」 는 쓸 수 없다.** 항목1 은 글리프 2칸을 채워야 하는데 「예」 는
이스케이프(2칸으로 갈라짐)이고 「네」 는 한 글자라 칸이 남는다. 단일바이트
음절 두 개로 만들 수 있는 긍정 표현은 「그래」 뿐인데 존댓말 물음과 말투가
어긋난다. `ＯＫ`(`0x4f` `0x4b`)는 `KEEP` 이라 원본 알파벳 글리프를 그대로 쓰고
말투도 중립이다.

**이 창 하나에 다섯 번 손댔다.** 효과가 있었던 것은 두 가지뿐이다.

- **원본 화면과 직접 비교** — 앞머리 글리프 두 개가 아이템 아이콘임을 확정
- **ASCII 탐침** — `ＹＥＳ`/`ＮＯ` 로 필드가 칸 수 고정임을 확정,
  「리마네」로 `0x80` 경계 가설을 폐기하고 항목1 이 2칸임을 확정

화면을 보고 짐작해 빌드를 반복한 네 번은 전부 헛수고였다. **원본 글리프를 넣어
대조하는 것이 가장 빠르다.**

### 4.16.1 이름표는 강제 배정으로 풀 수 없다 ← 판단 필요

파티 상태창의 인물 이름과 마법 목록의 마법 이름도 같은 문제다. 이름은 표에서
오는데 그 음절이 이스케이프면 두 글리프로 갈라진다.

**강제 배정 비용을 전수 측정했다.**

| 강제 대상 | 대사 예산 초과 | 단일바이트 커버리지 | 평균 |
|---|---|---|---|
| 없음 (현재) | **0개** | 79% | 1.21 |
| 인물 이름 12개 | **20개** | 78% | 1.22 |
| 마법 이름 18개 | 86개 | 76% | 1.24 |
| 단어표 56개 전부 | 136개 | 74% | 1.26 |
| 인물 + 마법 전부 | **433개** | 60% | 1.40 |

단일바이트 칸이 142개뿐이라, 이름 음절을 넣을수록 고빈도 음절이 밀려 대사가
무너진다. 이름 음절 다수가 음역 때문에 희귀하다 (놋1 렝1 멜1 즌1 톰1 페1 펠1
퓨1 닝2 블2 윈2 힐2). **출현 1회짜리를 단일바이트에 태우고 출현 31회짜리를
밀어내는 거래다.**

한자어로 바꿔 흔한 음절을 재사용하는 길도 반쯤 막혀 있다. 단일바이트 142자에
불·화·염·빙·뇌 계열 음절이 없어서 ファイアボール·アイスストーム·ライトニング
같은 이름을 옮길 수 없다.

**선택지** (마제스티의 판단이 필요하다)

1. 인물 이름 12개만 강제 — 파티 상태창이 한국어가 된다. 대사 20곳 다듬기
2. 마법 이름을 일본어로 되돌린다 — 목록이 원본 그대로 정확히 나온다. 비용 0
3. 인물 + 마법 전부 강제 — 433곳 다듬기. 사실상 불가능

### 4.17 오프닝·세이브 선택 화면 — 텍스트로 존재하지 않는다 (2026-09-08)

마제스티 요청으로 두 화면을 조사했다. **둘 다 롬에 평문 텍스트로 없다.**

**롬 전체(3MB)를 문자열 검색했다.** 게임 tbl 로 인코딩해 찾은 결과:

| 후보 | 결과 |
|---|---|
| `つづきから` `はじめから` `ぼうけん` `きろく` `データ` `セーブ` `ロード` `つづける` `おわる` `えらんで` `ください` `だれもいません` | **0곳** |
| `ホセ` | 40곳 — 그중 알려진 구간 밖은 `0x10dfe` 하나뿐이고, `ギがゴ` 가 반복되는 구조화된 데이터표의 우연이었다 |
| `スタート` | 1곳 (`0x4a1eb`) — `マスタードラゴン` 의 일부, 일반 대사다 |
| `やみ` | 22곳 — `0x38c9` 등은 65816 코드다 |

**가나 밀도 스캔은 무용하다.** tbl 256칸 중 162칸이 가나로 해독되므로 임의
데이터도 63%가 걸린다. 임계값 55%로 스캔하니 3,332개 구역이 나왔고 전부 오탐이었다.
**이 방법은 다시 쓰지 말 것.**

**§4.9 의 "미식별 6.6KB"(`0x2FD32E`~`0x2FF780`)도 텍스트가 아니다.**

| 측정 | 값 |
|---|---|
| 고유 바이트 값 | 250개 |
| `0x20` 미만 | 4,506개 (**48%**) |
| 최빈 | `0x02`×1389 `0x00`×1377 `0x01`×1047 |
| `0xFF` 종료 레코드 | 222개 (길이 중앙값 6, 최대 3349) |
| 짝수/홀수 정렬로 타일맵 속성 비율 | 68% / 66% (정렬 선호 없음) |

`0x82` `0x83` `0xc2` `0xc3` 같은 값이 보여 SNES 타일맵을 의심했으나, 정렬 선호가
없어 단순 비압축 타일맵은 아니다. **압축 데이터이거나 별도 레코드 형식**으로 본다.

**결론**: 오프닝과 세이브 선택 화면은 4.1(메뉴 폰트가 ROM→WRAM→VRAM)과 같은
계열이다. 텍스트를 찾아 바꾸는 방식으로는 접근할 수 없다.

**다시 시도할 때의 전제** (4.1 이 6회 실패한 원인과 같다 — VRAM 을 먼저 확정하지
않고 감시 지점을 추정으로 정했다)

1. 해당 화면의 **VRAM 을 손으로 저장** (Debug → Memory Tools → Video RAM → File → Export)
2. 그 VRAM 에서 글자 타일의 **정확한 바이트 범위를 특정**
3. 화면 캡처로 **원문 문자열을 확정** (검색 대상을 알아야 한다)
4. 그 다음에야 감시·브레이크포인트

특히 3번이 이번에 막힌 지점이다. 무엇이 쓰여 있는지 몰라 검색어를 짐작으로 만들었다.

### 4.17.1 세이브 선택 화면 — 별도 폰트를 쓴다 (확정)

마제스티가 화면 캡처를 줘서 원문이 확정됐다. 「新規」「削除」「設定」과
「セーブエリアを選んでください」.

**문자열 검색: 전부 0곳**

| 검색 | 인코딩 | 결과 |
|---|---|---|
| `セーブ` | `7e b0 1c` | 0곳 |
| `セーブエリア` | `7e b0 1c 74 98 71` | 0곳 |
| `を選んでください` | `a6 f624 dd f3 b8 f0 bb b2` | 0곳 |
| `選` 단독 | `f6 24` | 11곳 (전부 대사) |

**한자 네 자가 대사 폰트에 없다.** 이것이 결정적이다.

| 글자 | 대사 폰트 | 확인 |
|---|---|---|
| 新 | `F6 B4` | 있음 (비트맵 확인) |
| 定 | `F6 00` | 있음 |
| 規 | **없음** | 최고 후보 `F7 DE` (0.676) 를 렌더하니 **검은 채움 타일** |
| 削 | **없음** | 최고 0.567 — `F5 03` 은 創 이다 |
| 除 | **없음** | 최고 0.589 — `F6 E6` 은 忄 부수 다른 글자 |
| 設 | **없음** | 최고 0.478 — `F6 68` 은 最 이다 |

F5/F6 의 미식별 슬롯은 9칸뿐이고 F7 유효 구간까지 합쳐 49칸을 전수 매칭했다.
어디에도 없다.

**결론**: 이 화면은 대사와 다른 문자 집합·다른 폰트를 쓴다. 4.1(메뉴 폰트가
ROM→WRAM→VRAM)과 같은 뿌리다. 텍스트 검색으로는 절대 못 찾는다.

**다음에 필요한 것은 VRAM 덤프 하나다.** 그것으로 할 수 있는 일:

1. VRAM 에서 新·規·セ·ブ 의 **실제 비트맵을 뽑는다**
2. 그 비트맵을 롬에서 검색한다 → 폰트 위치 확정, 또는 압축 확정
3. VRAM 타일 번호로 타일맵을 찾고 거기서 텍스트 스트림을 역추적한다

4.1 이 6회 실패한 이유가 이 순서를 뒤집었기 때문이다. 이번에는 캡처(원문 확정)를
먼저 얻었고, VRAM 이 두 번째다.

### 4.17.2 메뉴 폰트를 찾았다 — 뱅크 0x16, LZ 압축 (2026-09-08)

VRAM 덤프로 **§4.1 이 6회 실패한 지점을 통과했다.**

**1. 형식이 다르다.** 대사 폰트는 2bpp(플레인 동일)인데 메뉴 폰트는 **4bpp** 다.
플레인 네 개가 서로 다르다 — 음영이 들어간 폰트다.

```
대사 폰트 0x2F0000  01017f7f66667f7f6f6f7f7f77776f6f...   플레인0 == 플레인1
메뉴 폰트 VRAM      00001810191019016f287d119901181000001900...  네 플레인이 다름
```

**2. VRAM 배치를 확정했다.** 16×16 글자 = 2×2 타일, **`n, n+1 / n+16, n+17`**
(16타일 폭 시트). 배치 후보 네 개를 템플릿 매칭으로 비교해 갈랐다.

| 배치 | 최고 유사도 3개 | 規 |
|---|---|---|
| `TL,TR,BL,BR` | 0.700 0.671 0.652 | 0.70 |
| `TL,BL,TR,BR` | 0.658 0.649 0.636 | 0.64 |
| **`행16`** | **0.849 0.771 0.746** | **0.85** |
| `열2` | 0.714 0.696 0.657 | 0.66 |

`規` = VRAM 타일 586 (`0x4940`), 유사도 0.849, 비트맵 육안 확인(夫+見).

**3. 롬에 비압축으로 없다.** 3MB 전체를 세 형태로 검색해 전부 0곳이다.

| 검색 형태 | 결과 |
|---|---|
| 4bpp 타일 32바이트 | 0곳 |
| 플레인 0/1 16바이트 | 0곳 |
| 플레인 OR 8바이트 (1bpp) | 0곳 |

**4. 그런데 플레인 8바이트는 있다.** 이것이 결정적이다.

| 대상 | 롬 위치 | 간격 |
|---|---|---|
| 타일 586 p0 | `0x16aaf2` | — |
| 타일 586 p2 | `0x16ab01` | +15 |
| 타일 587 p0 | `0x16ab0f` | +29 |
| 타일 602 p0 | `0x16ac79` | — |

`0x16aaf1` 이 `0xff` 이고 그 다음 8바이트가 정확히 p0 다. 간격이 16·32 에서
한 바이트씩 어긋나고 사이에 `9e` `10` 같은 값이 낀다.

**제어 바이트 + 리터럴 8개**, 그리고 비트가 0 인 자리는 역참조 —
**비트 플래그 LZ 압축**의 전형이다.

```
0x16aaf0  83 ff 00 18 19 19 6f 7d 99 18 10 9e 00 01 28 11
              ^^ 제어(전부 리터럴)  ^^^^^^^^^^^^^^^^^^^^^^^ = 타일586 p0
```

**결론: 메뉴 폰트는 뱅크 `0x16`(`0x16AAF0` 부근)에 LZ 압축돼 있다.**

### 4.17.3 다음은 압축 해제 루틴이다 ← 에뮬레이터 필요

압축 스트림의 **시작점**을 정적으로는 못 찾았다. 24비트 포인터 검색은 오탐만
41개 나왔다 (768바이트 구간에 3바이트 패턴이면 우연히 그만큼 걸린다).

**필요한 것: VRAM 쓰기 브레이크포인트.**

```
Mesen → Debug → Debugger → Breakpoints → Add
  Type: Write     Memory: Video RAM (VRAM)
  Address: 0x4940   (規 가 올라가는 자리)
```

세이브 선택 화면으로 들어갈 때 걸린다. 그 지점의 PC 와 호출 스택에서

1. DMA 루틴 → 소스 주소(압축 해제 버퍼 또는 롬 직접)
2. 거기서 거슬러 올라가 **압축 해제 루틴**
3. 알고리즘을 읽어 해제·재압축 구현

4.1 의 실패 원인이 이 순서를 건너뛴 것이었다. 이번에는 1·2단계(원문 확정, VRAM
확보)를 끝냈으므로 3단계가 처음으로 가능해졌다.

**주의: 이건 텍스트 작업이 아니라 폰트·그래픽 작업이다.** 압축을 풀어도
(a) 4bpp 한글 글리프를 그려 넣고 (b) 재압축하거나 비압축 자리를 찾고
(c) 글리프 번호를 참조하는 텍스트·타일맵을 찾아 바꿔야 한다. 규모가 크다.

### 4.17.4 시험 벡터 확보 — 압축 형식 검증용 (2026-09-08)

압축 해제 결과의 **바이트 배치를 확정했다**: 타일당 **평면 나열**
`p0[8] p1[8] p2[8] p3[8]` = 32바이트. VRAM 은 이것을 인터리브해서 담는다.

**타일 589 시험 벡터** — 어떤 압축 해제 후보든 이걸 통과해야 한다.

```
입력  ROM 0x16ab43 부터
      00 7d 8f 02 c6 e2 70 f8 25 79 28 70 78 38 07
      00 bb 7f fe 7a 7e be 7f 00 44 f0 78 bc 9c 7e 87

출력  32바이트
      00 7d 8f 02 c6 e2 70 f8   p0 (리터럴 그대로)
      00 28 70 78 38 1c 0e 07   p1 (7바이트로 압축)
      00 bb 7f fe 7a 7e be 7f   p2 (리터럴 그대로)
      00 44 f0 78 bc 9c 7e 87   p3 (리터럴 그대로)
```

**압축률이 매우 낮다.** 타일당 21~32바이트로 원본 32바이트와 큰 차이가 없다.
`p1` 구간에서 `00` 과 `1c 0e` 만 역참조로 대체됐고 `25 79` 두 바이트가 그 자리를
채운다. `1c 0e` 는 그 시점까지의 출력에 없으므로 **창(window)이 이전 타일들까지
걸친다**.

**타일 위치 (플레인 8바이트를 롬에서 찾은 것)**

| 타일 | p0 | p2 | p3 | p0→p2 |
|---|---|---|---|---|
| 582 | `0x16aa98` | `0x16aaa5` | `0x16aaad` | +13 |
| 586 | `0x16aaf2` | `0x16ab01` | — | +15 |
| 589 | `0x16ab43` | `0x16ab52` | `0x16ab5a` | +15 |
| 591 | `0x16ab82` | `0x16ab91` | `0x16ab99` | +15 |
| 598 | `0x16ac19` | `0x16ac25` | `0x16ac2d` | +12 |

`p2 → p3` 가 항상 정확히 `+8` 이다. 즉 16바이트가 제어 바이트 없이 연속 리터럴이므로
**"8항목마다 제어 바이트" 방식이 아니다.** "개수 바이트 + N 리터럴" 계열이다.

**시도했으나 실패한 것**: 비트 플래그 LZSS 8변종(비트 순서 2 × 오프셋 인코딩 4)을
`0x16a000`~`0x16ab00` 전 시작점에 대해 돌렸다. 정답 플레인 212조각 중 최대 9개만
재현했다. 리터럴은 형식이 틀려도 통과하므로 9개는 우연이다. **이 8변종은 아니다.**

**브레이크포인트가 안 걸린 이유**: 폰트가 세이브 화면 진입 시가 아니라 부팅·타이틀에서
이미 올라간다. VRAM `0x4940`~`0x5fff` Write 로 잡아도 안 걸린다. 압축 해제 루틴을
잡으려면 **브레이크포인트를 켠 상태로 Power Cycle** 해야 한다.

### 4.17.5 메뉴 폰트 코덱을 해독했다 — 3/4 검증 완료 (2026-09-08)

디스어셈블리($C03300~$C034CD)를 읽어 코덱을 `darkhalf-kr/gfx.py` 에 구현했다.

**구조**

| 주소 | 역할 |
|---|---|
| `0x100000` (`$D00000`) | 압축 블록 인덱스. 4바이트/엔트리, 41개, `0x1000a4`~`0x1d5c74` |
| 엔트리 → 서브 표 | **16비트** 오프셋 목록. `0xFFFF` = 데이터 없음 |
| `$2C` | **비트 스트림**. `$34CF` 가 1비트씩 꺼낸다 (`$4E` 가 8회 세고 리필) |
| `$28` | **데이터 스트림**. `$28 = $2C + [$2C-1]` |
| `$7E273B` | 출력 버퍼 `0x400`바이트. **VRAM 인터리브 형태로 바로 만든다** |

세이브 화면 폰트 = 엔트리 `[22]`(`0x169a53`)의 9번째 오프셋 `0x0FC2` →
**`0x16aa16`, 크기 785바이트** (다음 오프셋 `0x12D3` 까지).

**명령** — 한 바이트가 핸들러 4회를 담당하고 각자 상위 2비트를 먹는다
(`$53`, `$53+1`, `$53+0x10`, `$53+0x11`).

| 비트 | 주소 | 동작 |
|---|---|---|
| `0,1` | `$C033EE` | 8바이트를 `0x00`/`0xFF` 로 채움 |
| `0,0` | `$C033A1` | **니블 역인터리브** 4회 (16바이트) |
| `1,1` | `$C0346A` | 8바이트 리터럴, 또는 마스크+채움 |
| `1,0` | `$C03414` | 이전 출력에서 8바이트 복사 |

**니블 역인터리브가 이 코덱의 핵심이다.** 원본은 두 플레인의 니블을 한 바이트에
붙여 담고, 하드웨어 곱셈기(`WRMPYA=0x10`)로 `<<4`/`>>4` 해서 갈라 놓는다.

```
out[X]   = (L1 & 0xF0) | (L2 & 0x0F)
out[X+2] = (L1 << 4)   | (L2 >> 4)
```

**채움 극성을 처음에 거꾸로 넣었다.** `LDA #$00 / SBC #$00` 은 캐리가 1이면
`0x00`, 0이면 `0xFF` 다. 고치자 일치율이 23%에서 첫 16바이트 완전 일치로 뛰었다.

**검증**: VRAM `0x4800` 과 대조해 네 핸들러 중 셋이 바이트 단위로 정확히 맞는다.

```
X=0x00  니블   0026340e06070300  일치
X=0x01  채움   0000000000000000  일치
X=0x10  니블   001a3c0602050101  일치
X=0x11  역참조                   불일치
```

**남은 문제 둘**

1. **역참조 원본이 이전 블록의 잔존 데이터다.** `$C03321` 은 서브 오프셋이
   `0xFFFF` 일 때만 버퍼를 지운다. 블록을 순서대로 이어 풀어야 한다.
2. **원본 인덱스 계산이 미확정.** `TAY / AND #$03 / XBA / TYA / AND #$FC /
   ASL / ROL / TAY` 는 8비트 A 와 16비트 Y 가 섞여 정적으로 확정이 어렵다.
   소비 바이트 수도 1이 아닐 수 있다 (역참조 이후 스트림이 어긋난다).

**다음 단계**: 엔트리 [22]의 서브 블록을 첫 번째부터 순서대로 풀어 버퍼를
이어 가며 VRAM 과 맞춰 본다. 그러면 역참조 원본이 채워지고 인덱스 계산도
정답에서 역산할 수 있다.

### 4.17.6 메뉴 폰트 코덱 완전 해독 — 1024/1024 검증 (2026-09-08) ← 4.1 돌파

**실기 VRAM 과 1024바이트 전부 일치한다.** `darkhalf-kr/gfx.py`.

```
블록 0x16aa16 (785바이트) -> 1024바이트 -> VRAM 0x4800 (타일 576~607)
검증: 1024/1024 (100%)
```

교차 검증도 맞는다. `規` 가 블록 타일 10 이고 블록이 VRAM 타일 576 에 올라가므로
576+10 = **586** — VRAM 덤프에서 템플릿 매칭으로 찾은 위치와 같다 (4.17.2).

**마지막 조각은 「복사 + 부분 덮어쓰기」였다.**

`$C03452` 의 `PLY` 가 단서였다. `(1,0)` 핸들러는 8바이트를 복사한 **뒤**
`$C03455` 의 마스크 루프로 떨어져 일부를 리터럴로 덮어쓴다.

| 해석 | 일치율 |
|---|---|
| 복사만 (덮어쓰기 없음) | 12% |
| 마스크+채움 (복사 없음) | 84% |
| **복사 + 부분 덮어쓰기** | **100%** |

**원본 인덱스는 어셈블리를 그대로 옮겨야 맞는다.**

```
v  = b & 0xFC
a1 = (v << 1) & 0xFF   c1 = v >> 7        ; ASL
a2 = ((a1 << 1) | c1) & 0xFF   c2 = a1>>7 ; ROL  <- 최상위가 최하위로 돌아온다
Y  = ((b & 3) << 8) | a2                  ; XBA 로 상위가 b & 3
덮어쓰기는 c2 == 0 일 때만                 ; BCS $C03469
```

`b*4` 처럼 '그럴듯한' 공식은 **89%에서 멈춘다.** `ASL`/`ROL` 이 8비트 A 에 걸려
비트가 돌아 들어오는 것과, 상위 바이트가 `b>>6` 이 아니라 `b&3` 인 것이 핵심이다.

**글자 위치를 찾았다.** 엔트리 [22] 는 서브 블록 51개다.

| 글자 | 블록 | 타일 | 유사도 |
|---|---|---|---|
| 規 | `0x16aa16` | 10 | 0.849 |
| 選 | `0x16b71f` | 0 | 0.746 |
| 設 | `0x16b9dc` | 10 | 0.730 |
| 除 | `0x16ad27` | 2 | 0.728 |
| エ | `0x16b25b` | 5 | 0.771 |
| 定 | `0x16b9dc` | 12 | 0.660 |
| 新 | `0x16a6d5` | 10 | 0.647 |
| 削 | `0x16ad27` | 0 | 0.637 |

**이것으로 4.1 의 폰트 쪽은 뚫렸다.** 남은 것은 삽입이다.

1. 한글 **4bpp** 글리프를 그린다 (지금 한글 폰트는 2bpp 다)
2. 코덱으로 **재인코딩** — 리터럴 8개 명령만 써도 되므로 인코더는 단순하다.
   다만 크기가 늘면 블록을 옮겨야 하고 서브 오프셋 표를 고쳐야 한다
3. 글리프 번호를 참조하는 **텍스트·타일맵**을 찾는다 (아직 미착수)

3번이 다음 관문이다. 폰트를 바꿔도 어떤 글리프를 어디에 그리라고 지시하는
데이터를 찾지 못하면 화면은 그대로다.

### 4.17.7 삽입 경로가 열렸다 — 타일맵을 건드릴 필요가 없다 (2026-09-08)

**타일맵은 「타일 `0x260` 부터 연속으로 그려라」 형태다.**

VRAM `0x7000` 대가 타일맵이고 항목이 `0260 0261 0262 0263 …` 처럼 연속 증가한다.
그 구간의 타일을 이어 붙여 렌더하면 **읽힌다** — 왼쪽 16px 이 `削`(肖+刂),
다음 16px 이 `除`(阝+余) 다.

즉 **폰트 시트에 글자가 화면에 필요한 순서대로 나열**돼 있다. 화면마다 필요한
글자만 모아 시트를 만들고, 타일맵은 그 시트를 통째로 붙인다.

**그래서 글리프 비트맵만 바꾸면 화면이 바뀐다.** 타일맵도, 텍스트도, 글리프
번호도 건드릴 필요가 없다. 글자 수만 유지하면 된다.

이것이 4.17 에서 「텍스트를 못 찾는다」 던 이유다. 텍스트가 없다. 그림이다.

**막다른 길로 확인된 것들** (다시 걷지 말 것)

| 시도 | 결과 |
|---|---|
| 타일맵에서 `新規` 인덱스(554,555,586,587) 검색 | ROM 0곳 |
| 해제한 2,354개 블록에서 같은 검색 | 0곳 |
| 글리프 인덱스 추정(新=61 規=69 …) 로 코드열 검색 | 0곳 |

**인코더도 만들었다.** `gfx.pack()` / `gfx.block()`.

명령 셋 중 셋을 쓴다 (복사는 안 쓴다 — 인코더를 복잡하게 만들고 조용히 깨진다).
열마다 가장 싼 것을 고른다.

| 명령 | 비용 |
|---|---|
| 채움 | 0바이트 + 1비트 |
| 마스크 + 채움(비트) | 1 + 비채움 개수, 3비트 |
| 마스크 + 채움(리터럴) | 2 + 비채움 개수, 2비트 |
| 니블 역인터리브 + 마스크 | 1 + 비채움 개수, 1비트 |
| 리터럴 8개 | 8바이트 + 1비트 |

니블 역산에서 `L2` 의 니블을 바꿔 넣어 51개 블록이 전부 깨졌다. 맞는 식은

    L1 = (a & 0xF0) | (b >> 4)
    L2 = ((b & 0x0F) << 4) | (a & 0x0F)

**검증: 전 블록 2,354개 왕복 일치, 실패 0개.**

**크기 문제도 해결됐다.**

| | 크기 |
|---|---|
| 원본 블록 `0x16aa16` | 785B |
| 재인코딩 (그대로) | 827B (+42) |
| 재인코딩 (`規` 자리를 비움) | **716B (-69)** |

뱅크 `0x16` 에는 64바이트 이상 빈 구간이 **0개**라 제자리가 필수인데, 한글은
한자보다 획이 적어 재인코딩이 원본보다 작아진다. **이전이 필요 없다.**

**남은 것은 하나다** — 16×16 **4bpp** 한글 글리프를 그린다. 대사 폰트는 2bpp
(플레인 동일)라 그대로 쓸 수 없고, 원본 메뉴 폰트의 음영을 흉내내야 한다.

### 4.17.8 첫 한글 글리프 삽입 — 제자리 성공 (2026-09-08)

`menufont.py` + `patch_menu.py`. 세이브 선택 화면의 `規` 를 「규」로 바꿨다.

```
블록 0x16aa16  타일 10  規 -> 「규」
재인코딩 749 / 칸 786바이트  (37바이트 여유)
바뀐 바이트 739개, 전부 0x16aa15~0x16ad01 (블록 자기 칸)
```

**색 번호는 역할만 맞춘다.** 원본 `規` 의 분포는 `0:101 5:72 9:32 7:27 4:12 13:12`
로 **5 가 본체**다. 실제 팔레트 색은 화면마다 다르고(CGRAM 은 다른 화면 것뿐)
한글은 획이 단순하므로 본체 색 5 단색으로 칠한다.

**`blocks()` 가 서브 오프셋 개수를 몰라 쓰레기를 읽고 있었다.** 64개를 무조건
읽으니 블록 데이터가 오프셋으로 오해돼 엉뚱한 주소가 섞였고, 칸 계산이 786 대신
523 으로 나와 제자리 삽입이 막혔다. **첫 오프셋이 목록 길이다** (`0x40` -> 32개).

**남은 것**

1. 실기 확인 — 「新규」로 보이면 경로가 증명된다
2. 나머지 글리프 위치 확정 (`新` `削` `除` `設` `定`, 그리고 아래 문장 14자)
   현재 확정된 것은 `規` 뿐이다. 템플릿 매칭 점수가 낮은 것들은
   블록을 시트로 렌더해 눈으로 찾아야 한다
3. 음영을 흉내낼지 판단 (단색 5 로 충분한지 실기에서 본다)

### 4.17.9 그리기 규칙을 실기가 가르쳐 줬다 — 색 5는 그림자다 (2026-09-09)

4.17.8 의 시험 롬을 실기에서 보니 **`規` 가 사라지고 빈칸이 됐다.** 패치는 먹혔고
글리프는 안 보였다.

**원인**: 색 5 를 획 색으로 골랐는데 **색 5 는 그림자색**이다. 배경과 가까워
획에 쓰면 보이지 않는다.

글리프를 색별로 분해하니 규칙이 나왔다.

```
削:  ..#######o.        # = 획   (4/7/9/13)
     ..#ooooo#o.        o = 색 5, 획의 **우하단 1px 그림자**
     ..#o....#o.        . = 색 0, 투명
```

색 5 를 뺀 `4·7·9·13` 만 렌더하면 `規` 가 1px 획으로 깔끔하게 읽힌다.
색 분포(`削`)는 `0:109 5:71 4:18 7:19 9:30 13:9` 로, 배경 0 과 그림자 5 가
대부분이고 획은 76px 뿐이다.

**획 색은 디더링이다.** `削` 의 긴 직선 획을 뽑으면 `4,9,9,4,9,7,d` 처럼 섞여
있다 — 팔레트 중간색을 만드는 것이다.

**그런데 디더를 흉내내면 자리에 안 들어간다.** 색이 섞이면 압축이 나빠진다.

| 방식 | 크기 / 칸 786 |
|---|---|
| 4색 디더 + 그림자 | 787 (초과 1) |
| 2색(9,7) + 그림자 | 795 (초과 9) |
| **단색 9 + 그림자** | **770 (가능)** |
| 단색 9, 그림자 없음 | 749 (가능) |

단색 9 로 간다. 9 는 원본 획에서 가장 많이 쓰이는 색이라 확실히 보인다.
원본보다 평평하지만 읽힌다.

**획 굵기도 고쳤다.** 원본은 1px 인데 `NanumGothicBold` 14 는 2px 이 나온다.
`malgun.ttf` 14 가 1px 로 깔끔하다 (획 36px).

### 4.17.10 세이브 화면 라벨 3개 한글화 — 실기 확인됨 (2026-09-09)

**「新규」가 실기에서 나왔다** (실기). 4.1 이 뚫렸다.

색 5(그림자)를 제외하고 렌더하면 글자가 선명하게 읽힌다. 처음 시트를 볼 때
그림자를 포함해서 뭉개져 보였고, 그래서 `新` 의 자리를 잘못 짚었다.

**자리를 찾는 방법이 확립됐다.**

```
VRAM 타일 = 576 + 32*(블록순번 - 7) + 블록내타일
```

블록순번은 엔트리[22]를 **주소순으로 정렬**한 것이고, `0x16aa16` = VRAM 576 은
1024/1024 일치로 확정한 값이다 (4.17.6). VRAM 덤프를 템플릿 매칭해 글자의
VRAM 타일을 얻고 이 식으로 역산한다.

| 글자 | VRAM 타일 | 블록 | 타일 | 바꾼 글자 |
|---|---|---|---|---|
| 新 | 554 | `0x16a6d5` | 10 | 신 |
| 規 | 586 | `0x16aa16` | 10 | 규 |
| 削 | 608 | `0x16ad27` | 0 | 삭 |
| 除 | 610 | `0x16ad27` | 2 | 제 |
| 設 | 778 | `0x16b9dc` | 10 | 설 |
| 定 | 780 | `0x16b9dc` | 12 | 정 |

**같은 블록에 두 글자가 들어간다.** `削`·`除` 는 `0x16ad27`, `設`·`定` 은
`0x16b9dc` 다. 항목마다 블록을 다시 풀면 앞의 수정이 날아가므로 블록별로 묶었다.

**네 블록 전부 제자리에 들어갔다.**

| 블록 | 크기 / 칸 |
|---|---|
| `0x16a6d5` | 824 / 834 |
| `0x16aa16` | 770 / 786 |
| `0x16ad27` | 584 / 632 |
| `0x16b9dc` | 634 / 655 |

**남은 것**: 아래 문장 「セーブエリアを選んでください」 14자. 그리고 같은
방법으로 아이템 목록 창과 오프닝.

### 4.17.11 아래 문장까지 — 타일맵이 두 겹이었다 (2026-09-09)

「신규 / 삭제 / 설정」이 실기에서 확인됐다 (실기). 의도한 타일만
바뀌었음도 확인했다 — 네 블록의 글리프 타일 외 변화 0개, 다른 블록 변화 0개.

**문장을 찾는 데 타일맵이 두 겹인 것이 관건이었다.**

| 타일맵 | 내용 | 특징 |
|---|---|---|
| `0x7000` | 배경 그림 | 빈 타일 `0x028f` 가 410회. **행 26 이후가 비어 있다** |
| `0x7800` | 문장 | 행 24~25. 빈 타일 `0x0000` 이 956회 |

배경 타일맵만 보고 「행 26 이후가 비었다」에서 멈췄다가, 2KB 창마다 최빈 항목을
세어 `0x7800` 을 찾았다. **최빈 항목이 압도적으로 많은 구간이 타일맵이다.**

**그 BG 의 문자 베이스가 512 다.** 행 24 가 `160..175, 192..201` 이고
`セ` 를 VRAM 타일 672 로 매칭했으므로 `672 = 512 + 160` ✓.

```
글자 k = VRAM 타일 672+2k        (k < 8,  블록 0x16b25b 타일 2k)
         VRAM 타일 704+2(k-8)    (k >= 8, 블록 0x16b4c6 타일 2(k-8))
```

**문장은 13칸이다.** 원문은 14자로 읽히는데 타일맵 행이 26타일(=13글자)뿐이다.
렌더해 보면 `セ ー ブ エ リ ア を 選 ん で く だ さ` 로 13자가 읽힌다.
13칸에 맞춰 「 세이브 영역을 고르세요」 (앞 1칸 비움) 로 넣었다.

**빈 칸 처리를 추가했다.** `menufont.render(" ")` 는 전부 0 인 셀을 돌려준다.

**여섯 블록 전부 제자리**

| 블록 | 크기 / 칸 | 글자 |
|---|---|---|
| `0x16a6d5` | 824 / 834 | 신 |
| `0x16aa16` | 770 / 786 | 규 |
| `0x16ad27` | 584 / 632 | 삭 제 |
| `0x16b9dc` | 634 / 655 | 설 정 |
| `0x16b25b` | 417 / 620 | (공백) 세 이 브 (공백) 영 역 을 |
| `0x16b4c6` | 493 / 602 | (공백) 고 르 세 요 |

한글 글리프가 한자보다 단순해서 문장 블록은 원본의 3분의 2 크기다.

### 4.17.12 설정 화면이 깨졌다 — 그리고 내 추론이 틀렸다

문장까지 넣은 빌드를 사용자가 돌렸다. 세이브 화면은 완벽했는데
(`image/메뉴시험3.png`) **설정 화면이 깨졌다** (`image/메뉴시험-설정.png`).

「メッセージ速度」 자리에 「면공가했ジ땠곧」 이 나왔다.

내가 즉시 세운 추론은 이랬다:

> 폰트 시트가 화면 전용이 아니라 **공유**다. 문장은 가나 13자인데 가나는
> 표음문자라 온 화면에 재사용된다. `セ -> 세` 로 바꾸면 다른 화면의 `セ` 도
> 「세」가 된다. 문장을 되돌리겠다.

그럴듯했다. 그래서 되돌렸다. **그리고 그 추론은 틀렸다.**

**깨진 글자를 세어 봤다.** 면 공 가 했 땠 곧 쌌 데 흠 막 보 역 큐 범 여 럴 릴 고
— 18자. 전부 `codes.json` 에 있었다. 즉 **대사 폰트에 배정된 한글**이다.
메뉴 폰트가 아니다.

결정적 증거가 둘 더 있었다.

  - `魔` 가 정상 출력됐다. 이건 F4 제거로 **복구한 대사 폰트 글리프 0x00** 이다.
  - `ＯＮ` `ＥＸＩＴ` 도 정상이다. 대사 폰트의 ASCII 자리다.

**설정 화면은 대사 폰트를 쓴다.** 그 깨짐은 4.1 의 기존 증상이고 메뉴 패치와
무관하다. 4.17.11 의 문장 되돌리기는 근거가 없어졌으므로 **복구했다.**

블록 소유를 확인해 뒷받침도 얻었다. `gfx.blocks()` 로 41개 엔트리를 전부 훑으면
건드린 여섯 블록은 **전부 엔트리 22 전용**이다 (전체 42441 블록 중 12308개가
둘 이상 엔트리에 걸쳐 있으니, 공유가 흔한 롬에서 이 여섯은 아니었다).

**교훈.** 두 화면이 같이 깨졌다는 사실만으로 원인을 잇지 말 것. 깨진 **글자가
어느 폰트에 있는지** 확인하면 1분에 갈린다. 이번에도 4.17.4 와 같은 실수였다
— 위치만 보고 코드를 안 봤다.

### 4.17.13 설정 화면 한글화

깨진 글자의 **코드로 롬을 검색**해 텍스트 위치를 찾았다.

```
「면공가했」 = 92 6f 7e b0  ->  0x2ff706   (원본과 바이트 동일 = 미번역)
```

`0x2FF706`~`0x2FF748` 이다. 4.9 에서 이 구간(`0x2FD32E`~`0x2FF780`)을
「텍스트가 아니다」 라고 판단했는데 **틀렸다.** 일부가 텍스트다.

한글 글리프와는 겹치지 않는다. 이 구간은 F7 슬롯 `0xDC`~`0xDD` 로 배정 제외
구간(`0x3E`~`0xDD`) 안이고, 한글이 쓰는 상위 슬롯은 `0xDE`(`0x2FF780`) 부터다.

미식별 한자를 렌더해 확정했다: `F7 2F` = 速, `F7 30` = 遲, `F7 31` = 左,
`F7 32` = 右. 화살표 십자 주위 네 글자가 右·下·左·上 이다.

**「좌」 가 대사 폰트에 없었다.** 「좌」 도 「왼」 도 배정이 없었다. 억지로 넣는
대신 `patch_opt.pairs()` 를 `build.plan` 의 배정 입력에 넣어 정식으로 통합했다
(설명문·엔딩과 같은 방식). 배정이 803 -> 804 음절로 늘었고 예산 초과는 0건.

설정 화면도 메뉴 계열이니 `no_risky` (메뉴 안전 슬롯) 에도 넣었다.

**바이트 예산 때문에 못 쓴 말**

```
「빠름」   4바이트 > 3   ->  「빨리」   3바이트
「스테레오」 5바이트 > 4   ->  「입체」   3바이트
「모노랄」              ->  「모노」   3바이트
```

**남는 공백이 칸을 늘리는 문제.** 종료자가 없어 바이트를 정확히 맞추고 공백
`0x20` 으로 채우는데, 공백도 1칸을 먹는다. 6개 필드가 원문보다 칸이 늘었다
(7->8, 4->5, 1->2 ×3, 4->5). 그래도 안전하다고 판단한 근거는
`patch_opt.py` 의 docstring 에 적었다 — 늘어난 칸은 전부 **뒤쪽 공백**이고,
칸 고정이든 바이트 고정이든 **화면에 보이는 모습이 같다.** 한 줄에 두 필드가
나란히 놓이는 곳(遅い/速い, ＯＮ/ＯＦＦ, ステレオ/モノラル)만 칸이 늘지 않게
맞췄다.

`ＯＮ` `ＯＦＦ` `ＥＸＩＴ` `←` `→` 는 그대로 뒀다. 원본 글리프다.

패치된 롬에서 12줄을 직접 렌더해 눈으로 확인했다. 전부 정상 한글이다.

### 4.17.14 본 빌드에 통합

메뉴 폰트 패치와 설정 화면 패치를 `build.py` 에 넣었다. 이제 시험용 롬을 따로
만들지 않는다.

검증도 둘 늘려 **11개**가 됐다.

```
[10] 설정 화면 제자리          — 인코딩 재계산 후 바이트 비교
[11] 메뉴 폰트 글리프 19개      — 압축이라 바이트 비교가 안 된다.
                                풀어서 menufont.render() 결과와 타일 비교
```

`[3]` 은 설정 구간을 제외해야 한다. 폰트 영역 안이지만 글리프가 아니다.
`[5]` 는 메뉴 블록 구간(`block_limit` 까지)을 허용에 추가했다.

**수동 확인이 필요하다.** 설정 화면과 세이브 화면은 실기(또는 에뮬레이터)에서
직접 봐야 한다. 자동 검증은 「롬에 의도한 바이트가 들어갔는가」 까지다.

### 4.17.15 칸이 밀렸다 — 남는 공백도 칸을 먹는다

4.17.13 에서 「늘어난 칸은 전부 뒤쪽 공백이라 안 보인다」 고 판단했다.
**틀렸다.** 실기에서 글자가 줄을 넘고 잘렸다 (`image/image.png`).

```
1행:  메시지  속도            림  빨
2행:  리이동방                      향
3행:                    EX      우
4행:  하   좌상   마법   효과
아래:  모노
```

「느림」의 「느」가 없고, 「빨리」가 두 줄로 갈렸고, 「사운드」·「입체」는
아예 안 나왔다. **바이트는 정확히 맞췄는데도** 밀렸다는 것이 핵심이다.

**원인.** 남는 공백 `0x20` 도 1칸을 먹는다. 그리기 루틴은 칸을 세며 커서를
전진시키므로, 칸이 하나 늘면 그 뒤가 전부 밀린다. 바이트 수를 맞추는 것으로는
부족하다.

**정확한 제약**을 세웠다. 이스케이프 e개, 단일바이트 s개, 남는 공백 p개면

```
바이트 = 2e + s + p = nb
칸     = e + s + p  = nb - e
```

즉 **칸 = 바이트 − 이스케이프 수**다. `nb` 가 고정이니 **이스케이프 개수가
원문과 같아야 칸이 같다.** `필요 e = nb - nc` 다.

| 원문 | 번역 | nb | nc | 필요 e | 그때 e |
|---|---|---|---|---|---|
| メッセージ速度 | 메시지 속도 | 10 | 7 | 3 | 2 |
| 移動方向 | 이동방향 | 7 | 4 | 3 | 2 |
| 右 / 下 / 上 | 우 / 하 / 상 | 2 | 1 | 1 | **0** |
| サウンド | 사운드 | 5 | 4 | 1 | 0 |
| ステレオ | 입체 | 4 | 4 | 0 | **1** |
| モノラル | 모노 | 4 | 4 | 0 | **1** |

여덟 항목이 틀렸다. 방향은 두 가지고 수단도 두 가지다.

**e 를 줄이려면 — `force` (단일바이트 승격).**
`ステレオ` 는 이스케이프 0개짜리 4칸이라 네 음절 전부 단일바이트여야 한다.
「테」와 「노」를 `force` 에 넣어 「스테레오」·「모노」를 제대로 썼다
(`patch_opt.FORCE`). 대가로 대사 #1060 이 1바이트 넘쳤고, 「案ずるな」의
번역을 「걱정하지 말라」 -> 「걱정 말라」 로 줄여 51/52 로 맞췄다. 원문이 더
짧은 말투라 오히려 나아졌다.

**e 를 늘리려면 — 쌍둥이 글리프.**
「우」는 단일바이트라 1바이트 1칸이다. 원문 「右」는 2바이트 1칸이다. **2바이트
1칸**을 쓰는 방법은 하나뿐이다 — **같은 글자를 이스케이프 슬롯에도 하나 더**
두는 것. 대사는 계속 싼 단일바이트를 쓰고 설정 화면만 쌍둥이를 쓴다.

```
시 f7f7   이 f7f8   우 f7f9   하 f7fa   상 f7fb   사 f7fc   (6자)
```

메뉴 안전 슬롯만 썼다. 설정 화면 렌더러가 5D/D5(엔진 패치가 추가)를 아는지
확인되지 않았고, 둘째 바이트가 `0x20` 미만이면 제어 코드로 읽힌다.

**안전 슬롯이 한 칸도 안 남아 있었다.** 651칸이 음절 804자에 전부 소진된다.
그래서 할당기에 `reserve_safe` 를 넣어 뒤에서 8칸을 떼어 뒀다
(`krcodec.allocate`). 뒤쪽을 떼는 이유는 안전 슬롯이 빈도순으로 앞에서
소진되므로 뒤쪽이 가장 늦게 쓰이는 칸이기 때문이다.

**nc 를 손으로 적었다가 틀렸다.** 「メッセージ速度」를 8칸으로 셌다.

```
92 6f 7e b0 7c 01 f7 2f f5 be
メ  ッ  セ  ー  シ ゛  速    度      -> 7칸
```

`0x01` 은 **탁음 결합**이고 칸을 늘리지 않는다. `サウンド` 도 `84 01`
(ト+゛) 이라 4칸이다. 상수를 믿은 것이 문제였으므로 `orig_cells()` 로
**원본에서 세어 대조**하게 했다 (`check_nc`). 이제 표가 틀리면 빌드가 멈춘다.

결과: 12항목 전부 원문과 칸·바이트가 정확히 일치한다. 배정은 804 -> 810
슬롯(쌍둥이 6)으로 늘었다.

**교훈.** 「안 보이니 괜찮다」는 추론을 실기 확인 없이 커밋했다. 4.17.12 와 같은
실수다 — 그때는 두 화면의 동시 이상을 원인으로 이었고, 이번엔 렌더러 모델을
확인 없이 골랐다. **렌더러가 무엇을 세는지 모르면 칸을 원문과 똑같이 맞춰라.**

### 4.17.16 실기 확인 — 설정 화면 완료

`image/메뉴시험-설정2.png` 로 확인했다. 깨진 원본(`image/메뉴시험-설정.png`)과
자리가 정확히 일치한다.

| 자리 | 원본(한글 폰트로 깨진 상태) | 지금 |
|---|---|---|
| 1행 라벨 7칸 | 면공가했ジ땠곧 | 메시지 속도 |
| 1행 값 2칸 | 쌌데 | 빨리 |
| 2행 라벨 4칸 | 흠막보역 | 이동방향 |
| X 네 귀퉁이 | 늘 얄 획 끈 | 상 우 좌 하 |
| 3행 라벨 7칸 | 魔큐범여럴릴고 | 마법 효과 |
| 값 | ＯＮ | ＯＮ (원본 유지) |
| 아래 | ＥＸＩＴ | ＥＸＩＴ (원본 유지) |

X 자 네 방향은 같은 바이트 자리에 같은 칸 수로 썼으므로 위치가 그대로
보존됐다. 화면상 배치는 좌상=上, 우상=右, 좌하=左, 우하=下 다. 아이소메트릭

그래서 `0x2FF734`~`0x2FF740` 의 「サウンド」「ステレオ」「モノラル」 은 이
화면이 아닌 다른 곳에서 쓰이거나 미사용이다. 번역은 넣어 뒀지만 **확인하지
못했다.** 확인하려면 그 문자열을 그리는 화면을 찾아야 한다.

값 표시는 현재 설정만 그린다 (「빠름/느림」 중 하나, ＯＮ/ＯＦＦ 중 하나).
그래서 「느림」 은 메시지 속도를 느리게 바꿨을 때만 보인다.

## 4.18 오프닝 컷신 — 글리프를 찾았다 (타일맵은 아직)

「확정된 텍스트 구간 4곳 어디에도 없다」로 여섯 번 막혔던 문제다. 이번에
글리프를 **정확히** 찾았다.

### 4.18.1 gfx.blocks() 에 버그가 있었다 — 이게 여섯 번의 실패 원인이다

블록 목록 길이를 「첫 오프셋 ÷ 2」로 구했다. 그런데 **첫 항목이 `0xFFFF`(빈
블록)일 수 있다.**

```
엔트리 18: ff ff 40 00 a2 01 5d 03 ...   -> first//2 = 32767 (쓰레기)
엔트리 28: ff ff ff ff ff ff ff ff ...    -> 여섯 개가 FFFF
엔트리 22: 40 00 22 02 ff ff b3 03 ...    -> 중간에 FFFF (이건 괜찮았다)
```

`first//2` 를 쓰면 32767개 블록이 나와 블록 데이터를 오프셋으로 오해한다.
그래서 4.17 에서 **엔트리 18·28 을 「그래픽 표가 아니다」라고 제외했다.**
오프닝 텍스트는 정확히 그 안에 있었다.

고친 규칙: **처음 나오는 실제 오프셋**을 쓴다. 목록이 표 바로 뒤에서
시작하므로 그 값이 목록 길이 × 2 다.

```
전체 유효 블록 1271 -> 1299 (엔트리 18 에서 16, 28 에서 12)
복호 1299/1299, 재압축 왕복 1299/1299
```

### 4.18.2 찾은 방법 — 스크린샷을 템플릿으로 썼다

Noto CJK Bold 로 만든 템플릿은 최고 0.70 에 머물렀다. 이 서체가 게임 전용
장식체라 TrueType 축소와 성질이 다르다 (4.4 에서 겪은 것과 같은 문제).

그래서 **스크린샷에서 글리프를 직접 뽑았다.** 에뮬레이터 창이 정확히 2배
스케일이라(행이 쌍으로 동일) 나누기만 하면 원본 픽셀이 나온다.

```
자간 32px = 게임 16px.  1행 x0=136 y0=368, 2행 x0=122 y0=416
BOX 축소로 16x16, 임계값 30 으로 잉크 마스크
```

대조는 IoU. 후보는 블록 1299개 × 타일오프셋 15 = 19,485개를 벡터화해서
템플릿 하나당 49번(±3 이동) 행렬곱으로 계산했다.

**15자 전부 IoU 1.000.** 완전 일치다.

| 블록 | 엔트리 | 타일 0·2·4·6·8·10·12·14 |
|---|---|---|
| `0x159197` | 18 | (빈칸) は 闇 に か え り を |
| `0x159321` | 18 | う み だ す べ て そ こ |

한 번 `bool @ bool` 로 행렬곱을 해서 점수가 0.02 로 무너졌다. numpy 에서
불리언 곱은 논리곱이라 개수가 안 나온다. 정수로 캐스팅해야 한다.

### 4.18.3 시트는 내레이션 전체다 — 중복을 뺀 첫 등장 순서

엔트리 18 의 텍스트 블록 11개 × 8글리프 = 88칸이다 (`image/오프닝글리프.png`).

```
_ は 闇 に か え り を | う み だ す べ て そ こ | ら 始 ま い つ へ む っ
く ル ナ ッ 天 存 在 大 | 地 と 生 命 モ ン ス タ | 一 人 間 た お な る 支
配 い 魔 王 よ ば れ の | お 絶 対 で あ 現 ひ ぃ | き 運 変 者 が わ 英 雄
神 口 ン ら 6 聖 騎 士 彼 | 戦 ど で 封 じ あ が 時
```

순서가 **첫 등장 순서**임을 확인했다. 화면의 두 문장은
「光は闇にかえり」 + 「闇は光を」 + 「うみだす」 인데, 시트는
`光 は 闇 に か え り` 다음에 **`を`** 가 온다. 중복된 `闇は光` 을 뺀
자리다. 즉 컷신 전용 미니 폰트다.

**「光」만 엔트리 18 에 없다.** 완전일치가 엔트리 22 (`0x169c76` 타일 10)
한 곳뿐이다. 엔트리 22 는 세이브 화면 라벨(新規·削除·設定)이 있는 공용 한자
시트다. 블록 `0x159197` 타일 0 은 잉크 0(빈칸)이다. 그림 데이터와 텍스트
사이의 여백으로 보인다. 화면이 두 시트를 함께 올리는 것으로 추정하지만
**확인하지 못했다.**

일부 가나는 엔트리 28 에도 완전일치 사본이 있다 (は に か り を う す).

### 4.18.4 막힌 곳 — 조합용 타일맵이 롬에 평문으로 없다

글자를 바꾸려면 글리프만으로는 안 된다. 한국어는 어순·글자 수가 달라서
**어느 글리프를 어느 자리에 그리는지**를 정한 인덱스 스트림 또는 타일맵을
고쳐야 한다.

없다는 것을 아래 전부로 확인했다.

| 찾은 것 | 결과 |
|---|---|
| 인덱스 바이트열 (1행 = 0..6 오름차순 + 2행 = 2,1,0,7…) | 0건 |
| 같은 패턴, 간격 1~8 (스프라이트 항목 대비) | 0건 |
| 같은 패턴, 16비트 워드 | 0건 |
| 제어 바이트 허용 — 부분수열 매칭 | 0건 |
| 16x16 글리프 타일맵 서명 (윗줄 14 + 아랫줄 +16) | 롬 평문 57건 전부 램프표 오검출 |
| 같은 서명, 워드 형태 | 20건 전부 순차 이미지 맵 오검출 |
| 복호한 1299블록 안 워드 증가런 | 0건 |

차이 수열로 찾았으므로 **기준값 오프셋과 무관하게** 없다. 압축돼 있거나
코드가 만들어 내는 것이다.

**다음 입력이 필요하다 — 오프닝 텍스트가 떠 있는 순간의 VRAM·타일맵 덤프.**
세이브 화면을 뚫은 것과 같은 방법이다 (4.17.11). 실제 타일맵 워드를 알면
그 값으로 롬을 찾을 수 있고, 없으면 그때는 코드를 읽어야 한다.

### 4.18.5 VRAM 덤프로 구조가 갈렸다 — 스프라이트였다

`Dark Half (Japan) - SnesVideoRamopening.dmp` 로 확정했다.

엔트리 18 의 블록이 VRAM 에 순차로 올라간다. 롬 블록의 32바이트 타일을 VRAM
에서 그대로 찾아 확인했다.

```
블록5 0x159197 -> VRAM 타일 544      블록12 -> 768
블록6 0x159321 -> 576               블록13 -> 800
...                                 블록15 -> 864
VRAM 타일 = 544 + 32*(블록순번 - 5) + 블록내타일
```

**배경 타일맵에는 없었다.** 타일 512~640 을 참조하는 연속 워드 런이 VRAM 어디에도
없다. 즉 배경이 아니라 **스프라이트**다.

그래서 실제 VRAM 타일 번호로 롬을 다시 찾았다. 「闇は光をうみだす」 = 타일
548,546,938,558,576,578,580,582 이고, 이걸 **스프라이트 이름 하위바이트**로
바꿔(`24 22 aa 2e 40 42 44 46`) **간격 2** 로 찾으니 `0x9ED8A` 한 곳이 나왔다.
간격 2 는 (타일, 속성) 쌍 구조라는 뜻이다.

**형식** — 글자마다 2바이트다.

```
(타일 하위바이트, OAM 속성)
속성 = OAM 바이트3: bit0=이름 9번째 비트(N), bit1~3=팔레트, bit4~5=우선도

  속성 0x21 (N=1, 팔레트0) -> VRAM 타일 = 512 + 하위     (544~767)
  속성 0x22 (N=0, 팔레트1) -> VRAM 타일 = 768 + 하위     (768~1023)

  ff ff = 줄 끝      fe ff = 쪽 끝
```

교차 검증: 「光」은 `aa 22` -> 768+170 = VRAM 938 이고, VRAM 938 의 32바이트가
엔트리 22 블록 `0x169c76` 타일 10 과 **바이트 일치**한다. 그래서 4.18.3 의
「光 만 엔트리 18 에 없다」가 설명된다 — 화면이 두 시트를 함께 올리고, 光 은
공용 한자 시트에서 가져온다. 엔트리 18 의 첫 칸(타일 544)은 빈칸이고 **공백**으로
쓰인다.

**스크립트 전체는 `0x9ED6E`~`0x9EFF4` 646바이트, 23줄 273칸, 11쪽이다.**
복호해 렌더하니 내레이션이 전부 읽혔다.

```
光は闇にかえり / 闇は光をうみだす / すべてはそこから始まり
いつかはそこへむかっていく / 天と地がわかれ / 大地に生命がうまれるころ
すでにルキュは存在した / ルキュはおおいなる闇を支配し / いつしか魔王とよばれた
魔王のちからは絶対であった / 人間は魔王を恐れ / そのちからのまえにひれふした
しかしあるとき / この運命を変えようとする者が / あらわれる
英雄神ローグと / ６人の聖騎士たち / 彼らは魔王に戦いをいどみ
みごと魔王を封じこめた / 人間がおびえてくらす時代は / 過去のものとなり
あたらしい太陽がのぼった / 〜「魔王神話」序説〜
```

### 4.18.6 오프닝 한글화

**칸 수를 줄마다 원문과 똑같이 유지했다.** 한국어를 가운데 맞춤으로 넣고 남는
칸은 공백(타일 544)으로 채운다. 그러면 바이트 길이가 원문과 같아 포인터를
건드릴 위험이 없다. 4.17.15 에서 설정 화면이 칸 하나 때문에 밀린 뒤로 이
원칙을 먼저 세웠다.

**슬롯이 88칸뿐이다.** 초안은 고유 음절 93자로 넘쳤다. 한 번만 쓰는 음절이
많은 문구를 바꿔 83자로 줄였다.

```
하늘과 땅이 나뉘고  -> 천지가 갈라지고      (늘·땅·뉘 빼고 천·갈 넣어 -1)
그 힘 앞에 엎드렸다 -> 그 힘에 굴복했다     (앞·엎·드 빼고 굴·복 -1)
새 태양이 떠올랐다  -> 새 태양이 떴다       (떠·올·랐 빼고 떴 -2)
여섯 성기사들       -> ６인의 성기사        (여·섯 빼고 원본 ６ 재사용 -2)
끝내 마왕을 봉인했다 -> 마왕을 봉인했다      (끝·내 -2)
영웅신 로그와       -> 영웅신 로그          (와 -1)
루큐는 큰 어둠을... -> 루큐는 어둠을...     (큰 -1)
```

두 칸은 예약했다 — 타일 544(공백)와 타일 838(`６`). 23행의 `〜` `「` `」` 는
VRAM 896 이상, 즉 **공용 한자 시트**에 있어서(910·928·932) 건드리지 않고 그대로
참조한다. 다른 화면이 쓰는 시트라 손대면 안 된다.

**4색 그라데이션을 못 썼다.** 원본 글리프는 중심에서 바깥으로 2->3->4->5 방사형
그라데이션인데, 그대로 쓰면 재압축이 칸을 넘는다. 한글은 획이 흩어져 색 경계가
많고, 우리 packer 는 원본이 쓰는 **역참조(copy, `$C03414`) 명령을 내보내지
않는다.** 실제로 **원본 데이터를 그대로 재압축해도 넘친다** (블록5: 419 > 395).

```
4색     초과 7/11 블록
2색 4/5 초과 0/11   310/395 ~ 440/468
단색 4  초과 0/11   204/395 ~ 348/468
```

2색(바깥 5, 안쪽 4)으로 원본 방향을 지키면서 전부 칸에 들어갔다.

서체는 `NotoSerifCJK-Bold` 15 다. 원본이 명조계라 맞다 (메뉴 폰트는 고딕계
malgun 이었다 — 화면마다 서체가 다르다).

`patch_menu.block_limit` 은 같은 엔트리 안에서만 다음 블록을 찾으므로 엔트리의
**마지막 블록**에서 None 을 준다. 롬 전체에서 다음 블록을 찾는 `block_cap` 을
따로 뒀다.

검증은 `[12]` 로 넣었다 — 스크립트 바이트와 글리프 83자를 풀어서 대조한다.
결과는 `image/오프닝한글.png` 다. **실기 확인이 필요하다.**

### 4.19 「일본어가 남았다」로 보이던 것이 제어 파라미터였다

실기에서 워프 목록 한 항목이 「마왕  정상G모습이다」로 깨졌다
(`image/오류.png`).

**구조.** `#1078`~`#1096` 이 워프 목록 19개고, 원본은 전부 이렇게 끝난다.

```
<FA><士>     <EB><15>の頂<EE>に←     =  fa 01 20*5 eb 15 c9 f5 6c ee c6 e0
```

추출기는 `c6` 을 「に」로 읽는다. 표에 그 글자가 있으니 당연하다. 그래서
번역할 때 「〜에←」로 고쳤다. **그런데 `c6` 은 텍스트가 아니라 `<EE>` 의
파라미터다.** 바꾸면 렌더러가 다른 동작을 하고 뒤가 무너진다.

증거는 분포였다. 19개 중 **5개만**(`#1078`·`#1085`·`#1087`·`#1093`·`#1095`)
「에」로 바꿨고 나머지 14개는 「に」를 그대로 뒀다. 깨진 것은 그 5개뿐이다.
바꾼 것만 깨졌고 안 바꾼 것은 멀쩡했다.

```
원본  ... ee c6 e0
신규  ... ee 82 e0     (82 = 에)   -> 깨짐
```

「に」가 화면에 안 보이던 이유도 이걸로 설명된다. 사용자가 계속 플레이했는데
워프 라벨 19개에 일본어가 보였다는 말이 없었다 — 애초에 그려지지 않는다.

**되돌렸다.** 5개를 `<EE>に←` 로 복구해 19/19 가 원본과 같은 `ee c6 e0` 이다.

**검사를 추가했다 (`trcheck` [12]).** 원본과 번역에서 `<EE>` 다음 토큰이 같아야
한다. 기존 「제어 코드 불일치」 검사는 `<E5>`~`<FE>` 태그의 **개수**만 보므로
이건 못 잡는다 — 태그는 그대로고 그 뒤 글자만 바뀌었기 때문이다.

바이트 수준으로 0xEE 를 세면 안 된다. `f5 ee` 처럼 **이스케이프의 둘째 바이트**가
0xEE 인 경우가 있어서 `#673` 이 오검출된다. 판독문 토큰 단위로 봐야 한다.

회귀 시험도 했다 — `#1095` 를 다시 「에」로 바꾸면 검사가 잡는다.

**교훈.** 추출기가 텍스트로 읽어 준 글자가 전부 텍스트는 아니다. 제어 코드
바로 뒤의 글자는 인자일 수 있고, 그때는 **일본어로 남겨 두는 것이 맞다.**
같은 구조가 여럿일 때는 **전부 같게 처리해야** 한다 — 5개만 바꿨더니 그
5개만 깨졌다.

## 4.20 아이템 창 VRAM 덤프 — 「목록 창은 메뉴 폰트를 쓴다」가 틀렸다

`Dark Half (Japan) - SnesVideoRamitem.dmp` (원본 롬 상태) 를 분석했다.

### 4.20.1 이름·설명은 대사 폰트를 64바이트 통째로 올린다

VRAM `0x3000`~`0x3400` 을 대사 폰트 글리프와 바이트 비교했더니 전부 맞았다.

| VRAM | 글리프 | 무엇 |
|---|---|---|
| `0x3040` `0x3080` `0x30c0` | ヒ ー ル | 아이템 이름 |
| `0x3140` `0x3180` `0x31c0` | Ｈ Ｐ を | 설명 1행 |
| `0x3200` `0x3240` | **F6 3f** **F5 20** | 回 復 (뱅크 이스케이프) |
| `0x3280` `0x32c0` | す る | |
| `0x3300` `0x3340` | **F6 bb** **F6 bc** | 한자 이스케이프 |
| `0x33c0` | ア | 설명 2행 |

**이스케이프가 정상 해석된다.** `F6 3f` 가 뱅크 F6 의 0x3f 글리프로 올라가 있다.
즉 이 업로더는 프리픽스를 이해한다.

`セ` 는 VRAM 에 없다 — 필요한 글리프만 올린다. 이름은 `0x3000` 을 비우고
`0x3040` 부터 3개, 설명은 `0x3100` 을 비우고 `0x3140` 부터다.

**그래서 README 의 「마법 목록 / 원본 가나 / 메뉴 폰트 — 미패치」는 틀렸다.**
목록 창은 메뉴 폰트가 아니라 **대사 폰트**를 쓴다. 4.1 의 「롬→WRAM→VRAM 경로로
폰트를 따로 올린다」는 관찰은 맞았지만, 올리는 것이 별개 서체가 아니라 **대사
폰트의 필요한 글리프**였다.

마법 이름은 이미 번역돼 있다. 한글 롬 `0x4f400` 부근이

```
원본  ff 83 01 7d ff | 8b b0 99 ff | 77 6d 71 ff   (デス / ヒール / キュア)
한글  ff b4 64 ff ff | f7 25 ff ff | f5 fa 83 ff   (데스 / 힐 / 큐어)
```

`힐` = `f7 25` 이고 둘째 바이트 0x25 는 0x20 이상이라 메뉴 안전 조건도 만족한다.

`image/KR.png` (2026-09-08 캡처) 의 깨짐은 마법 이름표 번역(09-03) **이후**지만
`F4` 제거와 메뉴 안전 슬롯 도입(같은 09-08)과 시점이 겹친다. 그 캡처가 이미
고쳐진 증상일 가능성이 있으므로 **현재 빌드로 다시 확인해야 한다.**

### 4.20.3 내 세이브 문장 패치가 아이템 창을 건드린다

아이템 창은 엔트리 22 **블록 7~13** 을 VRAM 576~799 에 올린다. 세이브/시스템
메시지 글리프다. 그중 블록 10·11 은 내가 세이브 문장으로 덮은 블록이다.

아이템 창의 타일맵(VRAM `0x1800`)에서 16x16 글리프를 뽑으면 타일
712·714·716·718 = **さ い 説 明** 을 참조한다. 이 중

```
712 = 블록11 타일8  = さ   <- 내가 「요」로 덮었다
714 = 블록11 타일10 = い   그대로
716 = 블록11 타일12 = 説   그대로
718 = 블록11 타일14 = 明   그대로
```

**한 칸이 깨진다.** 문장이 실은 14자였고(블록10 8자 + 블록11 6자
`ん で く だ さ い`) 세이브 화면 타일맵은 13칸만 쓴다. 그래서 13칸으로 넣은
것은 맞았지만, 13번째가 `さ` 자리라 그 글리프를 쓰는 다른 화면에 번진다.

**즉 「폰트 시트가 공유다」는 4.17.12 의 첫 추론이 아이템 창에 대해서는
맞았다.** 설정 화면에 대해서는 틀렸고(그건 대사 폰트였다), 아이템 창에
대해서는 맞았다. 같은 문장으로 두 결론이 갈린다.

## 4.21 아이템 창 — 버그가 아니라 미완성이었다

한글 빌드의 VRAM 덤프(`SnesVideoRamitem2.dmp`)로 확정했다. 엔트리 22 블록
7~13 이 한글 롬 것과 바이트 일치하므로 이 덤프는 한글 빌드다.

### 4.21.1 장비 이름표가 절반만 번역돼 있었다

`0x4f1c0`~`0x4f3d3` 에 15개가 번역돼 있고 **13개가 일본어로 남아 있었다.**
미번역 일본어는 회수된 가나 슬롯을 가리키니 반드시 깨진다.

```
ショートソート -> 한글 폰트로 읽으면 「즈력되은는되은」
```

아이템 창의 깨짐이 이것이다. 13개를 번역해 장비 이름 29개가
전부 한글이 됐다 (롬에서 되읽어 확인).

`<EE>` 뒤 인자는 전부 보존했다. 이미 번역된 「윙`<EE>`コ`<F3>`」와 같은
구조다 — 4.19 에서 워프 목록 5개만 바꿔 깨진 것과 같은 규칙이 여기서는
처음부터 지켜져 있었다.

이름 예산이 3바이트뿐인 곳이 둘 있어 문구로 해결했다.

```
ナイト -> 「나이트」 4B 초과 -> 「기사」 2B   (「기사문장」과 일관)
タワー -> 「타워」  4B 초과 -> 「탑」  2B
```

### 4.21.2 세이브 문장과 아이템 창이 타일을 공유한다 (그대로 둔다)

아이템 창 타일맵(VRAM `0x1800`)이 타일 712·714·716·718 = `さ い 説 明` 을
참조한다. 세이브 화면 덤프의 문장 타일맵 행 24 를 보면

```
행24: 672 673 ... 686 687 | 704 705 706 707 708 709 710 711 712 713
```

**13번째 칸이 정확히 타일 712** 다. 문장이 13칸을 꽉 쓰므로 피할 수 없다.
한글 덤프에서 그 자리가 「요」로 나오는 것을 확인했다.

**그대로 둔다.** 아이템 창에 한 글자가 섞이는 손실이 세이브 화면 문장
전체를 잃는 것보다 작다. 4.17.12 의 첫 추론(「폰트 시트가 공유다」)이 아이템
창에 대해서는 맞았다는 것이 이걸로 확정됐다 — 설정 화면에 대해서는 틀렸다.

### 4.21.3 목록 창은 대사 폰트를 쓴다 (4.20.1 재확인)

원본 덤프에서 이름·설명 글리프가 VRAM `0x3000` 부터 대사 폰트 64바이트
통째로 올라가 있고 이스케이프도 해석된다. 한글 덤프에서는 그 버퍼 내용이
한글 롬 폰트와 일치하지 않는데, **두 덤프가 서로 다른 창 상태**라 직접
비교가 안 된다. 이름 경로가 이스케이프를 해석하는지는 **확인하지 못했다.**

확인 방법이 있다. 이미 번역된 장비 중

```
「무라마사」 = 3d 2b 3c 3e   (전부 단일바이트)
「버클러」   = 65 7d bd      (전부 단일바이트)
「드래곤세이버」 = dd c7 f5dd a6 22 65   (곤 이 이스케이프)
```

**앞의 둘은 정상이고 뒤가 깨진다면 이름 경로는 바이트당 한 타일**이고, 그때는
장비·마법 이름 음절을 전부 단일바이트로 강제해야 한다. 셋 다 정상이면 이
문제는 없다.

마법 목록도 같은 검증에 쓸 수 있다. 원본 초반 목록은 이렇다 — コンディション · フォーメーション · ファイアボール · アイスストーム ·
ライトニング · ディスペル. 마법 이름표는 이미 번역돼 있으므로 새 빌드에서
파이어볼·아이스스톰·라이트닝·디스펠로 나와야 한다. 안 나오면 이름 경로가
이스케이프를 해석하지 못한다는 증거다 (「파이어볼」 은 이스케이프를 쓴다).

## 4.22 몬스터 이름표 — `<EE>` 가 16비트 포인터다

`<EE>` 뒤 2바이트가 **공유 접미어를 가리키는 16비트 포인터**다. 값이 전부
몬스터 표 구간(`0x4f672`~`0x4f8aa`) 안이고, 따라가면 실제 접미어가 나온다.

| 포인터 | 접미어 | | 포인터 | 접미어 |
|---|---|---|---|---|
| `0x4f68c` | バット | | `0x4f7c8` | ドラゴン |
| `0x4f6b6` | スライム | | `0x4f830` | オーガ |
| `0x4f6d7` | オーズ | | `0x4f744` | ザード |
| `0x4f775` | デーモン | | `0x4f7b2` | ゴーレム |

10개를 따라가 전부 맞았다. 그래서

```
ストーン <EE>→0x4f830  =  ストーンオーガ
```

**4.13 의 「접미사 공유」가 이것이다.** 추출기는 `ee 30 f8` 을 `<EE>０<F8>`
로 읽어 텍스트처럼 보여 주는데, 실제로는 제어 코드 + 포인터다. 4.19 에서
배운 「`<EE>` 다음은 인자다」가 여기서는 **2바이트**로 확장된다.

**그래도 번역하지 않았다.** 두 가지가 미해결이다.

1. **엔트리 경계.** 포인터 표를 못 찾았다 — 16비트도 24비트도, 0xFF 로 끊은
   엔트리 시작 57개를 담은 표도 없다. 순차 주사나 계산된 오프셋으로 보인다.
2. **낱개 라틴 바이트.** 세그먼트 중간에 `Ｐ`(0x50) `Ｖ`(0x56) `Ｆ`(0x46)
   `Ｉ`(0x49) `Ｈ`(0x48) `Ｌ`(0x4c) 이 끼어 있다. 0x46~0x56 이라는 좁은
   범위인데 정체를 모른다. #1326 은 이 바이트로 **시작**하므로 단순 구분자도
   아니다.

경계 규칙을 모르는 채 20개를 고치면 표침범이다 (이미 세 번 겪었다).
**포인터 표나 그리기 코드를 찾는 것이 다음 단계다.**

## 4.23 단어표 엔트리 0 을 빠뜨리고 있었다 — 「려팔카」

실기에서 「나는려팔카‥‥」 가 나왔다 (`image/오타.png`).

「려팔카」 의 코드를 원본 표로 되읽으면 `99 77 6d` = **ルキュ** 다. 주인공
(마왕) 이름이 미번역으로 남아 한글 폰트로 읽힌 것이다.

**원인.** 단어표를 `0x05c0a6` / 56엔트리로 잡았는데 실제로는 `0x05c0a4` /
**57엔트리**다. 인덱스 규칙이 `<EB>N -> [N-1]` 이므로 `<EB>00` 은 표 시작보다
하나 앞을 가리키고, 그 값 `0xc116` 이 「ルキュ」 다. `<EB><魔>`(= `eb 00`)를
쓰는 세그먼트가 여럿이라 넓게 번졌다.

고친 뒤 규칙은 **인덱스 = `<EB>` 값**이다. 프로브 검증과도 일치한다 —
`<EB><04>` = ファルコ 이고 지금 ファルコ 는 `WORDS[4]` 다.

세 곳을 함께 고쳐야 했다. 하나만 고치면 매핑이 어긋난다.

```
words.py   PTR_TABLE 0x05c0a6 -> 0x05c0a4, DATA -> 0x05c116, COUNT 56 -> 57
words.tag  <EB><n+1> -> <EB><n>
wordfix.py k = b - 1  -> k = b        (이걸 빼먹어 조사 검사가 78건 오검출했다)
```

「루큐」 = `73 7b` 2바이트로 칸 3바이트에 들어간다.

## 4.24 번역문에 남은 한자 이스케이프 9건

실기의 「魔획아바입니다」 를 추적했다. `#195` 다.

```
「<F4><魔><A1D><EB><03>입니다
  F4 00 = 魔     F5 1D = ?     <EB><03> = アーヴァ = 아바
```

`F5 1D` 을 렌더하니 **女** 였다. 즉 원문은 「魔女アーヴァでございます」 이고
「마녀 아바입니다」 가 맞다. 한자 이스케이프를 지우지 않고 남겨 두었더니
그 슬롯이 한글로 회수돼 「魔획」 으로 나왔다.

전수 조사하니 번역문에 뱅크/F4 이스케이프가 남은 세그먼트가 **9개**였다.
그중 5개가 이름표 `<FB>兵<F4><士><F8>` = 「兵士」 로, 화면에 일본어 한자가
그대로 보이고 있었다. 「병사」(`bd 3e`) 로 고쳤다.

남은 3개는 미식별 뱅크 한자다 — `#57`(`<C3B><C39><C3A>`), `#599`(`<BA9>`),
`#44`(`<EE><F4>` 제어열). 글리프 식별이 먼저다.

`trcheck` 의 「한글속한자」 검사는 이걸 못 잡았다. 그 검사는 한국어 **음절
사이**에 낀 한자를 보는데, 이 경우는 문장 맨 앞이거나 이름표 안이라 걸리지
않았다.

## 4.25 아이템표도 `<EE>` 가 포인터였다 — 공유 접미어를 깨뜨렸다

4.21.1 에서 장비 13개를 번역했다. 그때 `<EE>と<F1>` 을 「제어 코드 + 인자」
로 보고 바이트만 보존했다. **틀렸다.** 4.22 의 몬스터 표와 같은 구조다.

```
ee c4 f1  ->  포인터 0x04f1c4  ->  ソード
「ロング<EE>→0x4f1c4」 = ロング + ソード = ロングソード
```

포인터 넷이 있고, 셋은 **다른 엔트리의 중간**을 가리킨다.

| 포인터 | 원본 | 어디 |
|---|---|---|
| `0x4f1c4` | ソード | `#1223`(ショートソード) 오프셋 4 |
| `0x4f259` | スタッフ | `#1243` 시작 |
| `0x4f2d6` | アーマー | `#1261`(スチールアーマー) 오프셋 4 |
| `0x4f37a` | シールド | `#1283`(ハードシールド) 오프셋 4 |

내가 「ショートソード」 를 「숏소드」 로 짧게 쓰자 `0x4f1c4` 가 공백을
가리켰다. 「롱소드」 가 「롱」 만 되는 것이다. `#1291`「윙」·`#1292`「매직」 은
**내 작업 전부터 같은 이유로 깨져 있었다** (シールド 가 일본어일 때는
「윙シールド」 였다).

**해법 — 접두어를 정확히 4바이트로 맞춘다.** 공백을 **앞**에 두어 단어가
쪼개지지 않게 했다.

```
#1223  「␣␣숏소드」   20 20 + 숏(2B) = 4B, 「소드」가 오프셋 4
#1261  「␣스틸아머」   20 + 스틸(3B) = 4B, 「아머」가 오프셋 4
#1283  「␣␣하드실드」  20 20 + 하드(2B) = 4B, 「실드」가 오프셋 4
```

결과로 합성 이름이 전부 맞는다.

```
롱소드 · 브로드소드 · 그레이트소드 · 메이지지팡이
기사아머 · 홀리아머 · 탑실드 · 윙실드 · 매직실드 · 파워실드
```

**교훈.** `<EE>` 뒤는 세 곳에서 세 가지였다 — 워프 목록에서는 1바이트 인자,
몬스터 표와 아이템표에서는 2바이트 포인터. 「인자니까 보존하면 된다」 로
끝내면 안 되고 **가리키는 곳까지 확인해야** 한다. 바이트를 보존해도 대상이
바뀌면 깨진다.

## 4.26 미해결 — 아이템 창 커서 이동 시 화면 깨짐

사용자 보고: 아이템 창을 열고 화살표를 움직이면 화면이 깨진다. 원인을 찾지
못했다. 검사한 것과 결과:

- 고아 이스케이프 프리픽스: 아이템·마법·몬스터·단어표 전부 0건
  (`0x05c13a` 의 `f6 ff` 는 「담」=`f6 f6` 의 인덱스 바이트로 오탐이었다)
- 포인터 대상이 이스케이프 중간을 가리키는 경우: 0건
- 이름·설명 글리프 버퍼(VRAM `0x3000`~`0x4000`)는 64바이트 슬롯 64개

다음에 필요한 것은 **커서를 움직여 깨진 직후의 VRAM 덤프**다. 정상 상태
덤프와 비교하면 어느 영역이 넘치는지 바로 드러난다.

## 4.27 마법 목록은 패치된 대사 폰트를 쓰지 않는다 (4.20.1 정정)

`image/깨짐.png` — 마법 목록이 깨졌다. `image/깨짐2.png` — 화살표를 움직이면
**화면 전체가 붕괴**한다.

### 4.27.1 롬 데이터는 정상이다

먼저 데이터를 전수 확인했다. 전부 정상이다.

```
마법 이름표 0x4f3d3~0x4f45c  18엔트리 전부 한글
  파이어볼 아이스스톰 라이트닝 윈드블레이드 매직애로 데스 힐 큐어
  디스펠 실드 카운터매직 컨퓨전 패럴라이즈 포이즌블로 슬립 스트렝스 언데드
0xFF 종료자    사라진 것 0개 (아이템·마법 83개, 몬스터 56개 그대로)
고아 이스케이프  0건
포인터가 이스케이프 중간을 가리키는 경우  0건
공유 접미어 4개  전부 한글로 해결 (4.25)
```

### 4.27.2 결정적 증거 — 「フォーメーション」

화면 2행이 **깨끗한 일본어 가나** 「フォーメーション」 이다. 그 바이트는

```
8c 6b b0 92 b0 7c 6e 9d
```

이고 이 여덟 슬롯은 **전부 한글로 회수돼 있다.**

```
フ 8c -> 를   ォ 6b -> 용   ー b0 -> 말   メ 92 -> 들
シ 7c -> 럴   ョ 6e -> 력   ン 9d -> 인
```

패치된 대사 폰트로 그리면 「를용말들말럴력인」 이 나와야 한다. 그런데 가나가
나온다. **그러므로 이 창은 패치된 대사 폰트를 쓰지 않는다.**

그래서 4.20.1 의 「목록 창은 대사 폰트를 쓴다」 는 **범위를 좁혀야 한다.**
그 결론은 `SnesVideoRamitem.dmp` 로 확인한 **아이템 이름·설명 상자**에만
맞는다 (VRAM `0x3000` 의 64바이트가 대사 폰트와 바이트 일치했고 이스케이프도
해석됐다). **마법 목록은 다른 경로다.**

한글 이름이 깨지는 것도 이걸로 설명된다. 「파이어볼」 = `f5 97 22 85 f5 d2`
인데, 뱅크 이스케이프를 모르는 렌더러라면 `f5` 를 글리프 번호로 읽는다.
프리픽스를 잘못 처리하면 폭주해서 VRAM 을 넘어 쓸 수 있다 — `깨짐2.png` 의
전체 붕괴가 그 모습으로 보인다.

### 4.27.3 그 폰트를 못 찾았다

찾은 것과 결과.

| 찾은 방법 | 결과 |
|---|---|
| 롬 평문에서 원본 가나 글리프 사본 | 글리프마다 **1곳뿐**, 전부 패치됨 |
| 41엔트리 압축 그래픽 19,485 글리프 후보 | 최고 IoU 0.545 (불일치) |

즉 별개 서체도 아니고, 우리가 아는 압축 표에도 없다. 다른 압축 방식이거나
다른 표다.

**다음 입력이 필요하다 — 마법 목록이 떠 있는 순간의 VRAM 덤프.** 오프닝을
뚫은 것과 같은 방법이다 (4.18.5). 화면의 가나 글리프가 VRAM 어디에 있는지
찾고, 그 32바이트로 롬을 되짚으면 폰트 위치가 나온다. 전체 붕괴 직후의 덤프도
있으면 어느 영역이 넘치는지 바로 보인다.

### 4.27.4 완화책 (선택)

전체 붕괴는 위험하다. 원인을 찾기 전까지는 `patch_names` 를 끄면 마법 이름이
일본어로 돌아가지만 목록은 최소한 안정된다. 결정은 사람이 한다.

## 4.28 미해결 — 컷신 「復活節第１日」

`image/미번역.png` 의 두 줄을 못 찾았다.

```
復活節第１日            (붉은 글씨, 좌상)
わがうちに憂いは満ちぬ    (초록 글씨, 하단)
```

- 대사 인코딩으로 검색: 「わがうちに」 = `dc e6 b3 c1 c6` **없음**
- 満·復·第 는 단일바이트 표에 없다 (뱅크 한자)
- 오프닝식 스프라이트 스크립트: `0x90000`~`0xA0000` 전수 훑어 **오프닝 것
  하나뿐**이다 (`0x9ED6C`~`0x9EFF4`, 23줄)

오프닝과 같은 기법이 아니거나, 스크립트가 다른 뱅크에 있다. 이 화면의 VRAM
덤프가 있으면 4.18 과 같은 순서로 풀 수 있다.

## 4.29 화면 전체 붕괴의 원인 — 남는 칸을 0xFF 로 채운 것

`memory.dmp`(정상)와 `broken.dmp`(붕괴)를 비교해 찾았다.

### 4.29.1 증거

```
broken.dmp  0xc61b 부터 0xFF 가 9,886바이트 연속 (64바이트 이상 구간 11개, 합 11,452B)
memory.dmp  64바이트 이상 0xFF 연속 구간 0개
```

9.7KB 의 0xFF 가 어디서 왔나. 단어표 뒤가 `0x05c263`~`0x060000` = **0xFF 채움
15,773바이트**다 (words.py 주석). 거기까지 읽어 복사한 것이다.

### 4.29.2 원인

`patch_words` · `patch_names` 가 남는 칸을 **0xFF 로 채웠다.** 주석에
「종료자 뒤라 표시에 영향이 없다」 고 적어 뒀는데 **틀렸다.**

```
원본 표의 연속 0xFF 쌍   마법표 0개   단어표 0개
0xFF 패딩 후             마법표 31개  단어표 67개
```

표를 **0xFF 구분자로 순차 주사**하는 루틴이 그 쌍을 **빈 엔트리**로 읽는다.
그러면

1. 인덱스가 밀려 목록에 엉뚱한 이름이 나온다 (`image/깨짐.png`)
2. 밀린 채 계속 읽으면 표를 넘어 뒤쪽 0xFF 채움 구간에 들어간다
3. 종료자를 못 만나 폭주하며 VRAM 에 0xFF 를 9.7KB 쏟는다 (`image/깨짐2.png`)

**4.27.2 의 「フォーメーション」 도 이걸로 설명된다.** 인덱스가 밀려 손대지
않은 `0x4f466`(원본 일본어)을 읽은 것이다. 「이 창은 패치된 대사 폰트를 쓰지
않는다」 는 결론은 **틀렸다** — 폰트는 맞고 **읽는 자리가 밀렸을** 뿐이다.
그래서 4.27.3 의 「그 폰트를 못 찾았다」 도 없는 것을 찾은 셈이다.

### 4.29.3 고친 방법

남는 칸을 **공백(0x20)** 으로 채우고 종료자를 **원래 자리**에 둔다.

```
before  [한국어][0xFF][0xFF 0xFF ...]        연속 0xFF 발생, 종료자가 앞으로 당겨짐
after   [한국어][0x20 0x20 ...][0xFF]        0xFF 는 엔트리당 하나, 원본과 같은 자리
```

포인터로 읽으면 뒤에 공백만 붙고, 순차로 훑어도 경계가 원본과 같다.

**verify 도 함께 고쳐야 했다.** 처음엔 `rstrip(b'\x20')` 로 뒤 공백을 뗐는데,
**이스케이프의 인덱스 바이트가 0x20 일 수 있어서** 글자를 잘라 먹는다
(「국왕」「마왕」 이 그렇게 6건 오검출됐다). `apply` 가 쓰는 배치를 그대로
만들어 대조하는 방식으로 바꿨다.

### 4.29.4 검사 추가 — 역검증 [13]

표마다 연속 0xFF 쌍 수가 원본과 같은지 본다. 회귀 시험으로 확인했다 —
0xFF 패딩으로 되돌리면 `[13] 표 연속 0xFF: 원본과 다른 표 1개
[('단어표', 0, 67)]` 로 잡힌다.

**교훈.** 「종료자 뒤니까 상관없다」 는 추론이 틀렸다. 제자리 삽입에서는
**남는 칸에 무엇을 쓰는지도 데이터**다. 원본이 쓰지 않는 바이트 패턴을
만들어 내면, 그 패턴에 의미를 두는 루틴이 어딘가에 있다.

## 4.30 `is_story()` 가 장비 이름을 이야기 대사로 오분류했다

4.29 의 패딩을 고쳤는데도 **여전히 붕괴했다.** 다시 파서 찾은 것.

한글 롬에만 있는 큰 0xFF 구간이 하나 있다.

```
0x301100 부터 1,019.8KB 0xFF   (엔진 패치가 늘린 뱅크 F0 의 미사용 영역)
원본 롬에는 이 구간이 없다. 뱅크 F0 사용분은 0x300000~0x3010ff = 글리프 68개.
```

뱅크 F0 은 프리픽스 `5D`·`D5` 로만 닿는다. 그 프리픽스는 **패치한 대사·옵션
렌더러만 안다** (patch_engine 이 `$950F`·`$5CFA` 두 곳을 고친다). 메뉴·목록
렌더러는 모른다.

세그먼트를 파싱해 표 구간의 위험 프리픽스를 찾으니 **장비 이름에 하나 있었다.**

```
#1268  0x04f309  「홀리<EE>よ<F2>」   「홀」 = 5d 43
```

**원인은 `is_story()` 의 오분류다.** 그 판별자는 `<F2>`(초상화)를 이야기
대사의 표지로 본다. 그런데 장비 이름 「홀리`<EE>よ<F2>`」 의 `<F2>` 는
초상화가 아니라 **`<EE>` 뒤에 붙는 제어 바이트**다. 그래서 이 이름이 이야기
대사로 분류돼 `no_risky`(메뉴 안전 슬롯) 제약에서 빠졌고, 「홀」 이 `5D` 를
받았다. 그 이름을 그리는 아이템 창이 깨졌다.

같은 프리픽스를 쓰는 다른 네 곳(`#1099` 딴 · `#1101` 춤 · `#1165` 훗 ·
`#1169` 뀐)은 실제 NPC 대사라 문제가 없다.

**고친 방법.** 이름표가 소유한 구간(`trbatch.table_owned()`)은 **내용과
무관하게 메뉴 텍스트**로 본다.

```python
def is_story(addr, txt):
    if any(lo <= addr < hi for lo, hi in OWNED): return False
    return "<FB>" in txt or "<F2>" in txt or txt.lstrip().startswith("「")
```

배정이 804 -> 807 음절로 늘었고 예산 초과는 0건이다.

**검사 추가 — 역검증 [14].** 이름표 구간에 F4·5D·D5 프리픽스가 없는지 본다.
회귀 시험으로 확인했다 — `is_story` 를 되돌리면
`[14] 이름표 구간 위험 프리픽스: 1건 [('1268', '5d43')]` 으로 잡힌다.

**교훈.** 판별자를 **내용**으로만 만들면 제어 바이트가 우연히 표지와 겹칠 때
무너진다. 자리(주소)로 확정할 수 있는 것은 자리로 판별해야 한다. 4.15 에서
「주소로 갈랐다가 틀려서 내용으로 뒤집었다」 고 적었는데, 정답은 **둘을 함께**
쓰는 것이었다 — 표가 소유한 자리는 주소로, 그 밖은 내용으로.

## 4.31 필드 방향 표시 — UI 가 뱅크 한자를 직접 그린다

`image/동서남북.png` — 필드에서 이동 방향을 고르는 표시가 「형 조 숨 예」 로
나왔다. 그 코드를 되짚으면

```
형 = f5 4d = 東    조 = f5 4e = 西
숨 = f5 4f = 南    예 = f5 50 = 北
```

**`F5 4D`~`F5 50` = 東西南北 이고, 필드 UI 가 그 뱅크 한자를 직접 그린다.**
이름표도 대사도 거치지 않으므로 `no_risky`·`menu_safe` 로는 막히지 않는다.

`krcodec.UI_KANJI` 로 배정 풀에서 뺐다. 수용량 1257 -> 1253 자, 예산 초과는
0건이다. 글리프 넷이 원본과 바이트 일치하는 것을 확인했다.

**같은 종류가 더 있을 수 있다.** 화면에서 한자가 한글로 바뀐 것이 보이면 그
글자의 코드를 되짚어 `UI_KANJI` 에 넣으면 된다. 일반적인 탐지 방법은 없다 —
UI 코드가 인덱스를 하드코딩하므로 데이터만 봐서는 알 수 없다.

## 4.32 마법 목록은 **반각(8px) 폰트**다 — 한글이 들어갈 수 없다

4.29(패딩)·4.30(5D 유출)을 고쳐도 **여전히 붕괴했다** (붕괴 화면 2장). 원본 마왕 초반 목록 화면의 자간을 재서 원인을
찾았다.

```
「コンディション」 7글자가 게임 픽셀 55px  ->  자간 7.86px
잉크 세로 11px
```

**이 창의 폰트는 폭 8px 반각 가타카나다.** 대사 폰트(16x16)와 완전히 다른
서체다. 그래서

- 16x16 글리프로 찾던 지금까지의 모든 검색이 실패한 것이 설명된다
  (4.27.3 의 「롬 평문에도 압축 그래픽에도 없다」)
- **한글 음절은 8px 폭에 들어갈 수 없다.** 이 창에 한국어를 넣는 것은
  글리프를 새로 그려도 불가능에 가깝다
- 한국어 이름의 이스케이프 바이트(`f5 97` 등)가 반각 폰트의 인덱스 공간에
  들어가 폭주한다 — 그것이 전체 화면 붕괴다

**목록은 올바른 엔트리를 읽고 있다.** 붕괴 화면의 3행 MP 10, 5행 MP 20 이
원본(ファイアボール 10, ライトニング 20)과 일치한다. 읽는 자리는 맞고 **그리는
폰트가 한글을 표현할 수 없을** 뿐이다. 그래서 4.29.2 에서 「인덱스가 밀렸다」 고
본 것도 틀렸다.

반각 템플릿을 스크린샷에서 뽑아(`コンディション` 7자, 8x16) 롬을 1bpp 로
전수 대조했지만 못 찾았다 (최고 IoU 0.786). 압축돼 있거나 다른 배치다.

### 판단이 필요하다

마법 이름표는 두 곳에서 쓰인다.

| 창 | 폰트 | 한국어 |
|---|---|---|
| 아이템 이름·설명 상자 | 대사 폰트 16x16 | 정상 (4.20.1 에서 확인) |
| 마법·아이템 목록 | **반각 8px** | 불가 — 깨지고 붕괴한다 |

같은 문자열이므로 한쪽만 한국어로 둘 수 없다. 셋 중 하나다.

1. **이름표를 일본어로 되돌린다** — 목록이 정상·안정된다. 설명 상자의 마법
   이름도 일본어가 된다. 붕괴가 없어지므로 가장 안전하다.
2. 반각 폰트를 찾아 한글을 넣는다 — 8px 폭이라 음절 표현이 사실상 불가능하다.
3. 그대로 둔다 — 목록을 열면 화면이 붕괴한다. 배포할 수 없다.

## 4.33 반각 폰트 — VRAM 에는 있고 롬에서는 못 찾았다

4.32 에서 반각(8px) 폰트임을 확정한 뒤, 그 폰트를 찾아 한글을 넣는 길
(선택 2)을 시도했다.

### 4.33.1 「불가능」이라고 한 것은 틀렸다

8px 폭에 한글 음절이 안 들어간다고 했는데, **한 음절을 반각 두 칸에 걸쳐
그리는** 기법이 있다. 왼쪽 절반을 칸 N, 오른쪽 절반을 칸 N+1 에 넣는다.
그러면 「파이어볼」 4음절 = 8칸이고, 원문 「ファイアボール」 은 7칸이다.
칸이 하나 더 필요하지만 목록 행은 그보다 넓다. **원리적으로 가능하다.**

### 4.33.2 VRAM 에는 있다

`memory.dmp` 을 4bpp 8x8 타일 2048개로 전개해 시트로 렌더하니
(`scratchpad/sheet4.png`) 반각 라틴과 반각 가나가 보인다. 타일 256~320
부근이다. **이 덤프는 VRAM 이다** — 앞서 「VRAM 이 아니다」 라고 본 것은
16x16 으로만 찾아서 나온 오판이다.

### 4.33.3 롬에서는 못 찾았다

| 찾은 방법 | 결과 |
|---|---|
| VRAM 타일 32바이트(4bpp) 통째 검색 | 0건 |
| 1bpp 마스크 8바이트 검색 | 158건인데 전부 오탐 (밀집 데이터의 우연) |
| 연속 8타일 1bpp 64바이트 | `0x00F12B` 한 곳 — **단색 블록 오탐** |
| 연속 4타일 32바이트 | 같은 종류의 오탐 |

| 압축 블록의 4bpp 8x8 타일 통째 | 288건 — **엔트리 0** 이지만 폰트가 아니다 |

8바이트는 선택도가 낮아 밀집 구간에서 우연히 맞고, 길게 이어 붙이면 단색
채움 구간에만 걸린다.

엔트리 0 (블록 `0x1000c5` 등)은 VRAM 타일 256·288·320·352 에 올라가는데,
색 분포가 10·5·15·14·11·7 로 고르게 퍼진 **디더 패턴**이다. 목록 창 안쪽의
잔격자 배경이다 (붕괴 화면에서 보인다). 시트 렌더에서 그 격자를
반각 가나로 잘못 읽었다 — 회색 계조로 그리면 글자처럼 보인다.

**압축돼 있거나 코드가 만들어 내는 것으로 보인다.** 추측 검색은 여기서
끝낸다.

### 4.33.4 선택 2 를 하려면 넘어야 하는 것 둘

**하나 — 롬 위치.** 추측 검색은 한계에 왔다. 필요한 것은 **목록 창을 여는
순간의 DMA 로그** 또는 **VRAM 쓰기 로그**다. 소스 주소가 그대로 찍히므로
추측이 필요 없다. 4.1 에서 설명문 경로를 확정한 방법이 이것이다.

Mesen 에서
```
Debug -> Trace Logger   또는   Debug -> Event Viewer 의 DMA 표시
Debug -> Memory Tools 의 "Log VRAM writes"
```

**둘 — 같은 문자열이 두 폰트로 그려진다.** 마법 이름표는

```
아이템 이름·설명 상자  ->  대사 폰트 16x16   (이스케이프 해석함)
마법·아이템 목록       ->  반각 폰트 8px
```

두 렌더러가 **같은 바이트를 각자의 인덱스 공간으로** 읽는다. 그러므로 반각
폰트에 한글을 넣더라도 **대사 폰트의 한글과 같은 코드 자리**에 넣어야 양쪽이
맞는다. 반각 폰트는 글리프가 수백 개뿐이고 한국어는 807음절이므로, 겹칠 수
있는 것은 **단일바이트 142칸**뿐이다.

즉 선택 2 의 실제 모습은 이렇다.

1. 반각 폰트의 롬 위치를 찾는다 (DMA 로그)
2. 마법·장비 이름 음절을 **전부 단일바이트로 강제**한다
   (4.16.1 측정: 마법 이름 강제 = 대사 초과 86건 → 그만큼 문구를 고쳐야 한다)
3. 그 142칸에 대응하는 반각 글리프를 한글로 그린다 (두 칸 기법)
4. 목록의 칸 수가 늘어나므로 행 폭을 확인한다

작지 않은 작업이고 1번이 관문이다.

## 4.34 목록은 **바이트 하나 = 타일 하나**다 (타일맵으로 증명)

`vram_write.dmp`(목록 열림)와 `vram_write_close.dmp`(닫힘)를 비교했다. 차이는
`0xF100`~`0xF700` 뿐 — **타일맵**이다. 폰트는 이미 올라가 있었다.

타일맵 `0xF000`(32x32 워드)에서 목록 행을 읽으니 **타일 번호가 대사 폰트의
단일바이트 코드와 그대로 같다.**

```
행 7  122 157 131 104 124 110 157      = 7A 9D 83 68 7C 6E 9D = コ ン デ ィ シ ョ ン
행 9  140 107 176 146 176 124 110 157  = 8C 6B B0 92 B0 7C 6E 9D = フ ォ ー メ ー シ ョ ン
행11  140 103 114 113 142 176 153      = フ ァ イ ア ボ ー ル
행13  113 114 125 125 132 176 145      = ア イ ス ス ト ー ム
행15  151 114 132 134 157 120          = ラ イ ト ニ ン グ
행17  131 104 125 141 153              = デ ィ ス ペ ル
행24  153 119 109                      = ル キ ュ   (파티 이름)
숫자  48='0' 49='1' 50='2' 53='5'      (MP 10·15·20 과 일치)
```

**이것이 결정적이다.** 목록 렌더러는 문자열의 **바이트를 그대로 타일 번호로
써 넣는다.** 이스케이프를 해석하지 않는다 — 선택 필드 `<ED>出` 와 같은 방식이다
(4.15.3).

그래서 「파이어볼」 = `f5 97 22 85 f5 d2` 은 타일 `0xF5 0x97 0x22 0x85 0xF5 0xD2`
여섯 개로 갈린다. `0xF5` 는 폰트 범위를 벗어나므로 엉뚱한 타일이 나오고, 그
과정에서 폭주해 화면이 붕괴한다.

### 4.34.1 그래서 선택 2 의 요구가 확정됐다

**마법·장비 이름의 음절은 전부 단일바이트여야 한다.** 추정이 아니라 타일맵에서
읽은 사실이다. 그리고 코드 N 의 글리프가 목록 BG 의 폰트에 인덱스 N 으로
있어야 한다 — 즉 **회수한 단일바이트 142칸에 대응하는 반각 글리프를 한글로
그려야** 한다. 4.33.4 에서 추정한 경로가 그대로 맞았다.

### 4.34.2 남은 하나 — 그 폰트의 위치

VRAM 문자 베이스와 롬 소스를 아직 못 찾았다. 이번에 더 시도한 것:

| 방법 | 결과 |
|---|---|
| VRAM 전체를 2bpp/4bpp 타일 시트로 렌더 | 2bpp 시트에 「０１２３４」「５６７８９」 가 보인다 |
| `0x30`~`0x39` 가 숫자처럼 보이는 베이스 전수 스캔 (2bpp) | 후보 100개, 렌더해 보면 전부 조각 — 불일치 |

2bpp 인 것은 거의 확실한데(시트에 숫자가 보인다) 문자 베이스를 못 짚었다.
16px 높이 글리프가 두 타일에 걸쳐 있으면 8x8 단위 스캔이 어긋난다.

**필요한 것 — Mesen 의 Tile Viewer / Tilemap Viewer 한 장.**

```
Debug -> Tile Viewer     : 형식을 2bpp 로 두고 반각 가나 폰트가 보이는
                           VRAM 주소를 찾아 그 주소를 알려 주면 된다
Debug -> Tilemap Viewer  : 목록을 그리는 BG 의 "Tileset/Chr" 주소가 표시된다
```

그 주소 하나면 폰트 위치가 확정되고, 롬 소스는 그 바이트로 되짚으면 된다.

## 4.35 반각 폰트를 찾았다 — 그리고 packer 에 복사 명령을 넣었다

### 4.35.1 위치 — 압축 그래픽 엔트리 0

타일 뷰어 스크린샷의 타일을 VRAM 덤프와 대조해 정렬을
구했다 — **2bpp, 오프셋 0** (145개 일치). 즉 뷰어의 타일 번호 = VRAM 2bpp
타일 번호다.

숫자 행을 읽어 문자 베이스를 구했다.

```
타일 행 35 = 0123456789:;<=>?   ->  '0'(0x30) 이 2bpp 타일 560
문자 베이스 = 560 - 48 = 512 = VRAM 바이트 0x2000
검증: 행 36 첫 칸이 '@'(0x40) -> 512+64 = 576 ✓
```

**폰트는 8x8 2bpp, VRAM `0x2000` 부터 문자 코드순이다.**

그리고 그 자리는 **압축 그래픽 엔트리 0** 이다.

```
블록0 0x1000c5 -> 코드 0x00~0x3F   기호 + 0123456789:;<=>?
블록1 0x1003aa -> 코드 0x40~0x7F   @A~Z[\]^_ + アイウエオカキクケコサシスセソ
블록2 0x100659 -> 코드 0x80~0xBF   タチツ…ワン + あいうえお…
블록3 0x10095a -> 코드 0xC0~0xFF   たちつ…わん + 숫자
블록4~7 같은 범위의 사본, 블록8 은 0x00~0x3F 세 번째 사본
```

**4.33.3 에서 「엔트리 0 은 창 배경 격자다」 라고 한 것은 틀렸다.** 4bpp 로
읽어서 그렇게 보였다 — 4bpp 타일 256 의 바이트 주소가 2bpp 폰트 베이스와
같은 `0x2000` 이다. 2bpp 로 읽으면 폰트가 그대로 나온다.

### 4.35.2 packer 에 복사 명령을 넣었다

한글을 넣으려니 **원본을 그대로 재압축해도 칸을 넘었다.**

```
블록0 896 > 742   블록1 969 > 688   블록2 1061 > 770   블록3 902 > 810
```

4.17 에서 복사 명령($C03414)을 「복잡하고 잘못 쓰면 조용히 깨진다」며 일부러
뺐는데, 그 20~30% 가 여기서 발목을 잡았다.

**닿는 오프셋을 세어 보니 쓸 만했다.** `y` 는 128개뿐이고 **코덱이 쓰는 열 시작
위치와 정확히 같다** (`base+{0,1,0x10,0x11}`, base 는 0x20 배수). 즉 앞서
배출된 어느 열이든 역참조할 수 있다.

```
y = ((b & 3) << 8) | ROL(ASL(b & 0xFC))     b 256개 -> y 128개
c2 = ASL 의 캐리.  c2==1 이면 복사만(1바이트), c2==0 이면 마스크가 따라온다
복사는 비트 스트림을 쓰지 않는다 (전부 데이터 스트림에서 읽는다)
```

비용은 정확히 일치할 때 **1바이트**다 (리터럴 8바이트 대비). 다르면
`1 + 마스크 1 + 다른 바이트 수`.

결과.

```
원본 재압축   896 -> 745    969 -> 688   1061 -> 770   902 -> 813
              (원본 크기와 거의 같아졌다)
왕복 검증     1299/1299 블록
기존 패치     메뉴 폰트 블록도 824 -> 796, 770 -> 739 로 줄었다
```

### 4.35.3 한글이 들어간다

단일바이트 142칸에 8x8 한글을 그려 넣고 재압축했다.

```
블록0 칸 742  한글 16자 후 688  OK
블록1 칸 688  한글 37자 후 635  OK
블록2 칸 770  한글 58자 후 549  OK
블록3 칸 810  한글 31자 후 639  OK
```

**네 블록 전부 들어간다.** 8x8 한글의 가독성도 확인했다 — malgunbd 9pt 로
「파이어볼 아스톰 라닝디펠」이 읽힌다.

### 4.35.4 남은 작업

1. 마법·장비 이름 음절을 **전부 단일바이트로 강제** (4.16.1 측정: 대사 초과
   86건 → 그만큼 문구를 고쳐야 한다)
2. 반각 폰트 패처를 만든다 — `patch_menu` 와 같은 꼴이지만 2bpp 8x8,

3. 역검증에 반각 폰트 글리프 대조를 넣는다
4. 실기 확인

**선택 2 가 실현 가능해졌다.** 관문이던 폰트 위치와 압축 여유가 둘 다 풀렸다.

## 4.36 마법 목록 한글화 — 선택 2 완주 (1단계)

### 4.36.1 반각 폰트 패처 (`patch_hwfont.py`)

### 4.36.2 이름을 음역에서 한자어로 바꿨다

범위별 대사 초과(세그먼트/바이트)는

```
강제 없음  28자   11개 /  13B
마법만     66자   55개 /  76B
장비만     79자   74개 / 113B

```

마법만 먼저 했다. 실기에서 붕괴가 확인된 화면이고 평균 1.4바이트/건이다.

**그런데 음역이 비쌌다.** 「파이어볼」의 볼·「아이스스톰」의 톰처럼 음역은

흔한 음절을 쓴다.**

```
파이어볼 -> 불길    아이스스톰 -> 서리    라이트닝 -> 번개
윈드블레이드 -> 바람  매직애로 -> 마법화살   데스 -> 죽음
힐 -> 치유          큐어 -> 해독         디스펠 -> 해제
실드 -> 방어        카운터매직 -> 반사     컨퓨전 -> 혼란
패럴라이즈 -> 마비   포이즌블로 -> 독무     슬립 -> 수면
```

번역 성격이 바뀌는 결정이다. 음역이 원문에 가깝지만, 이 게임의 목록 창은
반각 폰트를 쓰고 그 폰트에 넣을 수 있는 것은 단일바이트 142칸뿐이므로
**한자어가 유일하게 성립하는 선택**이다.

## 4.37 장비·아이템 이름 한글화 (2단계) — `image/개선.png` 후속

실기에서 마법 목록은 나아졌으나 두 가지가 남았다는 보고를 받았다.

```
image/개선.png            팔코 아이템 창 — 이름이 「밝체늄」 꼴로 나온다
image/개선안됨_마왕초기.png  마왕 첫 메뉴 1행 깨짐 + 2행 일본어
```

### 4.37.1 원인은 폰트가 아니라 미완성이었다

먼저 「마왕 화면은 다른 폰트를 쓰는가」를 확인했다. 아니다.

- 압축 그래픽 41엔트리를 전부 풀어 엔트리 0 의 블록 내용과 대조 — **일치는
  엔트리 0 자신의 사본 9개뿐**이다. 다른 사본은 없다.
- 원본 롬 평문에서 반각 가나 타일(16바이트·64바이트)을 검색 — **0곳**.
- 패치 롬의 반각 폰트 코드 `0x8C` 는 한글이다 (원본 `31ce...` 아님).

그러면 마왕 화면 1행은 무엇인가. 「컨디션」 = `f72d f521 f72e` 이고, 이 여섯
바이트를 타일로 그리면 `ぷ 도 ぱ ！ ぷ 。` 가 된다. 화면에 `！` 와 `。` 가
그대로 보였다 — **번역문이 이스케이프를 쓰고 있었을 뿐**이다. 2행
「フォーメーション」(`0x04f466`)은 아예 미번역이었다.

즉 목록 창은 처음부터 하나였다. 남은 것은 그 창에 실리는 문자열을 전부
단일바이트로 만드는 일이다.

### 4.37.2 조립기 — `<EE>` 는 파라미터가 아니라 꼬리 점프다

아이템 이름표(`0x040260` 포인터 120개, 문자열 `0x04f1c0~0x04f470`)는 조립
언어로 쓰여 있다.

```
EE lo hi      ptr 로 꼬리 점프한다. 이 엔트리는 여기서 끝난다
F0 C4 lo hi   ptr 의 문자열을 끼워 넣고 계속 읽는다 (「＋１」 변형)
EB N          단어표 N 번을 끼워 넣는다
0xFF          끝
```

조립 결과 바이트가 타일 번호가 된다. **F5~F7 이스케이프는 조립기가 모른다** —
그래서 목록에서 두 글리프로 갈라진다.

여기서 한 번 크게 틀렸다. `<EE>` 를 지우고 이름을 리터럴로 풀어 썼다.
「장검」(2바이트)이 칸 6바이트에 들어가니 될 것 같았다. 조립기를 흉내 내
확인해 보니

```
[04] '장검     장검     장검     장검     장검     장검     장검     十１十１…'
```

**열한 엔트리는 0xFF 종료자가 아예 없다.** `<EE>` 가 끝을 표시한다. 리터럴로
바꾸자 남는 칸을 지나 다음 엔트리의 `F0 C4` 를 읽고 자기 자신을 다시
참조했다 — 실기라면 폭주한다.

```
0xFF 종료자가 없는 엔트리 11개
  0x04f1de 0x04f1fa 0x04f218 0x04f273 0x04f303 0x04f309
  0x04f395 0x04f3b0 0x04f3b8 0x04f3c0  (+ 0x04f340 은 뒤 엔트리의 0xFF 를 쓴다)
```

0xFF 를 새로 써 넣는 것도 안 된다. 원본에 없던 자리에 종료자가 생기면 표를
순차로 훑는 루틴이 엔트리를 하나 더 세어 인덱스가 밀린다 — 4.29 의 붕괴와
같은 부류다.

그래서 `<EE>` 를 되살렸다. 대신 **가리키는 곳을 옮겼다.** 공유 접미어는
엔트리 안의 고정 오프셋(+4)에 있었는데, 접미어 자체를 짧게 바꾸면 그
오프셋이 안 맞는다. 포인터 두 바이트는 우리가 다시 쓰는 엔트리 안에 있으니
그냥 새 위치를 적으면 된다.

```
0x04f1c4 「ソード」  ->  0x04f1c1 「검」    ([00] 「소검」 의 둘째 바이트)
0x04f2d6 「アーマー」 ->  0x04f2d4 「갑주」  ([28] 「강철갑주」 의 셋째 바이트)
0x04f37a 「シールド」 ->  0x04f378 「실드」  ([44] 「하드실드」 의 셋째 바이트)
```

이 참조는 그 셋뿐임을 전수 확인했다 (`<EE>`·`F0 C4` 대상 17곳 중 오프셋이
0 이 아닌 것은 셋).

### 4.37.3 음역을 버려야 값이 맞는다

강제해야 할 음절을 세 보면 처음엔 32자였고 대사 초과가 **116개/282바이트**로
튀었다. 단일바이트 칸이 141 뿐인데 강제가 110자면 대사에 남는 것이 31칸이다.

비용은 음절 빈도로 결정된다. 강제되지 않은 음절 중 마지막으로 칸을 받는
빈도가 **51** 이므로, 빈도 F 인 음절을 강제하는 값은 대략 `51 - F` 회의
출현이 2바이트로 밀리는 것이다.

```
숏 1   롱 3   엑 1   칼 1   팡 1   플 1   틸 1   슬 5   메 7   머 10
브 17  문 17  태 16  탈 3   트 29  형 28  실 36  장 39  날 39
```

빈도 1 짜리 여섯 개(숏·엑·칼·플·틸·팡)가 전체 비용의 70% 였다. 그래서 이름을
다시 지었다. 후보를 실제로 빌드해 재고 골랐다.

```
후보                    강제  대사 초과
A 음역 유지             105   93개/282B
B 검·갑주·실드 계열       97   36개/54B
C B + 사슬/강철/문장      99   51개/89B   <- 채택
D C + 엑스칼리버         100   62개/115B
```

최종 이름. 왼쪽이 원문, 오른쪽이 채택안이다.

```
ショートソード -> 소검      ロングソード   -> 장검
ブロードソード -> 대검      グレートソード -> 거대검
ドラゴンセイバー -> 용세이버  オーガスレイヤー -> 오거살해자
ムラマサ     -> 무라마사    エクスカリバー -> 신검
スタッフ     -> 지팡이      メイジスタッフ -> 마도지팡이
スラフニール  -> 스라니르
チェインメイル -> 고리갑주    プレートメイル -> 중장갑주
スチールアーマー -> 강철갑주  シルバーメイル -> 은갑주
ドラゴンメイル -> 용갑주     ナイトアーマー -> 기사갑주
ホーリーアーマー -> 사제갑주  ローブ       -> 법의
シルクローブ  -> 명주법의    メタルガード  -> 방호가드
ナイトエンブレム -> 기사문장  バックラー    -> 버클러
ハードシールド -> 하드실드    タワーシールド -> 대형실드
ウイングシールド -> 날개실드  マジックシールド -> 마법실드
パワーシールド -> 강력실드    シャイニングウォール -> 결계
コンディション -> 상태       フォーメーション -> 대형
ダークゲート  -> 마계문 (단어표 [0x17])
```

「엑스칼리버」는 엑·칼 두 음절이 빈도 1 이라 대사 13개를 더 넘긴다.
「신검」으로 했다. 「다크게이트」도 크·트 때문에 대사 15개를 넘겨
「마계문」으로 했다 — 마법표 `[0x11]` 이 `<EB><17>` 로 이 엔트리를 참조하므로
목록에 그대로 실린다.

되돌리고 싶으면 값은 위 표에 적힌 그대로다. 이름을 고르는 것은 사람 몫이다.

### 4.37.4 ＋(0x2B) 를 회수하고 있었다

강화 변형은 `F0 C4 <ptr> 2B 31` = 「이름＋１」 로 조립된다. `0x2B` 는 판독문에
`十` 로 보이지만 글리프는 **＋** 이고, 목록 창이 그 바이트를 타일로 그린다.
회수 대상에 들어가 있어서 「소검＋１」 이 **「소검하１」** 로 나왔다 (43곳).

`krcodec.KEEP` 에 넣었다. 東西南北(4.31)·♥ 과 같은 부류다. 단일바이트가
142 -> 141 로 줄어 대사 하나가 더 넘쳤다.

찾은 방법을 적어 둔다 — **표 구간에서 우리가 쓰지 않은(원본과 같은) 바이트
중 지금 한글 코드인 것**을 전부 세었다. 13개가 나왔고 12개는 포인터의 하위
바이트(조립기가 먹으므로 무해)였고 하나가 `0x2B` 였다.

### 4.37.5 `<ED>` 필드는 세그먼트 경계를 넘는다

「소울 사용」(#60)이 한 바이트 넘쳤다. 이 문구는 `<ED>出 … <ED>` 필드 안이
아니라 **세그먼트 맨 앞**에 있다 — 필드를 연 `<ED>出` 이 앞 세그먼트(#59)의
끝에 있다. 그래서 단일바이트 강제에서 빠져 「울」이 2바이트가 되어 있었다.

선두가 필드인지는 첫 `<ED>` 태그로 가른다.

```
<ED>出 로 열리면   그 앞은 질문문이다      #1 「괜찮습니까？」
<ED>界 로 닫히면   앞 세그먼트가 연 필드다  #60 「소울 사용  」
```

전체에서 이 모양은 #60 하나뿐이다.

### 4.37.6 대사 58건 + 엔딩 1조각

초과를 문구로 흡수했다. 이번에도 자동 치환은 쓰지 않았다.

```
1차 48건   여기선->여기서 / 걱정하지 말고->걱정 말고 / 지녔을->지닌
           차지 않는다->모자란다 / 지나지 않는다->불과하다 …
2차  9건   ＋ 보호로 한 칸이 줄어 생긴 것
3차  1건   #617
엔딩 #98   가운데맞춤 앞 공백 한 칸
```

한 가지 배웠다. **경계에 있는 음절의 출현을 지우는 수정은 되돌아온다.**
「당신이 이 여정에서」에서 당·신을 지우자 「당」이 빈도 경계 아래로 떨어져
초과 6건이 새로 생겼다. 공백·줄임표를 줄이는 수정은 그 되먹임이 없다.

마지막 한 칸은 문구가 아니라 이름으로 벌었다 — 「사슬갑주」를 「고리갑주」로
바꿔 「슬」(빈도 5)을 놓아 주었다. 그 한 칸이 「전」(빈도 50)에게 갔고 초과
9건이 한 번에 사라졌다.

### 4.37.7 반각 폰트 글꼴을 바꿨다

8x8 에 한글을 넣으면 ㅇ·ㅎ 의 속공간이 메워진다. 후보 8개를 실제 이름으로
나란히 그려 골랐다.

```
malgunbd 9px/100   무라마사->「부라마사」  오거->「모거」  용->「봄」
malgun   9px/60    ㄷ 은 살지만 ㅇ 이 여전히 막힌다
NanumGothic 9px/60 무라마사·독무·죽음·용세이버·마계문·결계 전부 제대로 읽힌다  <- 채택
```

**남는 한계: 받침 ㅇ 은 두 픽셀 높이라 속공간을 낼 수 없다.** 「방어」가
「밤어」, 「강화」가 「감화」, 「상태」가 「삼태」로 보인다. 3x3 이상 채워진
덩어리의 가운데를 뚫는 후처리를 시험했는데 그 덩어리가 2행뿐이라 걸리는
곳이 없었다. 제대로 고치려면 8x8 자모를 손으로 그려 조합해야 한다.

압축은 여유가 있다 (블록별 710/742 · 645/688 · 610/770 · 679/810).

## 4.38 창 장식 칸과 용사 쪽 메뉴 — `image/확인.png` 후속

마왕 첫 메뉴가 한글로 나왔다는 확인을 받았다. 남은 보고 두 가지.

```
「용사 메뉴도 필히 수정되어야 할겁니다」
「다이얼로그 창 귀퉁이에 세두, 남전이라고 보이는 부분도 수정되어야 할거 같아요」
```

### 4.38.1 목록 표 구간의 시작을 잘못 잡았다

`LIST_TBL` 을 `0x04f1c0` 부터로 잡았는데 **그 앞에도 목록에 실리는 것이
있었다.**

```
0x04f137~0x04f17e   마법 목록 18행 — 「♥<EE>포인터」 (♥ = 커서 표시)
0x04f184            カオスオーブ      -> 카오스보주
0x04f18c            マジックオーブ    -> 마법보주
0x04f196            きぼうのひかり    -> 희망의 빛
0x04f19f            エセルのかたみ    -> 에셀유품
0x04f1a8            コンディション    -> 상태     <- 용사 쪽
0x04f1b7            フォーメーション  -> 대형     <- 용사 쪽
```

**「컨디션」「진형」이 두 벌이다.** 마왕 쪽은 `0x04f45c`·`0x04f466`(4.37 에서
고쳤다), 용사 쪽은 `0x04f1a8`·`0x04f1b7` 이다. 뒤쪽만 고쳐서 용사 메뉴가
그대로 깨져 있었다.

구간을 `0x04f137` 부터로 넓히고 이름을 다시 지었다.

```
컨디션 -> 상태      (컨·디·션 3자 해방, 태는 이미 강제)
진형   -> 대형      (진 해방, 형은 이미 강제)
카오스오브 -> 카오스보주   매직오브 -> 마법보주   (매·직·브 3자 해방)
```

「오브」를 「보주」로 바꾼 것은 보·주가 이미 단일바이트라서다 (빈도 100·117).
「브」는 빈도 14 라 강제하면 값이 비쌌다. 뜻도 보주(寶珠)가 정확하다.

강제 음절 113 -> 104자, 대사 초과 78개 -> 14개가 되었다.

### 4.38.2 반각 폰트에는 한자가 없다 — 그 자리는 창 장식이다

이게 「세두·남전」의 정체다.

목록 창은 8x8 반각 폰트를 쓴다. 반각에 한자를 넣을 수는 없으니, **단일바이트
한자 코드 31개의 8x8 칸은 다른 그림**이다. 원본 시트를 뽑아 보면 창 테두리
레일(`0x5B`~`0x65`)·모서리 장식·게이지다.

타일맵으로 확인했다 (`item2` 덤프, 문자 베이스 `0x200`).

```
행14  0x229 0x22a 0x22b 0x22c   = 코드 29 2A 2B 2C    4x2 창 장식
행15  0x239 0x23a 0x23b 0x23c   = 코드 39 3A 3B 3C
행18  0x22f 0x22e 0x22d         = 코드 2F 2E 2D       3x2 (좌우 반전)
행19  0x23f 0x23e 0x23d         = 코드 3F 3E 3D
```

여기에 한글을 쓰면 창 귀퉁이에 글자가 나온다. 실제로 배정을 되짚으니

```
0xDE (中) -> 「당」    0xDF (物) -> 「전」    -> 창 모서리에 「당전」
0x70 (殺) -> 「두」    0x9E (結) -> 「감」    0x9F (知) -> 「찌」
```

**「남전」은 「당전」이었다.** 받침 ㅇ 이 8x8 에서 ㅁ 으로 보이는 것(4.37.7)과
겹쳐 「남전」으로 읽힌 것이다.

### 4.38.3 회수를 막을 필요는 없다 — 나누면 된다

여기서 東西南北(4.31)·＋(4.37.4) 처럼 `KEEP` 에 넣고 싶어진다. 그러면
단일바이트가 141 -> 110 으로 줄어 예산이 무너진다.

그럴 필요가 없다. **대사 폰트(16x16)에서는 이 코드가 정상 글리프 자리다.**
깨지는 것은 8x8 쪽뿐이다. 그래서 음절을 나눈다.

```
대사에만 나오는 음절   -> 이 코드를 줘도 된다 (16x16 만 덮는다)
목록·필드에 나오는 음절 -> 주면 안 된다 (8x8 이 장식이라 못 덮는다)
```

구현은 두 줄이다.

```python
# krcodec.allocate — 장식 코드를 단일바이트 풀 맨 뒤로 민다.
# ordered 는 force 가 앞이므로 목록·필드 음절은 이 코드를 받지 않는다.
_ui = hw_ui()
single = ([c for c in reclaimable() if c not in _ui]
          + [c for c in reclaimable() if c in _ui])

# patch_hwfont.single_codes — 이 폰트에서는 그 코드를 빼고 쓴다.
return {c[0]: ch for ch, c in codes.items() if len(c) == 1 and c[0] not in ui}
```

`force` 는 「바이트 하나 = 타일 하나로 그려지는 자리」의 음절 집합이므로 그것만
피하면 된다. 목록·필드에 쓸 수 있는 칸은 141 - 31 = **110칸**이고 지금 강제가
104자다 (여유 6칸).

장식 코드를 식별하는 규칙은 표에서 나온다 — **원문이 한자인 단일바이트
코드**가 그것이다. 반각 폰트에 한자가 없다는 사실이 그대로 판별식이 된다.

```
22 生  23 兵  24 出  25 時  26 手  27 力  2A 行  2C 界  2D 腕  2F 気
3A 石  3B 来  3C 者  3D 何  3E 思  40 輪  5B 前  5C 聞  5E 大  5F 方
60 世  61 命  62 言  63 死  64 子  65 今  70 殺  9E 結  9F 知  DE 中  DF 物
```

### 4.38.4 블록0 은 손대지 않는다

장식 코드를 빼자 **블록0(코드 `0x00`~`0x3F`)에 쓸 한글이 하나도 남지 않았다.**
`0x20`~`0x3F` 는 전부 `KEEP`(공백·！·괄호·＋·．·숫자·？) 아니면 장식이다.

그런데 빈손으로 재압축만 해도 칸을 넘겼다 (**745 > 742**). 우리 packer 가
원본보다 나쁜 블록이 있다는 뜻이다. 쓸 것이 없으면 두는 것이 맞다 —
`n == 0` 이면 건너뛴다.

나머지 블록은 여유가 늘었다 (636/688 · 589/770 · 670/810).

## 4.39 몬스터 이름표 — 구조는 풀렸고, 벽은 칸이다

「표 구조 미해결」로 적어 두었던 것을 풀었다. 그런데 풀고 보니 **막는 것은
구조가 아니라 단일바이트 칸**이었다.

### 4.39.1 겹친 게 아니라 읽는 법을 몰랐다

4.10 은 이 표를 「엔트리가 서로 겹쳐 읽힌다 / 절반만 가능」으로 봤다. 틀렸다.
아이템표(4.37)와 같은 조립 언어를 쓴다.

```
EE lo hi      ptr 로 꼬리 점프한다. **이 엔트리는 여기서 끝난다**
F0 C4 lo hi   ptr 의 문자열을 끼워 넣고 계속 읽는다
EB N          단어표 N 번을 끼워 넣는다
0xFF          끝
```

핵심은 **`<EE>` 도 종료자**라는 것이다. 그래서 엔트리 사이에 `0xFF` 가 없는
곳이 많고, `0xFF` 로만 자르면 여러 엔트리가 하나로 뭉쳐 보인다. 그 뭉친
덩어리를 보고 「겹쳐 읽힌다」고 판단했던 것이다.

제대로 자르면 **107 엔트리**다 (`0xFF` 로만 자르면 72개).

```
0x04f691  ジャイアント + EE->0x04f68c(バット)   = ジャイアントバット
0x04f69b  Ｐ           + EE->0x04f68c          = Ｐバット
0x04f708  F0C4->0x04f701(コボルド) + Ｋ         = コボルドＫ
```

「F7 비글리프 참조 5개」(4.10)도 같은 오해였다. `f0c401f74b` 를 순차로 훑으면
`f7 4b` 가 F7 이스케이프로 보이는데, 실제로는 `F0 C4` 의 포인터 하이바이트와
그 뒤 글자다. 그래서 「몬스터 이름에 뱅크 이스케이프 14곳」도 **0곳**이다.

`montbl.py` 가 파서다. `python3 montbl.py <rom>` 으로 107개를 찍는다.

### 4.39.2 이 표도 타일 직접이다

원본이 쓰는 2바이트 이스케이프 수를 표별로 세면 갈린다.

| 표 | 렌더러 | 원본의 뱅크 이스케이프 |
|---|---|---|
| 아이템·장비·마법표 | 타일 직접 (확인됨) | **0곳** |
| 몬스터·화자 이름표 | ? | **0곳** |
| 단어표 | 대사 렌더러 | 47곳 |
| 메인 대사 | 대사 렌더러 | 3,432곳 |

107개 이름에 한 곳도 없다. 대사 렌더러를 쓴다면 한자가 섞였을 것이다 —
단어표는 57엔트리에 47곳을 쓴다. 타일 직접으로 본다. **다만 이건 정황이고
실기 한 장이면 확정된다** (4.39.4).

### 4.39.3 벽 — 필요한 칸 41, 있는 칸 6

타일 직접이면 이름 음절이 전부 단일바이트여야 하고, 창 장식 칸(4.38)도
피해야 한다. 쓸 수 있는 코드는 **110개**이고 **지금 110개가 전부 차 있다**
(강제 104 + 빈도로 들어온 6).

부품 55개를 한국어로 옮기면 새 음절이 얼마나 필요한지 셌다.

```
자연스러운 안   50자   골구군금급남냥녀뇽늑달랑렘롱린메목박밤뱀베병볼부블색
                       시악액여왕위인적점좀쥐즈체케코크키탈파팽혈홉회흡
팔레트 우선 안  41자   (지옥개·이리·마신·죽은자·거상·거대·독·지옥·사람·
                       강철·은·돌·불·수장 등 23개 부품은 공짜)
```

**41자가 필요한데 6칸뿐이다.**

늘릴 수 있는 최대치도 재 봤다. 표 안에서 **한 이름에만 쓰이고 빈도가
경계(51) 아래인** 음절이 24자다 — 그 이름들을 전부 팔레트 안의 낱말로
바꾸면 24칸을 되찾는다.


### 4.39.4 그래서 다음은 실기 한 장이다

두 가지를 가르면 값이 달라진다.

1. **몬스터 이름을 그리는 것이 타일 직접인가** — 전투 화면 한 장이면 된다.
   이미 번역된 것이 여럿이고(Ｇ배트·오크Ｋ·코볼드·해골·골렘·Ｍ드래곤) 전부
   2바이트 음절을 품고 있다. 한글로 읽히면 대사 렌더러이고 **강제가 아예
   필요 없다**. 깨져 보이면 타일 직접이고 위 벽이 그대로다.
2. **화자 이름표(0x04f87a~ 하녀·여자·도적·노인·노파·시체·두목)도 같은가** —
   이 아홉은 이미 번역돼 있고 2바이트다. NPC 이름표가 뜨는 화면 한 장.
   여기가 대사 렌더러면 필요한 41자에서 9자가 빠진다.

정황(2바이트 이스케이프 0곳)은 타일 직접 쪽이지만, 4.27 에서 정황만 보고
「폰트를 못 찾았다」로 결론했다가 틀린 적이 있다. 실기로 가른다.

### 4.40.1 몬스터 이름은 타일 직접이다 — 4.39 의 정황이 맞았다

전투 화면의 이름 상자가 「자며라ᄂ맴보·유·재」 로 나왔다. 4.39.3 의 벽이

### 4.40.2 필드를 여는 것이 `<ED>出` 만이 아니다

전투 명령 넉 줄 중 첫 줄만 깨졌다.

```
<ED>界… <ED> <FD><09><12>공격하기   <ED>界…   <- 깨짐
        <ED>出마법 사용  <ED>界…             <- 정상
        <ED>出아무것도 안해<ED>界…            <- 정상
        <ED>出모두 도망  <ED>界…             <- 정상
```

첫 칸은 **`<ED>공백`** 이 연다. `<ED>出(.*?)<ED>` 만 보던 규칙이 이것을
놓쳐 「공격」이 2바이트로 남았다 (`f5 7d` `f5 c5`).

여는 쪽으로 규칙을 넓히면 `<ED>` 가 본문에 섞인 이야기 대사(#717~#725)까지
딸려 온다. **닫는 쪽으로 잡는 것이 안전하다 — `<ED>界` 로 닫히는 구간이
필드다.** `<ED>界` 는 칸 위치를 지정하는 명령이라 필드 끝에만 온다.

세 규칙을 합쳐 쓴다: `<ED>出…<ED>` · `<ED>界` 로 닫히는 구간 · 선두 구간
(앞 세그먼트가 연 필드, 4.37.5). 전부 `<ED>出` 이 있는 세그먼트로 한정한다.

**나머지 세 줄은 멀쩡했다.** 「마루것노 안해」로 보이는 것은 8x8 에서
ㅇ→ㅁ, ㄷ→ㄴ 으로 읽히는 4.37.7 의 한계다 (아무것도 → 마루것노).

### 4.40.3 「조심해魔」 — `<E9>` 의 파라미터를 글자로 읽었다

`#189` 의 꼬리다.

```
원본  … 조심해 <EA> <E9>21 <1E> <E9>07 | 5d 00
번역  … 조심해 <EA> <E9>21 <1E> <E9>07 | f5 8c 00     <- 1바이트 늘었다
```

`<E9>xx` 는 **2바이트 파라미터**를 받는다. 그 파라미터가 `5d 00` 인데
추출기가 `5d` 를 글리프로 읽어 판독문에 `備<魔>` 로 내보냈고, 인코더는
備 를 `f5 8c` 로 다시 썼다. **0x5D 는 엔진 패치가 이스케이프 프리픽스로
가져가서 단일바이트로 쓸 수 없기 때문이다.** 파라미터가 3바이트가 되자
렌더러는 `f5 8c` 를 파라미터로 먹고 남은 `00` 을 글리프 0(魔)으로 그렸다.

번역문의 꼬리를 `<E9><07><5D><00>` 으로 바꿔 바이트를 원본과 같게 했다.
파라미터 자리의 `5d` 는 글리프 경로를 타지 않으므로 프리픽스로 오해되지
않는다.

전수 조사했다. 0x5D/0xD5 가 글리프 자리에 있는 곳은 번역된 세그먼트에서
50곳인데, 그중 **뒤에 결합 바이트(00/01/02)가 오는 것은 두 곳**뿐이고
번역된 것은 `#189` 하나다. 나머지는 본문 안이라 2바이트 이스케이프로
다시 써도 글리프가 보존된다 (1바이트씩 더 쓸 뿐이고 예산에 이미 반영돼 있다).

**교훈은 4.19 와 같다** — 「일본어가 남았다」로 보이는 것이 제어 인자인
경우가 있다. 이번엔 그 인자가 **엔진 패치가 뺏은 코드**여서 드러났다.

### 4.40.4 컷신 「復活節第１日」 — 위치 확정

오프닝과 달리 **스프라이트가 아니라 BG 타일맵**이고, 글자는 16x16(2x2 타일)다.

```
VRAM 타일맵 0x7800
  행16-17  c0 c1 c2 c3 c4 c5 c6 c7 00 01 c8 c9   = 復活節第１日 (6자 x 2타일)
  행23-24  86 87 8c 8d 22 23 46 47 60 61 ca cb
           20 21 66 67 cc cd 46 47 62 63          = わがうちに憂いは満ちぬ (11자)
```

**글꼴** — 문자 베이스 VRAM `0x6000`, **4bpp**. 후보 32개(베이스 16 x 2bpp/4bpp)를
나란히 그려 골랐다. `c0`=復 `c2`=活 `c4`=節 `c6`=第 `c8`=日 `86`=わ 로 맞는다.
롬에서는 **압축 그래픽 엔트리 28 의 블록 6~17** 이 VRAM `0x4000`~`0x7000` 에
올라간다 (블록14 `0x1882d4` 가 `0x6000`).

**본문** — 타일맵을 흘려 넣는 스크립트가 롬 평문 `0x0f0c00` 부터 있다.

```
ff ff <w16> <w16>   블록 머리
fe ff <n16>         다음 타일부터 n개를 1씩 증가시키며 쓴다
<tile16>            리터럴 타일맵 워드
```

확인:

```
0x0f0c0b  ff ff 00 02 00 00  fe ff 08 00  c0 20  00 20 01 20 c8 20 c9 20
          -> c0..c7 (8개 증가) + 00 01 c8 c9  = 행16 의 12타일 그대로
0x0f0c30  ff ff bc 00 8a 02  86 20 87 20 8c 20 …  = 행23 의 22타일 그대로
```

같은 줄이 뒤에서 되풀이되는데 `00 01` 자리만 `02 03` 으로 바뀐다 —
**第１日 / 第２日 …** 이다.

남은 일은 (1) 엔트리 28 에 한글 16x16 을 그려 넣고 (2) 타일맵 워드를 다시
쓰는 것이다. 주의할 것은 엔트리 28 이 다른 컷신과 공유하는 한자 시트라는
점이다 — 이 화면에서 쓰지 않는 타일을 덮으면 다른 화면이 깨질 수 있다.
