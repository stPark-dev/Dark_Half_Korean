# Dark Half (SNES) 한글화 — 진행 상황

새 세션에서 이 파일부터 읽으면 이어서 작업할 수 있습니다.

- **대상**: `Dark Half (Japan).sfc` — SNES HiROM, 3MB, MD5 `55108013f875db3b39da04b8f58489ab`
- **작업 폴더**: `darkhalf-kr/`
- **목표**: 전체 한글화. 메뉴 UI + 마법/아이템 설명문 완료, 한자 553자 식별 완료(대사 판독률 98.7%)

## 1. 확정된 기술 사실

### 1.1 인코딩 (relative search + 폰트 렌더로 검증)

1바이트 코드. 가나가 반각 가타카나 Shift-JIS 코드와 같은 자리에 배치돼 있고, 글리프만 히라가나로 렌더됩니다.

| 코드 | 내용 |
|---|---|
| `0x20` | 공백 |
| `0x21` `0x3F` | `！` `？` |
| `0x30-0x39` | `０`~`９` |
| `0x41-0x5A` | `Ａ`~`Ｚ` |
| `0xA1-0xA6` | `。` `「` `」` `、` `‥` `を` |
| `0xA7-0xAF` | 작은 가나 `ぁぃぅぇぉゃゅょっ` |
| `0xB0` | 장음 `ー` |
| `0xB1-0xDD` | `あ` ~ `ん` (45자 연속) |
| 그 외 `0x22-0xA0` 산재 | 단일바이트 한자·가타카나 |

전체 테이블은 `darkhalf.tbl`, 폰트 시트는 `font_single.png`.

### 1.2 제어 코드

| 코드 | 의미 | 근거 |
|---|---|---|
| `0xFF` | **메시지 종료** | 포인터 테이블 목적지 직전이 58/58 일치 |
| `0x01` | **탁점** (앞 글자에 결합) | `ト`+01=`ド`, `ホ`+01=`ボ` → "オレはドロボー" 복원 |
| `0xE3` | 개행 | |
| `0xF5 xx` `0xF6 xx` `0xF7 xx` | 한자 뱅크 0/1/2 | `F505`=人 `F512`=王 `F50E`=下 |
| `0xF7 xx` | 한자 뱅크 2 | 원문 대사에서 171회 사용 확인 |
| `0xEB xx` `0xE7` `0x06` `0x1C` 등 | 미해독 | 고정쌍 관측: `F0 C4`(92%) `F2 01`(91%) `1C 06`(81%) `FB EB`(67%) |

**`0x00`~`0x05`는 제어 코드가 아니라 실제 글리프입니다.** `00=魔` `01=士` `02=見` `03=ヴ`
`04=◀` `05=▶`. 「聖騎士」가 `F50A F50B 01`, 「発見」이 `F531 02` 로 쓰입니다.
`0x01`만 예외로, 앞 글자가 탁음 가능한 가나면 탁점으로 결합하고 아니면 `士` 글리프가 됩니다.
이걸 제어 코드로 버리면 문맥이 잘려 보입니다 (`kanjictx.py` 의 렌더러가 이 규칙을 구현).

**중요**: 탁음을 항상 `기본+0x01`로 쓰므로 완성형 탁음 슬롯(`0x02-0x1F`, `0xE6-0xFF`)의 **코드값이 통째로 비어 제어 코드로 재활용**되고 있습니다. 본문에 `ざ`(0xEB)가 1426회 나오는 식의 이상한 통계는 전부 이것 때문입니다.

### 1.2.1 글리프 주소 지정 = 10비트 평면 인덱스 (코드 확정)

`0x005c96` 글리프 페치 루프:

```
a5 00              LDA $00          ; 글리프 인덱스
0a 0a 0a 0a 0a 0a  ASL x6           ; x64
aa                 TAX
bf 00 00 ef        LDA $EF0000,X    ; 폰트 데이터
```

`0x009544` DMA 큐 설정도 동일하게 소스 뱅크 `$EF` 고정, 오프셋 `인덱스*64`,
전송 크기 `#$0040`. 단일바이트 인덱스 계산은 `0x009530` (SBC/CMP 로 범위 보정).

**이스케이프 판별 루틴 `$5CFA` (텍스트 바이트 -> 글리프 인덱스)**

```
005cfa  c9 f8 / b0 0e     CMP #$F8, BCS -> 제어 코드 경로
005cfe  c9 f4 / 90 0a     CMP #$F4, BCC -> 단일바이트 경로
                          ; 즉 $F4 <= A <= $F7 이 이스케이프
005d02  29 03             AND #$03      ; 하위 2비트만 인덱스 상위 바이트로
005d04  85 01
005d06  20 f1 5c          JSR $5CF1     ; 다음 바이트 읽기
005d09  85 00             STA $00
```

`$5CF1` 은 `LDA [$28]` + 포인터 증가 = '다음 텍스트 바이트 읽기'.

**이스케이프는 `$F4`~`$F7` 네 개이고, F5/F6/F7 은 별개 뱅크가 아니라
10비트 글리프 인덱스의 상위 비트다.**

**`$F4` 는 이미 동작하는 프리픽스다.** `F4 xx` = 인덱스 `0*256+xx` = 0~255 로,
맨바이트로는 쓸 수 없는 제어 범위 인덱스에 닿는 경로다. 원문이 실제로 그렇게
쓴다 (본문 153회): `F4 00`=魔 `F4 01`=士 `F4 02`=見 `F4 FF`=★.
맨바이트면 0x00~0x02 는 결합 부호로, 0xFF 는 메시지 종료자로 먹히기 때문이다.

**결합 부호는 세 개다** (`$5D0C` 이후). 현재 바이트가 글리프일 때 '다음'
바이트가 0x00/0x01/0x02 면 앞 글자의 인덱스를 보정한다.
본문 분포로 확인: `0x01` 3,705회(앞 글자 か/た/て/と = 탁점),
`0x02` 144회(앞 글자 は행 = 반탁점). `0x00` 의 682회는 대부분 제어 파라미터다.

주의: 한자 뒤에 맨 `0x01` 을 두면 **앞 한자의 인덱스가 보정되어 엉뚱한 글리프**가
나온다. 士를 쓰려면 반드시 `F4 01` 로 써야 한다.

| 표기 | 글리프 인덱스 | ROM 주소 |
|---|---|---|
| 단일바이트 `c` | c | `0x2F0000 + c*64` |
| `F5 xx` | 256 + xx | `0x2F4000 + xx*64` |
| `F6 xx` | 512 + xx | `0x2F8000 + xx*64` |
| `F7 xx` | 768 + xx | `0x2FC000 + xx*64` |

X 가 16비트이므로 **주소 지정이 1,024 글리프에서 끊긴다**
(`0x2F0000`~`0x300000` = 정확히 64KB = 1024 x 64바이트).
뱅크를 더 추가하려면 인덱스를 11비트로 넓히고 페치 루틴, DMA 설정,
텍스트 파서의 이스케이프 인식을 함께 패치해야 한다. 파서 쪽은 미특정.

### 1.2.2 엔진 패치 — 글리프 인덱스 10비트 -> 11비트 (실기 검증 완료)

수용량 상한을 없애기 위해 렌더러를 패치했다. **실기에서 작동 확인** (image/002.png:
힐 설명문에 「한글성공 확장！」 이 정상 렌더).

**패치 원리**

인덱스 1024 를 `ASL x6`(x64) 하면 `0x10000` 이라 16비트에서 하위 `0x0000` 으로
감긴다. 즉 하위 16비트는 이미 '다음 뱅크 내 오프셋'으로 정확하고, 바꿀 것은
**뱅크 바이트 하나**뿐이다.

    뱅크 = $EF + ($6A >> 2)

`$6A` 가 0~3 이면 `$EF`, 4~7 이면 `$F0`. HiROM 에서 뱅크 `$F0` = ROM `0x300000`
이므로 롬을 4MB 로 확장해 그 자리를 새 폰트 영역으로 쓴다 (헤더 롬 크기 바이트는
원래부터 `0x0C` = 4MB).

`$6A` 는 `0x9552` 의 `STA $69`(16비트) 에서 덮이므로 뱅크 계산을 인덱스 시프트보다
**먼저** 해야 한다. 그래서 `0x9548` 이후 꼬리를 빈 공간으로 옮겨 재구성했다.

**패치 지점** (`patch_engine.py`)

| 주소 | 변경 | 크기 |
|---|---|---|
| `0x00950F` | `JMP $F200` — 이스케이프 판별 확장 (메인 대사 렌더러) | 39바이트 |
| `0x005CFA` | `JMP $F260` — 이스케이프 판별 확장 (옵션·엔딩 렌더러) | 37바이트 |
| `0x009548` | `JMP $F300` — DMA 꼬리 재구성, 뱅크 계산 | 63바이트 |
| 롬 크기 | 3MB -> 4MB | |

`$5CFA` 는 바이트를 `A` 로 받아 상위를 `$01` 에 직접 저장하는 구조라 `$950F` 쪽과
코드가 다르다. 새 코드는 빈 공간 `0x00F200`/`0x00F260`/`0x00F300` (뱅크 `$C0`).

**프리픽스로 쓴 바이트**

`$5D`(備) 와 `$D5`(ゆ). 이 두 바이트는 우리가 번역하지 않는 구간(설명문 A/B,
옵션·엔딩 텍스트)에서 한 번도 쓰이지 않는다. 마법·아이템 이름 테이블은
`0x4f3d3` 부근으로 뱅크 0x04 안이라 우리 통제 하에 있다 (`ヒール` 를 인코딩해
검색으로 확정).

    $5D xx -> 인덱스 1024+xx -> ROM 0x300000 + xx*64
    $D5 xx -> 인덱스 1280+xx -> ROM 0x304000 + xx*64

**부작용**: 이 두 바이트가 이제 프리픽스이므로 단일바이트 글리프로 배정하면
안 된다 (`krcodec.PREFIX_BYTES`). 그래서 단일바이트 슬롯이 145 -> 143 으로 줄고,
그 영향으로 기존 설명문 2개가 1바이트씩 넘쳐 문구를 줄였다.
또 **아직 번역하지 않은 일본어 세그먼트 중 備/ゆ 가 들어간 것은 깨져 보인다.**
전량 번역이 끝나면 해소된다.

**확장 여지**: 뱅크 계산이 `$6A >> 2` 이므로 `$6A` = 6, 7 (인덱스 1536~2047,
ROM `0x308000`~`0x30FFFF`) 도 **코드 변경 없이** 쓸 수 있다. 프리픽스로 쓸 여분
바이트만 더 확보하면 된다.

## 2. 결정적 제약

### 2.1 텍스트 영역이 100% 꽉 참

뱅크 0x04 텍스트 영역 62,464바이트 = 런 본문 61,058 + 종료자 1,406. **여유 0바이트.**

### 2.2 리포인팅 금지 → 제자리 삽입만

번역문 길이를 바꿔 재배치했더니 **게임이 메뉴에서 멈췄습니다.** 원인은 주소 이동으로 미갱신 참조가 깨진 것입니다. 뱅크 0x04 밖에도 이 텍스트를 가리키는 테이블이 있고(`0x052128`, `0x054c41`, `0x0a045f` 등), 포인터가 하나도 없는 고아 런이 254개(5,025바이트) 있습니다.

전수 조사도 시도했으나 실패했습니다 — 런 시작 후보가 1,088개라 임의의 u16이 우연히 맞을 확률이 1.7%, 300만 위치면 기대 오탐이 5만 개입니다. 정적 스캔으로는 진짜 포인터를 가려낼 수 없습니다.

**따라서 현재 방식: 원본과 동일한 바이트 길이로 제자리 삽입, 남는 자리는 공백(`0x20`) 패딩.** 주소가 안 바뀌므로 포인터를 건드릴 필요가 없고 이 문제가 구조적으로 발생하지 않습니다.

### 2.3 바이트 예산

일본어 평균 **1.59 바이트/자**. 한글은 음절당 2바이트(뱅크) 또는 1바이트(단일바이트 슬롯).

현재는 미번역 일본어를 읽을 수 있게 **가나 글리프를 보존**하고 있어 단일바이트 슬롯이 34개뿐 → 평균 1.34~1.59 바이트/음절. 번역문이 원문보다 짧아야 합니다.

전면 번역 시엔 가나 145칸을 전부 회수할 수 있어 평균 1.0 근처로 떨어집니다.

### 2.4 고유 음절 상한 — 전면 번역의 실질 제약

수용량은 **1,321자**다. 엔진 패치(1.2.2)로 프리픽스 두 개를 추가해 확보했다.
(913 -> 753 -> 811 -> 1,321. 913 은 잘못된 가정, 753 은 실측, 811 은 `$F4`
프리픽스 발견, 1,321 은 엔진 패치.)

| 구분 | 슬롯 | 근거 |
|---|---|---|
| 단일바이트 | 145 | `0x20-0xDF` 중 보존 47개 제외 |
| F5 뱅크 | 256 | 전 구간 실제 글리프 |
| F6 뱅크 | 256 | 전 구간 실제 글리프 |
| F7 `0x00-0x3D` | 62 | 실제 글리프 (橋速遅左右輝識謁書修木節第臨土景 등) |
| F7 `0xDE-0xFF` | 34 | `0xFF` 채움 = 미사용 |
| **확정 안전 합계** | **753** | |
| F7 `0x3E-0xDD` | 160 | **엔딩 텍스트다** (2026-09-08 확정). `0x2FCFC0~0x2FF780`, 10,176바이트. 절대 덮으면 안 된다 |
| 주소 지정 이론 상한 | 1,024 | 10비트 인덱스 |

**필요량 추정**: 번역 91개(1,026음절) 시점의 Heaps 피팅 `V = 3.12 * N^0.647`,
전체 예상 19,500음절 -> 고유 **1,600~1,900자**. 보수적으로 봐도 1,600자.

**해결됨.** 엔진 패치(1.2.2)로 수용량이 1,321자가 되어 필요량 약 1,200자를
넘겼다. 어휘를 극단적으로 줄일 필요가 없어졌다. 아래는 패치 전 분석 기록이다.

패치 전 상황: 주소 지정 상한(1,024)을 전부 써도 필요량의 60% 였다.

다만 811자는 753자보다 실질적으로 다르다. 어휘를 의식적으로 통제한 번역이라면
(어미 고정, 한 개념 한 단어, 희소 음절 회피, 고유명사 12개 정도) 700~820자에
들어갈 수 있다. **빡빡하지만 가능한 범위**다. 대신 진행 중에 곡선을 감시해야
후반에 벽을 만나지 않는다 — `trcheck` 가 구간별 가드레일로 경고한다.

대응 방침 (사용자 확정): 어휘를 753자 인벤토리에 맞춘다. 문체의 다양성을
먼저 포기하고 고유명사와 게임 용어는 정확하게 지킨다.

### 2.5 실측: 811자로는 전량 번역이 불가능하다

어휘 통제(어미 고정, 1회용 음절 교체, 한 개념 한 단어)를 걸고 117개를

## 4. 미해결 문제

### 4.1 메뉴 폰트가 한글로 안 나옴 ← 미해결, 여러 차례 실패

**증상**: 메뉴 폰트를 쓰는 창만 한글화가 안 먹음. 대화창·설명문은 정상.

**2026-09-04 갱신 — 영향 범위가 라벨 13개가 아니었다. 우선순위 낮음 -> 높음.**

같은 문자열이 창마다 다르게 나오는 것을 프로브로 확정했다
(`make_probe_list.py`, image/소생_001.png, image/소생_002.png).
마법 [06] 이름을 단일바이트 코드만으로 「소생」(`b1 d4`) 으로 바꿨더니

| 창 | 출력 | 쓰는 폰트 |
|---|---|---|
| 마법 설명문 | 「소생」 | 메인 폰트 (0x2F0000) — 패치됨 |
| 마법 목록 | 「あや」 | 메뉴 폰트 — 미패치 |

`B1=あ`, `D4=や` 다. 즉 목록 창은 **패치한 글리프를 안 보고 원본 가나를
본다.** 이 관측 자체는 아래 '확정된 관측' 에 이미 있던 것과 같다
(0xB1 을 덮었는데 あ 가 나옴). 이번에 새로 확정된 것은 **범위**다.

  - 마법 이름 목록, 포메이션 창, 장비 창이 모두 메뉴 폰트를 쓴다
  - 즉 4.1 을 풀지 않으면 마법·아이템·장비 이름은 화면에서 영원히 일본어다
  - 라벨 13개 문제가 아니라 이름표 전체의 전제 조건이다

**VRAM 덤프로 배제한 것** (2026-09-04, 목록 창 열린 상태, 마제스티 수동 export)

덤프는 확보했다. 기존 문서가 선행 조건으로 지목한 바로 그 자료다.
그런데 이것만으로는 폰트 위치가 안 나왔다. 배제한 것을 남긴다.

| 시도 | 결과 |
|---|---|
| VRAM 비어있지않은 타일 3,038개를 롬에서 그대로 검색 | 237개 발견. 전부 배경·스프라이트 (0x26b000 0x26d000 0x1f1000 0x271200) |
| 메인 폰트 あ 비트맵을 VRAM 에서 검색 (2bpp OR / plane0만 / plane1만 / 1bpp) | 전부 0곳 |
| plane0==plane1 서명으로 글리프형 타일 추출 | 89개. 전부 창 격자무늬·세로줄 (VRAM 0x1400~0x1800) |
| 대역별 잉크량 필터로 글자 형태 육안 탐색 | 전부 디더링된 배경 그래픽 |

핵심 소득이 하나 있다. **메뉴 폰트의 あ 는 메인 폰트의 あ 와 비트맵이 다르다.**
같은 서체를 재인코딩한 것이 아니라 별개 서체다. 그래서 메인 폰트 비트맵으로
VRAM 이나 롬을 검색하는 접근은 원리적으로 실패한다. 이 계열은 더 시도하지 말 것.

또 하나. 내가 만든 「소」「생」 글리프와 ♥(0xa0) 이 이 덤프에 없다.
목록 화면은 그것들을 그리지 않으므로 당연하고, 동시에 **목록 창이 메인 폰트
글리프를 단 하나도 쓰지 않는다**는 독립 확증이다.

**DMA 로그로 확정한 것** (2026-09-07, `dma_log3.txt` 953줄, 마제스티 제공)

| 경로 | 관측 | 뜻 |
|---|---|---|
| 메인 폰트 | `src=$EF:xxxx size=64` **172건 전부 64바이트** | ROM 0x2F0000 에서 글리프 단위 직접 DMA. 기존 결론과 일치 |
| 메뉴 텍스트 | `src=$7E:81xx~85xx` -> `VRAM $F1xx~$F5xx` (델타 일정 0x7016) | **WRAM 에서 조립한 뒤 DMA** |

전체 소스 뱅크 분포: `$7E` 543건, `$EF` 172건, `$C6` 90건, `$C0` 33건,
`$CF`/`$E6` 32건, `$E7` 24건, `$7F` 15건, `$DF` 12건.

**이것이 롬 바이트 검색이 전부 실패한 이유다.** 메뉴 글리프는 롬에서 VRAM 으로
바로 가지 않는다. CPU 가 WRAM 버퍼에 조립하고 그 버퍼를 DMA 한다. 그래서
VRAM 타일과 롬 바이트가 일치하지 않는다 (압축이 아니라 조립이었을 수 있다).

VRAM 덤프와 이 로그를 직접 대응시키지는 않았다. 두 자료가 서로 다른 세션이라
같은 화면 상태가 아니다. 그 대응은 추정이므로 세우지 않는다.

**WRAM 추적 1차 결과 — 대상이 틀렸다** (`wram_write2.txt`)

`$7E:8100~8600` 에 쓰이는 값이 `00 01 02 03` / `20` / `23` / `32` 였다.
글리프 비트맵이 아니라 **타일 인덱스**다. 즉 그 버퍼는 타일맵이고, 그것이
VRAM `$F100~$F600` 으로 간다. 폰트 CHR 은 다른 경로다.

건진 것이 있다. `PC=$C0:9593/9597/959B/959F` 가 `00 01 02 03` 을
`$7E852C/852E/856C/856E` 에 쓴다. 0x40 간격 2x2 배치이므로 **16x16 글자
하나를 타일 4개로 놓는 루틴**이다. 즉 목록 창의 글자도 16x16 이다.

**CHR 조립 버퍼를 로그로 특정했다** (`dma_log3.txt` 재분석)

WRAM -> VRAM `$0000~$1FFF` 전송이 434건이고 그 소스가 몰려 있다.

| 소스 | 건수 |
|---|---|
| `$7E:2C00xx` | 246 |
| `$7E:2B00xx` | 178 |
| `$7E:27xx` | 8 |

전송 크기가 8~60바이트로 잘게 쪼개져 있다. 글리프를 조립해 부분 전송하는
방식이다. `$7E:273B`(v1 이 본 주소)도 이 목록에 있지만 8건뿐이고 본체는
`$2B00~$2CFF` 다. v1 이 실패한 이유가 이것일 수 있다.

**WRAM 2차 추적도 대상이 틀렸다** (`wram_write3.txt`)

`$7E:2B00~2CFF` 에 쓰이는 값이 `0x78 0x80 0x88 0x90 0xB0 0x28` 같은 좌표성
변수였다. 글리프 비트맵이 아니다. 그 구역은 스크롤·위치 변수로도 쓰인다.

DMA 로그에서 이 구역을 소스로 본 것은 내가 `r[1] & 0xFF00` 으로 버킷팅해
`$2B00xx` 로 뭉갠 결과였다. 실제 소스 오프셋은 `$273B~$F0A9` 로 넓게
퍼져 있어 특정 버퍼로 좁혀지지 않는다. **버킷팅이 만든 착시였다.**

**64바이트 전송 전수 조사 — 메뉴 폰트 전송이 이 로그에 없다**

64바이트는 16x16 글리프 1개 크기다. 전체 215건의 소스를 갈랐다.

| 소스 | 건수 | 오프셋 종수 | 판정 |
|---|---|---|---|
| `$EF` | 172 | 다수 | 메인 폰트. 글자마다 오프셋이 다르다 |
| `$C6` | 36 | **2종** (`0x951`, `0x991`) | 폰트 아님. 같은 것을 반복 전송하는 그래픽 |
| `$7E` | 7 | 5종 | WRAM 조립분 |

`$C6` 는 오프셋이 두 개뿐이므로 폰트일 수 없다. 폰트라면 글자마다 달라야 한다.
그리고 폰트 CHR 을 통째로 올리는 큰 전송(0x800 이상)이 로그에 아예 없다.

즉 **세 번의 로그로도 메뉴 폰트의 롬 출처를 특정하지 못했다.** 배제만 늘었다.

**그래도 확정된 진입점이 하나 있다 — 여기서 코드 읽기로 전환한다**

`PC=$C0:9593` 이 16x16 글자를 타일 4개로 배치하는 루틴이다 (`00 01 02 03` 을
`0x40` 간격 2x2 로 쓴다). 그리고 이 주소는 **내가 이미 패치한 메인 렌더러와
같은 구역**이다.

  `0x00950F`  이스케이프 판별 (내가 패치)
  `0x009548`  DMA 꼬리, 뱅크 = `$EF + ($6A>>2)` (내가 패치)
  `0x009593`  16x16 글자를 타일 2x2 로 배치  <- 목록 창 경로로 확인됨

목록 창 텍스트가 메인 렌더러 구역을 타는데도 원본 가나가 나온다. 그러므로
같은 폰트를 쓰면서 **인덱스나 뱅크 계산이 다른 갈래**가 있을 가능성이 높다.
이것은 로그가 아니라 디스어셈블로 확인할 일이다.

**코드 읽기로 확정한 것** (2026-09-08, 롬만으로)

`0x9593` 주변을 디스어셈블해 대사·설명문 렌더러의 전모를 읽었다.

```
0x009548  REP #$20 / LDA $69 / ASL x6        인덱스 x64
0x00955c  ADC #$1800                          VRAM 목적지 워드주소 = 0x1800 + Y*8
0x009576  LDA #$80EF / STA $0700,X            소스 뱅크 $EF 를 상수로 지정
0x009590~ STA $7FEA,X / $7FEC,X / $802A,X / $802C,X   타일맵 2x2 배치
```

즉 이 경로는 **뱅크 $EF(ROM 0x2F0000)를 코드에 박아** 쓰고, 글리프를 VRAM
바이트 0x3000 부근에 올린다. 내가 패치한 그 경로다.

DMA 뱅크를 쓰는 지점을 전수 조사했다 (`STA $0700,X` = `9d 00 07`, 12곳).
상수로 지정하는 곳은 넷뿐이다.

| 주소 | 뱅크 | 정체 |
|---|---|---|
| `0x009579` | `$EF` | 메인 폰트. 대사·설명문 |
| `0x003e5c` `0x003f46` `0x007b9f` | `$7E` | WRAM 조립분 |
| `0x025f94` `0x025fe2` | `$7F` | WRAM 상위 |

나머지는 `LDA $06FE,X` 로 읽는데, X 가 슬롯당 2씩 늘므로 `$06FE,X` 는
**직전 큐 슬롯**이다. 즉 앞 전송의 뱅크를 물려받는 것이고, 새 폰트 주소를
지정하는 코드가 아니다.

**따라서 롬에서 VRAM 으로 폰트를 올리는 경로는 $EF 하나뿐이다.**

그런데 프로브에서 목록 창은 원본 가나를 보였다. 롬에 あ 비트맵은
0x2F2C40 한 곳뿐이고 프로브 롬에는 그 자리에 한글이 들어 있다. 그러므로
목록 창은 **롬에서 직접 읽지 않는다.** 남는 설명은 하나다 —
롬(압축 또는 별도 포맷) -> WRAM -> VRAM 소구간 전송.

이것은 DMA 로그의 관측과 일치한다 ($7E 소스 543건, 큰 롬 전송 없음).

**다음에 할 것**: WRAM 폰트 적재 구간을 특정해야 한다. 다만 그 구간을
두 번 잘못 짚었으므로(4.1 기록 참조) 추측으로 대상을 정하지 않는다.
부팅·장면 전환 시 WRAM 에 쓰는 큰 루프를 찾는 것이 정공법이다.

**우선순위 재조정**: 4.1 을 풀지 않아도 이름표는 확인 창·대사 삽입·설명문
에서는 정상 표시된다 (image/problem_009.png 에서 확인됨). 그래서 아이템
이름표 조립기를 먼저 만드는 편이 눈에 보이는 진전이 크다.

**로그 요청은 중단한다.** 세 번 받아 배제 목록만 늘렸다. 다음은 `0x9593`
주변을 읽어 어느 DMA 설정을 쓰는지 확인하는 것이고, 그것은 롬만 있으면 된다.

버퍼를 채우는 것은 CPU 쓰기이므로 DMA 로그로는 안 보인다. 그 버퍼에 쓰는
명령의 PC 를 모으면 루틴을 특정할 수 있고, 루틴을 읽으면 원본 폰트의 롬
주소가 나온다. 대상 주소는 추측이 아니라 위 로그로 확정한 `$7E:8100~8600` 이다.

(기존 `tracewram.lua` 는 `$7E:273B` 를 봤는데 그것은 실패한 추적에서 나온
추정 주소였다. 그 계열을 반복하지 말 것.)

**참고 — 예전 DMA 로그** (이 방법으로 메인 폰트 경로를 이미 확정한 전례가 있다)

기존 문서에 「DMA 로그에서 `src=$EF:xxxx size=64` 가 45건」 으로 설명문 경로를
확정한 기록이 있다. 같은 방법을 목록 창에 적용하면 소스 주소가 직접 나온다.
글리프 비트맵을 추측할 필요가 없어진다.

  Mesen `Debug -> Event Viewer` 를 열고 마법 목록 창을 여는 순간을 기록.
  또는 `Debug -> Trace Logger` 로 DMA 레지스터($4300-$437F) 기록.
  필요한 것은 그 창을 열 때 발생하는 DMA 의 **소스 주소와 크기**다.

**이번에 추가로 배제한 것** (역검색 계열은 문서가 금지한 길이었다. 반복하지 말 것)
| 시도 | 결과 |
|---|---|
| あ 글리프 64바이트 롬 전체 검색 | 원위치 1곳뿐. 생(raw) 복사본 없음 |
| 행단위 1bpp 32바이트로 재포장해 검색 | 0곳 |
| 타일순서 1bpp 32바이트로 재포장해 검색 | 0곳 |
| 상단 8행 16바이트만 검색 | 0곳 |

메뉴 폰트는 메인 폰트의 단순 재인코딩이 아니다. 압축이거나 별개 서체다.
(문서의 기존 경고대로 '압축 확정' 으로 단정하지 않는다. 배제된 것은
'단순 재인코딩' 가설뿐이다.)

**확정된 관측** (진단 ROM `make_probe.py` 로 재현 가능)
- 메뉴 라벨 바이트를 바꾸면 표시가 바뀜 → 게임이 패치한 바이트를 읽는 것은 맞음
- 코드 `0xB1`(히라가나 범위)을 한글로 덮었는데 화면엔 `あ`가 나옴
- 코드 `0x71`(가타카나 범위)도 마찬가지로 `ア`가 나옴
- 코드 `0x22`(한자 범위)는 깨져서 나옴

**확정된 반대 사실**: 마법 이름·설명문은 메인 폰트를 씀. DMA 로그에서
`src=$EF:xxxx size=64` 가 45건 잡혔고, `$EF`=ROM `0x2F0000` 이며 64바이트는
글리프 1개. 코드로 환산하니 `ヒール` + `ＨＰを回復する呪文` 이 정확히 복원됨
(뱅크 F5/F6 한자까지 일치). **즉 설명문 경로는 메인 폰트 글리프 단위 DMA.**

**실패한 추적들** (같은 길 반복 금지)
| 시도 | 결과 |
|---|---|
| VRAM 타일을 ROM 에서 역검색 | 일부 구간만 맞음. "압축 확정"은 **오판**이었음 |
| `$E7:1200`(=ROM `0x271200`) 추적 | VRAM 과 128/128 일치하지만 **스프라이트 그래픽**이었음 |
| `$7E:273B` → VRAM `$5C00` 추적 | 값이 `1F 07 03 / E0 F0 F8 FC FF` → **창 테두리** 생성 버퍼 |
| VRAM 에 직접 쓰기 콜백 | Mesen 이 VRAM memType 콜백 미지원. 로그 빈 파일 |
| `emu.isKeyPressed("D")` | 무반응 (키 이름/포커스 문제) |
| 진단 ROM VRAM 덤프 | 메뉴가 열린 화면이 안 잡힘. 한글도 원본 가나도 VRAM 에 없음 |

**Mesen2 Lua 주의점**
- `emu.getState()` 는 **점 포함 평면 키**를 씀: `st["cpu.pc"]`, `st["cpu.k"]`.
  `st.cpu.pc` 는 nil → PC 가 `$00:0000` 으로 찍힘
- VRAM 은 `addMemoryCallback` 대상이 안 됨. PPU 레지스터
  (`$2115` VMAIN / `$2116-7` VMADD / `$2118-9` VMDATA)를 감시해 주소를 직접 추적해야 함

**다음에 시도할 것**
1. **메뉴가 확실히 열린 상태의 VRAM** 확보가 선행 조건. 자동 덤프는 타이밍을 놓침
   → Mesen `Debug → Memory Tools → Video RAM → File → Export` 로 수동 저장이 확실
2. 그 VRAM 에서 라벨 글리프 위치를 **확정한 뒤** 감시 대상을 정할 것.
   지금까지 실패는 전부 위치를 추정으로 정한 데서 비롯됨
3. 메뉴 화면 스크린샷도 단서가 됨 (무엇이 어떤 크기로 깨지는지)

**우선순위**: **높음** (2026-09-04 상향). 라벨 13개 문제가 아니라 마법·아이템·
장비 이름 전체가 걸려 있다. 이름표를 번역해도 목록 창에서는 보이지 않는다.

**선행 조건은 사람이 해야 한다**: 메뉴가 열린 상태의 VRAM 덤프.
Mesen `Debug -> Memory Tools -> Video RAM -> File -> Export`.
자동 덤프는 타이밍을 놓친다 (기존 실패 기록). 그 덤프에서 라벨 글리프
위치를 확정한 뒤에야 감시 대상을 정할 수 있다.

### 4.2 오프닝 컷신 텍스트를 못 찾음

동생(ホセ)이 형에게 말하는 오프닝 장면. `あにき`는 뱅크 0x04에 14곳뿐이고 그건 후반 재회 장면입니다(근처에 "호세의 시신" 표현). 확정된 텍스트 구간 4곳 어디에도 오프닝이 없습니다. **압축됐거나 별도 시스템**으로 추정 — 4.1과 같은 방법으로 접근하면 같이 풀릴 가능성이 높습니다.

### 4.3 몬스터 이름 구간은 다른 인코딩을 씀 ← 신규

미식별로 남긴 F7 뱅크 상위 약 55개 코드는 대사가 아니라 **가타카나 몬스터 이름** 안에
나타납니다: `グレーターオ<C4C>オ<C9A>ッサーオ` `ヘル<C79>ルベロス` `ドラゴＲ<C44>ナイト`
`Ｈ<C8E>ブ<C47>スラッグ`. 즉 이 구간은 `0xF7`을 뱅크 이스케이프로 쓰지 않습니다.
한자 매처가 실패한 것(IoU 0.39~0.6)도 글리프가 한자가 아니기 때문입니다.

몬스터 이름도 번역 대상이므로 나중에 별도로 풀어야 합니다. 다만 **전면 번역 시 이 슬롯은
어차피 회수 대상**이라 식별 자체는 불필요합니다. 필요한 것은 인코딩 구조입니다.

### 4.5 추출기의 0xFF 스캔이 이스케이프를 모른다 ← 신규 (2026-09-07)

**증상**: 세그먼트 17개가 프리픽스 바이트(`F4`~`F7`)로 끝난다.

**원인**: 원문에 「`Fx FF`」 형태의 글리프 참조가 있다. 예를 들어 `#802` 는
`... f5e7 f6 ff a6 ...` 인데 `f6 ff` 가 글리프 인덱스 767 을 가리키는 정상
참조다. 그런데 추출기의 메시지 경계 판정은 0xFF 를 무조건 종료자로 보므로
그 `ff` 에서 메시지를 쪼갠다. 그래서 앞 조각은 프리픽스로 끝나고, 뒤 조각이
별도 세그먼트가 된다.

게임은 그렇게 읽지 않는다. 렌더러는 `f6` 을 프리픽스로 보고 다음 바이트를
인덱스로 먹으므로 `ff` 를 종료자로 해석하지 않고 뒤 조각까지 이어 읽는다.

**해당 세그먼트 17개**
```
#364 #802 #917 #954 #1198~#1210
```
`#1198~#1210` 은 4바이트짜리 13개가 연속인데, 이 구간은 이름·아이템 관련
데이터일 가능성이 있다 (아직 확인 안 함).

**내가 이것 때문에 만든 회귀**: 「고아 프리픽스 정리」 때 `#364` 말미의
`<F5>` 를 지웠다. 그러자 뒤 `ff` 가 진짜 종료자가 되어 이어지는 `#365`
("예정대로입니다")가 화면에서 사라졌다. 원문 구조를 오류로 보고 지운 것이다.
`<F5>` 를 복구했다.

**대응**: `trcheck` 의 고아 프리픽스 검사에 예외를 넣었다. **원문이 같은
프리픽스로 끝나는 세그먼트에서는 번역문 말미의 프리픽스를 허용한다.**
그러면 정상 구조를 보존하면서도 진짜 고아는 계속 잡는다.

**남은 판단**: 이 17개를 번역하려면 말미 프리픽스를 유지해야 하는데, 그러면
`Fx FF` 글리프(원문 일본어 글자)가 한국어 문장 중간에 하나 남는다. `FF` 는
세그먼트 밖이라 우리가 못 바꾼다. 선택지는 셋이다.
1. 그대로 두기 — 글자 하나가 일본어로 남는다
2. 추출기를 이스케이프 인식으로 고쳐 두 조각을 한 세그먼트로 합치기
   (파이프라인 전체에 영향. 세그먼트 수와 주소가 바뀐다)
3. 프리픽스를 `F4` 로 바꾸고 인덱스 `0xFF`(폰트 255번)에 한글을 배정하기
   — 단어표·이름표는 `0xFF` 를 종료자로 쓰므로 그쪽과 충돌하지 않게
   대사 전용으로만 허용해야 한다

지금은 1번 상태로 두고 해당 세그먼트를 미번역으로 남겼다. `#364` 만 이미
번역돼 있어 원문 구조를 복구해 뒀다.

### 4.6 접미사 공유 이름표는 조립기가 필요하다 ← 신규 (2026-09-08)

몬스터·아이템 이름 엔트리 안에 절대 포인터가 박혀 있다.

  `EE <ptr16>`      ptr 의 0xFF 종료 문자열을 이어 붙인다
  `F0 C4 <ptr16>`   ptr 의 문자열을 넣는다

그리고 접미사를 공유한다. `#1325` 는 `0xf68c` 를 다섯 번 참조하는데 그
접미사는 앞쪽 다른 세그먼트에 있다. 제자리로 번역하면 참조 대상이 그대로
일본어로 남아 섞여 나오고, 거꾸로 참조되는 쪽을 덮으면 그것을 쓰는 다른
이름들이 함께 바뀐다.

**조립기 없이는 손댈 수 없다.** 재배치하면서 (1) 포인터 표, (2) 엔트리 안에
박힌 참조, (3) 공유 접미사의 위치를 함께 다시 계산해야 한다.

`trbatch.todo()` 가 이 세그먼트들을 작업 목록에서 뺀다. 표가 소유한 구간
(마법 이름 18개)도 함께 뺀다 — 그쪽은 `nametbl` 이 정본이다.

**같은 자리를 두 경로가 다투는 문제가 세 번 있었다**
  배치 42  patch_all.MENU 13개가 대사 세그먼트를 잘라 먹었다
  배치 65  이름표를 대사보다 먼저 써서 대사 되쓰기에 덮였다
  배치 79  마법 이름 7개를 대사로도 번역해 종료자가 어긋났다
`trcheck` 의 표 침범 검사와 `trbatch` 의 목록 제외로 두 층에서 막았다.

**보류 목록** (조립기 또는 별도 판단 필요)
| 세그먼트 | 성질 |
|---|---|
| `#1325` `#1326` `#1336` | 접미사 공유. 내부 참조 있음 |
| `#1316` `#1317` | 제어 비율 58~62%. 텍스트가 아니라 데이터로 보인다 |
| `#1198`~`#1210` | 4바이트 13개 연속. `Fx FF` 오분할 계열 (4.5) |

### 4.7 아이템 이름표는 손대지 않는다 ← 판단 (2026-09-08)

구조를 전수 측정한 결과 **문자열이 서로 겹친다.** 접미사 공유가 아니라
문자열 자체가 겹쳐 쌓여 있다.

| 측정 | 값 |
|---|---|
| 포인터 표 `0x040260` | 130엔트리 |
| 고유 문자열 | 95개 |
| **다음 엔트리를 침범하는 문자열** | **11개** |
| 내부 참조 대상 | 17곳 (각 3~7회 참조) |
| 주소 범위 | `0xf1c0 ~ 0xf46f` |

예를 들어 `0xf1de` 의 문자열은 13바이트인데 다음 엔트리(`0xf1e5`)까지
6바이트뿐이다. 즉 `0xf1de` 의 문자열 뒷부분이 곧 `0xf1e5` 엔트리이고,
그 자리를 두 엔트리가 함께 쓴다.

**두 방법 모두 막힌다**
- 제자리 번역: 한 바이트 위치가 여러 엔트리를 동시에 섬기므로 불가능
- 재배치 + 포인터 갱신: 표 130개는 고칠 수 있으나 이 주소 범위를 가리키는
  다른 참조를 전부 찾아야 한다. 범위를 값으로 갖는 16비트 위치가
  **25,246곳**이고 대부분 오탐이다. 원칙 1 의 리포인팅 실패, 그리고 이름표
  재배치로 메뉴가 멈춘 사고(4.5 앞부분)와 같은 상황이다

**성과도 반쯤 막혀 있다**: 4.1 이 미해결이라 아이템 이름은 목록 창에서
보이지 않는다. 확인 창과 대사 삽입에서만 보인다. 이 프로젝트에서 가장
위험한 작업인데 보상이 절반이다.

**결론**: 4.1 을 먼저 풀고, WRAM 폰트 경로를 알게 된 뒤에 다시 판단한다.
그때는 목록 창까지 보이므로 위험을 감수할 이유가 생긴다.

### 4.8 F7 `0x3E-0xDD` 의 정체 = 엔딩 텍스트 ← 해결 (2026-09-08)

오래 「정체 불명 데이터」 로 남아 있던 160슬롯이 무엇인지 확정했다.

**어떻게 찾았나.** 세 번째 렌더러(`0x005650~`)를 디스어셈블하다가
`0x005666` 의 `LDA $EFCFC0,X` 를 읽었다. `$EF:CFC0` = ROM `0x2FCFC0` 이고,
그 주소를 직접 판독하니 일본어 문장이 나왔다 (`0xF1` 줄 구분, `0xFD` 표식).

**확정된 구간**

| | |
|---|---|
| 엔딩 텍스트 | `0x2FCFC0 ~ 0x2FF780` (10,176바이트) |
| 읽는 코드 | `0x005666` `LDA $EFCFC0,X`, `0xFF`/`0xFE`/`0xFD` 판별 |
| 폰트 인덱스 환산 | 831 ~ 989 |

**F7 슬롯 배정이 안전함을 실측했다**

  F7 하위 `0x00-0x3D` -> 인덱스 768~829  = ROM `0x2FC000~0x2FCF80`
  엔딩 텍스트          -> 인덱스 831~989  = ROM `0x2FCFC0~0x2FF780`
  F7 상위 `0xDE-0xFF` -> 인덱스 990~1023 = ROM `0x2FF780~0x300000`

상위 슬롯 구간(2,176바이트)은 **100% `0xFF` 채움**이다. 엔딩 텍스트가
끝나는 바로 그 지점에서 시작한다. 경계가 정확히 맞아 겹침이 없다.

즉 「F7 0x3E-0xDD 는 쓰지 않는다」 는 기존 보수적 판단이 옳았고, 이제
그 이유를 안다. 그리고 상위 34슬롯은 안전이 증명됐다.

**엔딩 텍스트는 남은 번역 대상이다.** 10KB 이고, 스트림을 순차로 읽는
구조여서 제자리 번역이 가능해 보인다. 다만 진입점이 인덱스로 잡히는지
확인해야 길이를 바꿀 수 있는지 판단할 수 있다.

### 4.9 엔딩 본문은 866바이트다 (4.8 정정, 2026-09-08)

4.8 에서 본문을 `BODY`~`0x2FF780` (10,168바이트) 로 적었습니다. 틀렸습니다.
포인터 표는 4개고 각 블록은 첫 `0xFF` 에서 끝납니다.

| 블록 | 오프셋 | 크기 | 내용 |
|---|---|---|---|
| 1 | `0x000`~`0x0b0` | 176B | 팔코에게 남기는 부탁 |
| 2 | `0x0b1`~`0x139` | 136B | 팔코가 팔찌와 세계를 맡는다 |
| 3 | `0x13a`~`0x251` | 279B | 루큐가 세계를 물에 가라앉힌다 |
| 4 | `0x252`~`0x365` | 275B | 루큐가 모든 생명을 없애고 허공에 잠긴다 |

합 866바이트, 가나 포함 52조각. **엔딩은 4종입니다.**

`0x366` 이후 6.6KB 는 엔딩이 아닙니다. 포인터가 4개뿐이라 렌더러가 닿지
않습니다. `ending.TEXT_END = 0x366` 을 두고 `patch_ending.load()` 가 이 밖을
걸러냅니다. 상수는 `ending.text_end(rom)` 이 다시 계산해 검증합니다.

**F7 상위 슬롯은 폰트가 아닙니다.** 4.8 은 F7 `0x3E`~`0xDD` 를 "엔딩 텍스트"로
적었지만, 실제 엔딩은 F7 `0x3F`~`0x4C` (14슬롯) 만 씁니다. 그 뒤 `0x4D`~`0xDD` 는
위의 미식별 데이터가 깔려 있습니다. 글리프로 렌더해 보면(`0x4B` `0x77` `0x85`
`0x8F` 확인) 전부 노이즈입니다. **폰트 여유 슬롯으로 쓸 수 없습니다.**

### 4.10 몬스터 이름표 — 절반만 가능하다 (2026-09-08)

`0x04f672`~`0x04f801`. 아이템표(4.7)와 달리 **문자열이 겹치지 않습니다.**
각 엔트리가 `0xFF` 로 끝나고 다음 엔트리가 바로 이어집니다. 제자리 삽입 가능.

| 분류 | 개수 | 처리 |
|---|---|---|
| 깨끗한 이름 | 19개 | **번역 완료** |
| 접미사 공유 `<EE>` | 10개 | 불가 (4.6 — 어셈블러 필요) |
| `F7` 비글리프 참조 | 5개 | 손대지 않음 (아래) |

접미사 공유 10개 안에 이름이 여럿 들어 있습니다 (`#1354` 하나에 6개). 그래서
번역한 19개는 전체의 대략 절반이고, **몬스터 목록은 한국어와 일본어가 섞인
상태입니다.** 나머지는 4.6 이 풀려야 합니다.

**`F7` 비글리프 참조 5개** (`#1333` `#1334` `#1341` `#1344` `#1350`): `f7 4b`
처럼 F7 상위 슬롯을 가리키는데, 4.9 에서 확인한 대로 그 슬롯은 글리프가
아닙니다. 접미사 공유가 `<EE>` 만 쓰는 게 아니라는 뜻이거나 애초에 이름이
아니라는 뜻입니다. 어느 쪽이든 손대면 안 됩니다.
`trbatch.has_nonglyph_f7()` 이 걸러냅니다.

**아이템표 구간이 필터에 빠져 있었습니다.** 4.7 에서 손대지 않기로 판단한
`0xf1c0`~`0xf46f` 가 `table_owned()` 에 없어서 작업 목록에 장비 이름이 그대로
떴습니다 (`#1223` `#1261` `#1269` `#1315`). 배치 79 와 같은 표침범을 네 번째로
되풀이할 자리였습니다. 구간을 추가했습니다.

부수 효과: `#1222` 「フォーメーション」(`0x04f1b7`, 표 바깥) 은 「진형」으로
번역했지만 같은 낱말인 `#1315` (`0x04f466`, 표 안) 은 일본어로 남습니다.
4.7 이 풀릴 때까지 이 불일치는 남습니다.

### 4.11 메뉴 정지 — 제어 코드를 지웠다 (2026-09-08)

**증상**: 메뉴를 열면 게임이 멈춤. §4.5 와 같은 증상이지만 원인은 다르다.

**원인**: `#1095` 「`<EB><15>の頂<EE>に←`」 (이동 목록, `0x04e214`). 예산 4바이트에
맞추려 「`<EB><15>의 정상←`」 으로 줄이면서 **`<EE>` 를 지웠다.**

```
원  fa 01 20 20 20 20 20 eb 15 c9 f5 6c ee c6 e0
패  fa 01 20 20 20 20 20 eb 15 2b 20 bd c6 e0 20   ← ee 없음
```

같은 이동 목록의 다른 네 항목(`#1078` `#1085` `#1087` `#1093`)에는 `<EE>` 를
남겼는데 이것만 빠졌다. 이동 목록은 메뉴 화면이다.

**기존 검사가 못 잡은 이유**

| 검사 | 왜 못 잡는가 |
|---|---|
| `[1]` 바이트 역검증 | 길이만 맞으면 통과한다. 15바이트 그대로였다 |
| 고아 프리픽스 | `F4`~`F7`·`5D`·`D5` 만 본다. `EE` 는 대상이 아니다 |
| 예산 초과 | 오히려 지워서 예산에 들어갔다 |

**고친 것**: 「` 정상`」 + `<EE>` + 「`에`」 = 4바이트. 공백1 + 정1 + 상1 + 에1.
「마왕 정상에←」 로 렌더된다. `의` 를 버렸지만 `#1078` 「자가트 마을에←」 와
같은 방식이다.

**검사 9 를 추가했다** — 제어 코드 개수 보존. `E5`~`FE` 중 `F4`~`F7`(글리프
프리픽스, 한자를 한국어로 바꾸면 같이 사라지는 게 맞다)과 `EB`(단어표 참조,
넣고 빼는 게 번역 선택)를 제외한 전부.

이 검사로 이전 세션의 결함 둘도 찾았다.

- `#57` SAVE 창에 `<E9><15>タ` 가 잘못 끼어 있었다 (원문에 없는 제어 시퀀스)
- `#954` 페이지 넘김 `<E7>` 이 빠져 있었다

**폐기한 가설**: 「`#1222` 「진형」이 메뉴 명령 라벨이고 `f4` 이스케이프를 쓰므로,
이스케이프를 모르는 단순 라벨 루틴이 멈춘다.」 → 같은 라벨 표의 `#1220`
「コンディション」→「컨디션」이 이전 세션에 번역됐고 「컨」은 `F6` 이스케이프인데
메뉴가 동작했다. 라벨 표의 이스케이프는 무해하다.

### 4.12 메뉴 정지 — F4 이스케이프 (2026-09-08)

**이분 탐색으로 좁혔다.** 추측만으로는 두 번 틀렸다.

| 롬 | 담긴 것 | 결과 |
|---|---|---|
| A | 이번 세션 전 상태 | 열림 |
| B | 현재 − 엔딩 쓰기 | 멈춤 |
| C | 현재 − 표·메뉴 구역 32개 | 열림 |
| D | 현재 − 이동목록 7개 | 멈춤 |
| E | 현재 − 이름표 25개 | **열림** |

→ 원인은 `0x04f000` 이상 표 영역 25개 안에 있다.

**원인: `F4` 이스케이프.** `F4` 는 다른 뱅크와 성질이 다르다.

`F4 xx` 는 글리프 `xx` 를 가리킨다. 단일바이트로 쓸 수 있는 글리프는 단일바이트로
쓰므로, `F4` 에는 **바이트 값이 제어 코드와 겹쳐 단일바이트로 못 쓰는 글리프만**
남는다 (`F4_SLOTS = 0x00~0x1F, 0xE6~0xFF`). 즉 **`F4` 의 두 번째 바이트는 항상
제어 코드 값이다.**

`#1222` 「진형」은 `f4 1f f4 ef` 로 들어갔다. 라벨 렌더러가 `F4` 를 모르면 `0x1F` 를
제어 코드로 읽는다.

**원본 표를 전수 확인한 결과가 이를 뒷받침한다.**

| 구역 | 원본에 `F4` | 원본에 `F5`~`F7` |
|---|---|---|
| 라벨 표 | 0개 | 0개 |
| 몬스터 이름 | 0개 | **14개** |
| 화자 이름표 | 0개 | 0개 |
| 아이템표 | 1개 | 1개 |

`F5`~`F7` 은 쓰는데 `F4` 는 안 쓴다. 대사 렌더러는 `F4` 를 처리한다 (원문도
`<F4><魔>` 로 魔 를 쓴다). 메뉴·표 렌더러는 처리하지 않는다.

**고친 방법**: `krcodec.allocate(no_f4=...)`. 메뉴·표 영역(`0x04e000` 이상)과
단어표·이름표에 실리는 음절은 `F4` 를 받지 않는다. 뱅크 이스케이프는 어느
뱅크든 2바이트라 재배치 비용이 0이고, 표 음절이 건너뛴 `F4` 슬롯은 뒤의 대사
전용 음절이 받으므로 총 슬롯 소비도 같다 (`5D`/`D5` 로 넘치지 않는다).

결과: `#1222` = `f5 1d f5 26`. 표·메뉴 세그먼트 173개 중 `F4` 사용 0개.

**틀린 가설 둘을 기록한다**

1. 「`#1095` 에서 `<EE>` 를 지운 것이 원인」 — `<EE>` 제거는 실제 결함이었고
   고친 게 맞지만 정지의 원인은 아니었다. 새 빌드로도 멈췄다.
2. 「라벨 표의 이스케이프가 문제」를 `#1220` 「컨디션」으로 폐기했던 것 —
   폐기가 틀렸다. `#1220` 은 `f6cf c9 f6f1` 로 **F6** 만 쓴다. F4 와 F6 를 같은
   부류로 묶은 것이 오판이었다. 대조군을 볼 때 코드까지 봐야 했다.

### 4.13 F4 슬롯이 원본 글리프를 덮고 있다 ← 미해결

`F4` 슬롯 57개가 **원본 글리프를 전부 덮어쓴다.** 덮이는 글리프에 이런 것들이
있다.

| 글리프 | 내용 | 쓰이는 곳 |
|---|---|---|
| `0x00` | 魔 | 원문 `<F4><魔>` (미번역 세그먼트에 남아 있다) |
| `0x01` | 士 | 같음 |
| `0x02` | 見 | 같음 + 「アルヒ<見>ーヌ」 |
| `0x04` `0x05` | ◀ ▶ | **메뉴 화살표** |
| `0x06`~`0x1F` | ガギグゲゴ… | 미번역 이름의 탁음 가나 |

4.12 의 `no_f4` 는 표 영역만 막았고, `F4` 자체는 대사 전용 음절 57자가 계속 쓴다.
그래서 이 글리프들은 여전히 덮인다. 표시가 틀리는 문제이고 멈추지는 않는다.

**고치려면 `F4` 를 아예 안 써야 하고, 그러면 57칸이 부족하다.**

  단일 142 + F5 255 + F6 255 + F7 95 = 747 < 804

두 길뿐이다.

- `--engine` 을 켜서 `5D`/`D5` 를 쓴다. 다만 `5D`/`D5` 도 메뉴 렌더러가 모르므로
  표 영역에는 `no_5d` 제약이 같이 필요하다
- 고유 음절을 747 이하로 줄인다. 출현 1~2회 음절이 272자라 여지는 있다

**F7 이 95/95 로 꽉 찼다**는 점도 같이 걸린다. 다음에 새 음절이 하나라도 늘면
`5D`/`D5` 가 필요해지고 `--engine` 이 필수가 된다.

### 4.14 F4 를 비웠다 — 엔진 패치 기본 적용 (2026-09-08, 4.13 해결)

`--engine` 을 기본으로 켜고 **F4 를 배정 풀에서 뺐다.**

```
수용량  1314 -> 1257   (F4 57칸 제외)
필요량  약 836자        (여유 421자)
뱅크    단일 142 / F5 255 / F6 255 / F7 95 / 5D 255 / D5 255
롬      3MB -> 4MB
```

**되찾은 글리프 57개** — 전부 원본 유지로 확인했다.

| 글리프 | 내용 |
|---|---|
| `0x00` `0x01` `0x02` `0x1F` | 魔 士 見 入 (원문 `<F4><魔>` 등) |
| `0x04` `0x05` | ◀ ▶ 메뉴 화살표 |
| `0x06`~`0x1F` | ガギグゲゴ… 탁음 가나 |

그 57자는 새 폰트 영역 `0x300000`(뱅크 `$F0`)으로 옮겼다.

**`5D`/`D5` 도 위험 프리픽스다.** 엔진 패치는 이스케이프 판별 두 곳(`$950F`
대사, `$5CFA` 옵션·엔딩)만 고친다. 메뉴·표 렌더러는 모른다. 그래서
`krcodec.RISKY_PREFIX = {0xF4, 0x5D, 0xD5}` 를 두고, 메뉴·표 영역
(`0x04e000` 이상)과 단어표·이름표 음절은 이 프리픽스를 받지 않는다.

**배정 알고리즘을 바꿨다.** 처음엔 위험 슬롯을 만나면 건너뛰고 보류했다가
뒤의 대사 음절에게 주는 방식이었는데, 안전 슬롯이 먼저 소진되면 뒤에 오는
희귀한 표 음절이 빈손이 된다 — 단어표 `[07]` 「에놋」 의 「놋」 이 걸렸다.
지금은 **뒤에 남은 표 음절 수를 미리 세어 안전 슬롯을 그만큼 남겨 둔다.**

**`備`/`ゆ` 노출을 재봤다.** 이 두 바이트가 프리픽스가 되므로 미번역 일본어에
있으면 깨진다 (1.2.2 의 경고). 미번역 603개 중 5개뿐이고 전부 제어 코드 위주의
데이터다 (`#668` `#1316` `#1317` `#1434` `#1502`). 라벨·몬스터·화자 이름표에는
하나도 없다.

**삽입 검사를 손봤다**

- `[3]` 새 폰트 영역 `0x300000`~ 까지 훑는다 (안 하면 804 중 747만 보인다)
- `[5]` 엔진 패치가 고치는 자리를 허용 목록에 넣었다 (`$950F` `$5CFA` `$9548`
  + 새 코드 `$F200` `$F260` `$F300`)
- `[9]` 절대 개수 대신 **원본과의 차이**를 본다. 제어 코드마다 파라미터 길이가
  달라 이스케이프와 구분할 수 없다 — `#1187` 「`<FD>ゆ<F0>`」 의 `ゆ`(0xD5)는
  `FD` 의 파라미터인데 프리픽스로 오인됐다. 원본에 있던 것은 게임이 그대로 돌던
  것이므로 새로 넣은 것만 잡는다
